# Harmonia 重写方案

> 最后更新：2026-10-12（新增第 14 节：iOS App，v0.2.0；第 15 节：Windows CLI，v0.3.0）。

---

## 1. 摘要

旧项目的问题是**方向失控**，不在于代码写得差：4 天写了 8 万行以上代码，大部分花在对抗“服务端完全恶意”的自研授权链和恢复连续链、多个协议版本并存，以及三平台系统级服务的边角问题上；而核心流程至今走不通。

重写原则：

1. **用户路径优先**：完成的标准是验收清单（第 8 节）中的流程能闭环，不以测试数量或“证据文件”为准。
2. **安全刚好够**：机密性靠端到端加密；授权与完整性由自己部署的服务端执行。设备端只防常见风险，密钥下发到设备后的风险由使用者承担。
3. **只用标准构件**：libsodium 原语 + HTTPS + minisign。不做 PAKE，不做 DAG，不允许多个协议版本并存。
4. **范围收窄**：Android、Cloudflare Workers 服务端、Linux 与 macOS CLI。
5. **单仓库，设计文档常驻**：`docs/` 是唯一事实来源，代码变更先改文档。

本次交付目标：**v0.1.0，一个可以闭环的完整产品，而不是 demo。**

## 2. 旧项目复盘

### 2.1 规模与现状

| 模块 | 代码量 | 测试 | 提交（10-03 ~ 10-06） | 现状 |
| --- | --- | --- | --- | --- |
| core-go | ~50,000 行 | ~30,800 行 | 75 | 恢复与 DAG 相关约 2.3 万行（含测试）；同一能力有多套并行实现 |
| mobile | ~17,900 行 Dart + ~9,200 行原生 | ~7,800 行 | 45 | 冷启动无法恢复会话；登录后必然停在走不通的“等待授权”页 |
| server | ~4,600 行（高密度） | ~4,900 行 | 26 | 两层路由重复校验；多个版本的路由并存 |
| protocol | `wire.ts` 59 行 + 8,100 行向量 | — | 16 | 实际在用的协议不在这个仓库里 |

另外，2026-10-05 五个仓库合计删除了约 1 万行设计文档，次日又做了一次跨四个仓库的破坏性重构。

### 2.2 与定位逐条对照

| # | 定位 | 旧实现 | 新方案 |
| --- | --- | --- | --- |
| 1 | 解决 AI Agent 环境的密钥配置 | 未提及 AI；明确“不做容器和 cron” | `exec` 与 rc 注入覆盖终端和常驻进程；提供 Agent 接入文档 |
| 2 | 个人多设备 | 多账号公开实例 + 邮件体系 | 单实例单账号，不发邮件 |
| 3 | 手机负责信任与管理 | 方向一致，但实现失控、流程断裂 | 扫码配对；手机是账号级管理设备 |
| 4 | 成熟组件，不追求复杂自研协议 | 自研 DAG、证书 v3/v4/v5、BoringSSL SPAKE2 | 只用 libsodium、minisign 和标准哈希 |
| 5 | 环境三档权限，降权立即生效 | 客户端验证授权历史 | 服务端每次请求执法 |
| 6 | 只能经 App/CLI 修改，导入只同步选中项 | 写入签名 + 续办状态机 | 在线写入 + 幂等键 |
| 7 | 显式本地例外 | 有 | 保留 |
| 8 | 后台服务，清理不破坏原环境 | 系统级服务、逐 key 记录原值 | 用户级服务；Shell 集成按 5.8 刷新并恢复接管前的变量 |
| 9 | 系统验证优先，PIN 兜底；恢复后先轮换 | 每次操作都做系统验证；PIN 原生工作流；恢复依赖连续链 | App 锁（系统验证 / PIN）只控制界面；恢复流程简化 |
| 10 | 开源自托管，控制复杂度 | 5 个仓库 + submodule，证据文化 | 单仓库 + 防失控规则 |

### 2.3 根因

1. 没有用户路径层面的定义，开发由安全门槛和证据驱动。
2. 威胁模型定得过高，衍生出授权链、过渡链、DAG 和多个证书版本。
3. 旧路径从不删除，并行实现层层叠加。
4. 核心闭环还没跑通，就先攻坚平台边角。
5. 设计文档被删除后，没有可以对照的依据。

### 2.4 保留的资产

- `design/icons`、`design/mascot`，以及 `design_system.dart`（按需取用）。
- Cloudflare 的 Fork 部署和 Actions 更新流程。
- shell 值转义规则、`__HARMONIA_` 保留前缀、旧更新设计中的经验（详见 5.10 和附录）。
- 不保留：旧代码、旧协议、旧测试向量、旧证据文件。旧仓库归档为只读。

## 3. 产品定义

### 3.1 使用者与场景

**一个人**，拥有 1～2 台 Android 手机，以及若干台 Mac、Linux 电脑或服务器（包括运行 AI Agent 的机器）。

| 场景 | 做法 |
| --- | --- |
| 在终端运行 Agent 或 CLI 工具 | 激活环境后，新开的终端里直接可用 |
| Linux 服务器上常驻的 Agent | 用户级服务开机后自动同步；进程用 `harmonia exec` 启动，或在服务配置中引用 `env.sh` |
| 不想把 Key 贴进 AI 对话 | Agent 从环境变量读取 Key |
| 更换或轮换某个 Key | 手机上改一次，所有获授权设备在 3 秒内同步（在线时） |
| 设备退役或丢失 | 手机上撤销该设备，服务端立即回收，设备联网后自动清除本地数据 |

### 3.2 本次范围（v0.1.0）

**做：**

- 服务端：Cloudflare Workers + Durable Object（SQLite），实时推送。
- Android App（Flutter）：首次设置、App 锁（系统验证 / PIN）、环境与变量管理、扫码批准设备、权限管理、撤销、多管理设备、恢复与轮换恢复码、修改密码、应用内更新。
- CLI（Go，macOS arm64/amd64、Linux amd64/arm64）：登录、配对、实时同步、多环境激活与优先级、rc 注入、`exec`、本地覆盖、选择性导入、写入、用户级后台服务、自更新、卸载。
- 发布：GitHub Releases（签名 APK、CLI 二进制、签名清单）、安装脚本、服务端发布仓库（用户 Fork 后在 Cloudflare 导入部署）。

**不做（已冻结）：** Windows、Docker 自托管、fish shell、macOS 图形界面 App 的环境注入、环境钥轮换、App 后台推送、实例重置功能（确有需要时删库重建）、团队与共享、Passkey、浏览器扩展。

> iOS App 不在 v0.1.0 范围内，放在 v0.2.0，见第 14 节。
>
> Windows 在 v0.1.0 中冻结不做，v0.3.0 增加 Windows 上的 CLI，见第 15 节。
>
> Docker 虽然不在本次范围内，但服务端核心逻辑要与存储接口分离，方便以后补一个 Node 适配层。

### 3.3 核心概念

| 概念 | 定义 |
| --- | --- |
| 实例 | 一个 Workers 部署，可以有多个相互隔离的账号 |
| 账号 | 邮箱 + 密码。密码**只用于登录**，不参与加密 |
| 管理设备 | 具备管理功能的客户端（目前只有 Android App），持有全部环境的密钥，可以批准、调整权限、撤销设备，可以轮换恢复码。可以有多台。发起配对时客户端声明是否具备管理功能，只有具备的才能被批准为管理设备 |
| 客户端设备 | CLI，按环境获得 RO / RW / Admin 权限。Admin = 读写 + 环境改名或删除；不能批准设备 |
| 环境 | 一组变量，拥有独立的 32 字节环境钥（保留 `keyVersion` 字段，本次不实现轮换） |
| 激活与顺序 | 每条授权带“是否激活”和顺序，存在服务端，可以在管理设备上（拖动排序、开关）或设备本身（CLI 命令）修改；新授权默认激活并排在最后。激活只是使用上的便利，不是安全边界：设备能读取什么只由授权决定 |
| 本地覆盖 | 对某个已存在变量设置仅本机生效的值，不上传；云端删除该变量或失去授权后，覆盖失效 |
| 恢复码 | 128 位随机数，离线保存；在失去全部管理设备时用于恢复 |

## 4. 安全口径

### 4.1 保证的

1. **服务器只保存密文。** 数据库泄露、云厂商、备份外流都拿不到变量值。
2. **即使服务器被完全控制，也拿不到明文**，前提是你没有批准一台假设备：
   - 配对时会核对公钥指纹，服务器无法偷换公钥。
   - 管理设备只给持有有效设备证书的设备封装环境钥，服务器无法往设备列表里塞假设备来骗取密钥。
   - 只拿到密码，只能发起配对请求，仍然需要你在管理设备上扫码核对。
3. **降权、撤销、删除立即生效**（在服务端诚实的前提下）：服务端同步删除对应的密文、封装、授权和会话，并断开该设备的实时连接。
4. **尽力回收**：设备联网后，一旦发现自己被撤销或失去授权，就主动清除本地密钥、缓存和 `env.sh` 中对应的变量。离线设备最晚在授权到期时停用。

### 4.2 明确不保证的

1. **密钥下发到设备后，风险由使用者承担。** 已复制或已泄露的值无法追回，也不另外设计机制去追。
2. **手机被他人拿到，且对方知道 App PIN 或能通过指纹验证，不在防护范围内。** 这种情况下，用另一台管理设备或恢复码撤销它即可。
3. **在电脑上，同一用户的任何进程以及 root 都能读到变量**，包括 `env.sh` 文件和进程环境。Agent 运行 `env` 也可能把值带进日志或对话。Windows 上开启“写入用户环境变量”后，值保存在当前用户的注册表中，本用户之后启动的所有程序（不只是终端里的）都会带上这些变量，见 15.3。
4. **服务器被攻破后，撤销可能被它假装执行。** 由于本次不实现环境钥轮换，这种情况不做补救。
5. **服务器可以回滚或隐藏数据**：它可以把变量换回旧密文，或不下发新变量。这不会泄露明文。
6. **元数据可见**：变量名、环境名、设备名、访问时间。
7. **恢复码等于整个账号**：恢复码泄露，对方就能登记管理设备；恢复码和所有手机都丢失，数据永远无法找回。
8. **不在范围内**：已 root 的手机在 App 解锁期间（内存中的密钥可以被读取）、用户主动运行的恶意代码、依赖库的供应链风险（发布签名能缓解发布环节，但无法消除）。App 锁定时，root 也只能在这台手机上逐个尝试 PIN（见 4.3）；6 位数字 PIN 的强度有限，按手机算力估计，最快一两天可以试完，更长的 PIN 相应更难。

### 4.3 设备端必须做到的底线

- Android：关闭系统备份（`allowBackup=false` 加数据提取规则）；设备密钥用本机数据密钥加密，只有输入 App PIN 或通过指纹验证才能解开，Keystore 参与每一次 PIN 尝试，PIN 无法拿到手机以外暴力破解（[protocol.md](protocol.md) 2.5）；App 锁定时清除内存中的密钥；不用明文 SharedPreferences。
- iOS（v0.2.0）：与 Android 同样的底线，实现方式见 14.3：钥匙串条目全部仅限本机，App 数据不进备份；设备密钥只有 App PIN 或面容 ID / 触控 ID 能解开，Secure Enclave 参与每一次 PIN 尝试。
- CLI：`~/.harmonia/` 目录权限 0700、文件 0600（Windows 上是只允许本人、系统和管理员访问的访问控制列表，不继承上级目录的权限），写入采用原子替换。CLI 目前不具备管理功能；以后要支持作为管理设备，必须先把设备密钥加密保存（系统钥匙串或口令），再在配对时声明具备管理功能。
- 两端：收到“设备已撤销”的响应后立即自我清除，然后回到未授权状态。

## 5. 技术方案

### 5.1 仓库结构

```
harmonia/                     # 唯一开发仓库
├── mise.toml                 # [tools] + [tasks]
├── docs/                     # design.md / protocol.md / threat-model.md / acceptance.md
├── vectors/                  # 三端共用测试向量
├── server/                   # TypeScript，完全自包含（发布时推送到 harmonia-worker 发布仓库）
│   ├── src/core/             # Hono 路由、权限、同步、推送；依赖 Storage 接口
│   └── src/workers/          # Durable Object 适配 + 入口
├── cli/                      # Go：cmd/harmonia + internal/{crypto,api,store,sync,merge,shell,service,update}
├── app/                      # Flutter：lib/core（纯 Dart，可无界面运行）+ lib/ui
├── e2e/                      # 端到端脚本
├── design/                   # 图标、吉祥物
└── 每个子目录有自己的 AGENTS.md
```

版本：全产品统一版本号。打 `vX.Y.Z` tag 时同时发布 CLI 和 APK；服务端随 main 分支推送到发布仓库。CLI 和 App 的版本号在构建时取自标签；服务端的版本号写在 `server/package.json`（`/instance` 返回的就是它），打标签前要改成将要发布的版本号（预发布标签对应去掉后缀的版本号），发布流水线会核对，不一致时不发布。

### 5.2 密码学

| 用途 | 构件 | Go | Dart | TS |
| --- | --- | --- | --- | --- |
| 变量值加密 | XChaCha20-Poly1305；AAD 为 `["harmonia/value", envId, keyVersion, name]` | `x/crypto/chacha20poly1305` | `sodium` | — |
| 环境钥封装 | libsodium sealed box | `x/crypto/nacl/box` | `sodium` | — |
| 设备身份与证书 | Ed25519 | `crypto/ed25519` | `sodium` | WebCrypto 验签 |
| 密码 | 客户端 Argon2id（salt 由服务器下发）→ authKey → 服务端再做 PBKDF2-SHA256 存储 | `x/crypto/argon2` | `sodium` | WebCrypto |
| 恢复码 | 128 位随机数，Crockford Base32 分组显示（不含易混淆的 I、L、O、U）；用 HKDF-SHA256 分用途派生 Ed25519 和 X25519 密钥 | 标准库 | `sodium` / `cryptography` | — |
| 更新清单 | minisign（Ed25519） | `aead.dev/minisign` | Dart 侧用 Ed25519 验证 minisign 格式 | — |
| App 本机密钥保护 | Argon2id(PIN) → Keystore HMAC-SHA256 → XChaCha20-Poly1305 封装本机数据密钥；可选 Keystore AES-256-GCM（指纹）。见 protocol 2.5 | — | `sodium` + Keystore（Kotlin） | — |

签名原文统一采用 JSON 字符串数组，首项为用途域。全项目只有三种签名：设备证书、登录挑战、恢复钥轮换记录。

### 5.3 密钥体系

```
密码 ──Argon2id──▶ authKey：只用于登录
恢复码 ──HKDF──▶ 恢复签名钥：签发恢复登记的设备证书和恢复钥轮换记录
      └─HKDF──▶ 恢复加密钥：服务端为每个环境保存一份封装给它的环境钥
每台设备：签名钥 + 加密钥（Android 用本机数据密钥加密，数据密钥由 App PIN 或指纹解开；CLI 存为 0600 文件）
每个环境：环境钥，封装给全部管理设备、获授权的客户端设备和恢复钥
```

**设备证书**：由批准者（某台管理设备或恢复签名钥）签名，内容为 `[用途域, deviceId, kind, signPub, boxPub, issuerKeyId]`。管理设备在本地维护“受信签发者集合”，只为证书可以追溯到该集合的设备封装环境钥。不保存历史，不做 DAG。

### 5.4 认证与会话

| 会话 | 获取方式 | 权限 | 有效期 |
| --- | --- | --- | --- |
| 密码会话 | 密码登录 | 只能创建配对请求 | 15 分钟 |
| 设备会话 | 设备签名钥签名服务端下发的 nonce | 按该设备当前的授权 | 1 小时，自动续期 |
| 恢复会话 | 恢复签名钥签名 nonce（只需要恢复码，不需要密码） | 只能读取恢复封装、登记本机、轮换恢复码、设置新密码 | 15 分钟 |

限流与风控见 5.12。

### 5.5 服务端

- **运行时**：Hono + 一个名为 `instance` 的 Durable Object（SQLite 存储），所有状态都在里面，天然串行、原子。
- **数据表**：`account`（单行）、`devices`、`pairings`、`pairing_blocks`、`environments`、`envelopes`、`grants`、`variables`、`sessions`、`idempotency`、`meta(head_seq)`。每次变更时 `head_seq + 1`，并写入受影响行的 `updated_seq`。
- **API**（`/api/v1`）：
  - 实例：`GET /instance`（产品标识、服务端版本、协议版本、是否已初始化）
  - 初始化：`POST /setup`
  - 认证：`GET /auth/prelogin`、`POST /auth/login`、`POST /auth/challenge`、`POST /auth/device-session`
  - 账号：`PUT /account/password`（管理设备）
  - 配对：`POST /pairings`、`GET /pairings/{id}/events`（发起方等待连接）、`GET /pairings/{id}/status`、`GET /pairings`、`GET /pairings/{id}`、`POST /pairings/{id}/approve`、`POST /pairings/{id}/reject`
  - 同步：`GET /sync?since=N`；推送：`GET /events`（WebSocket）
  - 环境：`POST|PATCH|DELETE /environments[/{id}]`
  - 变量：`PUT|DELETE /environments/{id}/variables/{name}`，需要带幂等键
  - 设备：`GET /devices`、`PUT /devices/{id}/grants`、`PATCH /devices/{id}`、`POST /devices/{id}/revoke`
  - 恢复：`POST /recovery/challenge`、`POST /recovery/session`、`GET /recovery/envelopes`、`POST /recovery/enroll`、`POST /recovery/rotate`、`GET /recovery/rotate/{key}`
- **实例首页**（`GET /`）：在浏览器里直接打开服务器地址时显示的一张静态页面，让部署的人确认服务器已经跑起来，也让拿到地址的人知道接下来怎么做。
  - 内容：Harmonia 图标与一句话介绍、“运行中”、这台服务器的地址（取自访问时用的地址，供填进 App 和命令行）和地址的二维码（内容就是地址本身，由服务端生成后内嵌在页面里，供 App 的“连接服务器”页扫码填写；用手机相机直接扫则打开这张首页）、三步开始使用（下载 App、注册或登录、在电脑上安装命令行并 `harmonia login`）、三句话说明工作方式（手机负责授权、服务器只存密文、电脑自动同步）、项目主页和服务端仓库的链接。
  - 口径：不带脚本，不加载任何外部资源，链接只指向 GitHub 上的项目仓库；不显示这台服务器的配置和状态（是否开放注册、有没有账号、版本）；注明服务器由部署者自行运营、与项目方无关；要求搜索引擎不收录。
  - 配色与图标沿用 App，跟随系统的深浅色。
- **执法规则**：每个请求都检查会话、设备状态、授权有效期和角色。`rotation_required` 为 true 的设备，除轮换恢复码外，其他管理操作一律拒绝。
- **同步**：返回 `updated_seq > since` 且该设备可见的环境、授权、自己的封装和变量（含墓碑），以及 `headSeq`。失去访问权的环境以“已移除”项下发。
- **冲突**：同一变量按服务端接受顺序后写覆盖先写；同一幂等键重放时返回原结果。
- **表结构迁移**：用 schema 版本号加顺序执行的迁移脚本，保证升级不丢数据。
- **删库重建**：不提供功能入口，文档说明在 Cloudflare 后台删除 Worker（连同 Durable Object 数据）后重新部署。具体步骤在实现时核实。

### 5.6 实时推送

- 客户端用设备会话建立 `GET /api/v1/events` WebSocket 连接，服务端使用 Durable Object 的 Hibernation API。
- 推送消息**只是提示**，不携带任何密钥或变量值：
  - `{"type":"changed","headSeq":N}`
  - `{"type":"pairing"}`（只推给管理设备）
  - `{"type":"revoked"}`（推送后关闭连接）
- 配对发起方另有一条等待连接 `GET /api/v1/pairings/{id}/events`，用来接收批准结果，同时让服务端知道它还在等待（协议 3.5.1）。
- 客户端收到 `changed` 后调用 `/sync` 拉取。拉取是唯一的数据来源。重连后立即同步一次。
- CLI 后台服务：长连接 + 心跳，断线后指数退避重连，另外每 5 分钟兜底同步一次。
- App：只在前台时连接，不做后台推送。
- 目标：在线设备 3 秒内收到变化。

```

harmonia uninstall
```

- 本地状态放在 `~/.harmonia/`。CLI 和后台服务通过文件锁协调，不做本地 IPC。
- 合并规则：激活的环境按顺序叠加，同名变量由排在前面的环境提供；本地覆盖先替换所在环境中的值，再参与合并；授权已过期的环境在本地停用。
- 激活与顺序存在服务端（随授权同步），`activate`、`deactivate`、`order` 直接提交，需要联网；`order` 把列出的环境按给定顺序移到最前面，其余环境保持原有顺序。`harmonia env list` 显示顺序、是否激活，以及同名变量由哪个环境提供。
- 后台服务：
  - Linux 使用 `systemd --user` + `loginctl enable-linger`，开机后无需登录即运行。普通用户（例如通过 SSH 登录）通常没有权限自己开启 linger：开启失败时，在终端里询问是否用 sudo 开启（默认 Y），不同意或没有终端时给出要执行的命令。
  - macOS 使用 LaunchAgent，登录后运行。
  - Windows（v0.3.0）使用当前用户的计划任务，登录后运行，见 15.4。
  - 后台服务负责维持推送连接、同步、重写 `env.sh`，并每 24 小时检查一次更新。

### 5.8 rc 文件注入与提示符刷新

- 后台服务把合并结果原子写入 `~/.harmonia/env.sh`（0600），内容是普通的 `export KEY='value'`，值一律使用单引号字面量安全转义。
- **安装时询问**：安装脚本装好 `harmonia` 后，如果有终端可以交互，依次询问是否安装 shell 集成和后台服务，直接回车即安装（默认 Y）。shell 集成仍会先显示要修改的文件和内容；没有终端（例如在脚本或 CI 中运行）时跳过询问，只提示对应命令。两者在接入账号之前安装也没问题：`env.sh` 不存在时不加载变量，后台服务在接入前等待（2026-10-07 用户确认）。
- `harmonia login` 完成后，只提示还没有安装的 shell 集成或后台服务。
- `harmonia shell install` 先告诉用户要修改的文件和内容，确认后才写入（默认 Y）；已存在的 Harmonia 标记块直接更新，不重复添加：
  - zsh 写入 `~/.zshenv`，这样非交互的 zsh 也能读到。
  - bash 写入 `~/.bashrc`，并确保 `~/.bash_profile` 或 `~/.profile` 会加载它。
  - 写入带标记的加载代码，交互式 Shell 同时注册提示符刷新函数；首次安装后，已有终端需按安装提示手动加载一次，或新开终端。
  - 如果 rc 文件是符号链接，不自动修改，只提示用户自己添加。
- **提示符刷新**：支持 Bash 5.1 及以上、Zsh 5.0 及以上的交互式 Shell。Bash 使用 `PROMPT_COMMAND`，Zsh 使用 `precmd` 钩子；每次主提示符显示前检查本地变量，有变化才应用，不联网、不启动 Harmonia CLI。保留已有提示符功能和命令退出状态，重复加载不重复注册。
- **变量清理**：仅处理 Harmonia 托管的变量；新增和修改使用最新合并值，不再托管时恢复本终端接管前的状态，原来不存在则移除。
- **生效边界**：停留在提示符时收到更新，按一次空回车即可刷新；直接执行的第一条命令可能使用旧值。正在运行的程序不受影响。
- 手动修改 `env.sh` 会在下一次同步时被覆盖。在某个 shell 里手动 export 的值只影响那个 shell，本地变量文件下次变化时重新应用 Harmonia 的值。
- systemd、launchd、cron 不读 rc 文件，需要用 `harmonia exec` 启动，或在配置里引用 `env.sh`。文档会给出示例。

### 5.9 Android App

- **技术选型**：Flutter，`lib/core` 是纯 Dart，加密使用 `sodium_libs`；存储使用 `flutter_secure_storage`（Keystore 包装）；App 锁使用 App PIN 和系统指纹（`androidx.biometric`，原生实现）；扫码使用 `mobile_scanner`；路由使用 `go_router`。**不写原生桥代码**。
- **单一状态机驱动路由**：

```
启动 → 有已保存的服务器？ ─否→ [连接服务器]
        └是→ 本机是已授权设备？ ─是→ [App 锁] → 需要轮换恢复码？ ─是→ [强制轮换]
               │                                             └否→ [主页]
               └否→ [登录 / 注册] → [设置 App PIN] → 账号已初始化？ ─否→ [首次设置] → [恢复码确认] → [主页]
                                                           └是→ [本机未授权]
                                                                  ├ 让管理设备批准（显示二维码和核对码）
                                                                  └ 用恢复码恢复 → [强制轮换] → [检查其他设备] → [主页]
```

  `go_router` 的 redirect 只读取这个状态机，页面自己不决定跳转。跨阶段的跳转一律是替换，不入栈。

- **App 锁**（格式见 [protocol.md](protocol.md) 2.5）：
  - **设置 App PIN**：登录成功后，在保存任何设备密钥之前，必须先设置 App PIN（从登录页直接用恢复码恢复时，在恢复之后、保存之前设置）（6–16 位数字，输入两次）。这样设备密钥从第一次写入就受保护，中途退出也不会留下没有保护的密钥。App 锁不能关闭。
  - **开启指纹**：设置完 PIN 后，如果手机支持强生物识别（Class 3，例如指纹；多数手机的普通人脸解锁达不到这个等级，不提供），不再询问，直接弹出系统验证来开启指纹解锁（2026-10-12 调整，Android 与 iOS 相同）：验证通过即开启并继续；用户取消或验证失败时留在这一页，可以重试，也可以点“跳过”。以后可以在设置中开关。不提供“锁屏密码”解锁：它和 App PIN 作用重复，而且知道锁屏密码的人就能打开 App。
  - **解锁时机**：打开 App，或在后台满 5 分钟后回到前台。开启了指纹时先弹指纹，取消或失败可以改输 PIN；没开启时输入 PIN。
  - **再次验证**：批准设备、修改权限、撤销设备、更换恢复码、修改登录密码、退出登录、修改 PIN、开关指纹时，再验证一次（指纹或 PIN 均可）。
  - **解锁就是解开密钥**：验证通过指的是用指纹或 PIN 解开本机数据密钥，不是界面上的判断。锁定时（后台满 5 分钟，或进程结束）清除内存中的全部密钥，解锁后再解开。
  - **输错限制**：PIN 连续输错 5 次后等待 30 秒，此后每错一次等待时间翻倍，最长约 30 分钟。错误次数保存在本机，重启 App 不清零。不会因为输错而自动清除数据。
  - **指纹失效**：用户新增或删除指纹、关闭锁屏后，系统会作废指纹密钥。App 发现后改用 PIN 解锁，解锁后提示“手机指纹有变化，指纹解锁已关闭”，用户可以在设置中重新开启。数据不受影响。
  - **忘记 PIN**：开启了指纹时，用指纹解锁后在设置中修改 PIN。没开启指纹时，在锁屏页选择“忘记 PIN”，清除本机数据后重新登录，再让另一台管理设备批准或用恢复码恢复。这台手机此时已经无法通知服务端，它的旧设备记录需要在其他设备上移除，界面要说明这一点。
- **页面**：连接服务器（填写地址，或扫描服务器首页上的二维码；扫到后直接连接，2026-10-12 增加）、首次设置、恢复码展示与重输、更换恢复码说明、登录、本机未授权、等待批准、恢复码输入、恢复后检查其他设备、设置 App PIN（含开启指纹）、App 锁、环境列表、环境详情、变量编辑、设备列表（含待批准请求）、添加设备（扫码 → 核对 → 选择权限 → 验证 → 批准）、设备详情（含环境的激活开关和拖动排序，并显示同名变量由哪个环境提供）、设置（服务器、修改 App PIN、指纹解锁、修改密码、轮换恢复码、检查更新、关于、退出）。“关于”页显示版本，以及 App 里用到的全部开源项目的版权说明和许可证全文（2026-10-12 增加）：Dart 包、Flutter 引擎和 libsodium 的部分由 Flutter 构建时自动收集，BudouX 模型和 Android 原生依赖（AndroidX、Kotlin）在 `app/lib/app/licenses.dart` 中补登记。
- **文案**：不出现任何内部术语；每条错误都给出下一步该做什么。成段的文字只在句子之间分行，段与段之间不留额外间距；句子内部按词折行，不把一个词拆到两行——词的边界由 Google BudouX 的简体中文模型判断（`app/assets/budoux/zh-hans.json`，Apache-2.0，实现见 `app/lib/core/phrases.dart`），Android 与 iOS 相同（2026-10-12 增加）。

- 每次进入创建独立的内存会话，使用合成账号、设备、环境和变量；调试内的增删改查、授权、登录、注册、恢复、PIN、生物识别与更新都由模拟实现处理。不得复用真实控制器、存储、身份验证服务或网络客户端；输入真实格式的地址也不能发出请求。复制、扫码、PDF 保存、更新安装和外部跳转只显示模拟结果。调试表单不使用系统自动填充或保存密码；调试期间阻止真实配对弹窗进入，返回目录取消未完成的模拟等待。
- 模拟操作必须产生对应的内存状态变化，刷新和跨页查看保持一致；退出调试入口即丢弃，重新进入恢复初始样例。调试页面始终有返回目录和退出调试的入口，模拟失败不阻碍退出。
- 今后新增或调整页面、弹窗和分步流程时，必须同步更新页面调试目录及对应的合成场景；新增外部副作用必须同时提供模拟实现。新增页面不能只出现在正常流程而缺少调试入口。

### 5.10 配对

1. 新设备在本地生成密钥，调用 `POST /pairings`，得到 `pairingId` 和 `secret`。
2. 计算指纹 = `SHA-256(["harmonia/pairing", pairingId, signPub, boxPub])`。二维码包含 `pairingId` 和完整指纹；人工核对码是指纹的前 80 位，显示为 16 个 Crockford Base32 字符（4 组，每组 4 个）。
3. 手机扫码或手输核对码，拉取该配对请求并重新计算指纹比对。比对一致后，显示设备名和平台，让用户选择环境、角色和有效期，或者选择“作为管理设备”。
   - 管理设备在前台且已解锁时，收到新的配对请求（推送或同步时发现）会直接打开批准页，电脑和手机发起的请求都一样。App 在后台时不提醒；回到前台或解锁后先同步，发起方仍在等待的请求随即弹出。每个请求只弹出一次，已经有弹出的批准页时不再叠加，其余请求留在设备页的待批准列表中。
   - 弹出的批准页和列表中打开的一样，没有经过扫码：用户必须勾选“核对码一致”才能批准，页面同时提示“此刻没有在其他设备上登录就拒绝并修改密码”。
4. 手机签发设备证书、封装环境钥，调用 `approve`；新设备通过等待连接得知已批准，换取设备会话后完成同步。
5. **发起方离开**：新设备在等待期间一直保持等待连接（协议 3.5.1）。CLI 按 Ctrl+C 或进程退出、新手机离开等待页或 App 被关闭，连接断开（或 25 秒没有心跳）后请求立即作废：管理设备不再弹出，已经打开的批准页改为显示“这次请求已失效”，只留“关闭”。等待连接因网络中断断开时同样作废，新设备提示重新发起。
6. **拒绝并阻止**：批准页显示请求来自的 IP。拒绝时可以勾选“30 分钟内阻止这个网络再次发起请求”；被阻止的一方看到“这个网络暂时不能发起配对，请稍后再试”。修改账号密码时，所有待处理的请求一并作废。

### 5.11 更新机制

- **发布源**：主仓库的 GitHub Releases。每个 Release 附带 `manifest.json`，内容包括版本号、各平台包的下载地址、SHA-256、大小，以及支持的协议版本，并附带 minisign 签名。公钥内置在客户端中。
- **更新渠道**（2026-10-07 增加）：
  - 正式版：只接收不带后缀的版本；测试版：接收全部版本中最新的一个。标签带 `-rc.x`、`-beta.x` 等后缀的发布为预发布，只进入测试版渠道。
  - 版本顺序：同一基础版本内，正式版 > rc > beta > alpha，同类后缀按数字比较。例如 `0.1.2 > 0.1.2-rc.2 > 0.1.2-rc.1 > 0.1.2-beta.3 > 0.1.1`。
  - 渠道清单放在固定的预发布 `update-feed` 中：`stable.json`、`beta.json` 及其签名。发版时由 `releasetool feed` 判断，只有版本更新时才覆盖，补丁旧版本不会让渠道回退。正式版渠道收到带后缀的版本会拒绝。
  - 渠道在 App“设置 → 更新渠道”和 `harmonia update channel stable|beta` 中切换，默认正式版；测试版程序默认测试版渠道。安装脚本用 `HARMONIA_CHANNEL=beta` 安装测试版。
- **CLI**：
  - 后台服务每 24 小时（带随机抖动）检查一次，有更新时在 `status` 中和 stderr 上提示。
  - `harmonia update` 的步骤：下载 → 验证签名和哈希 → 运行新二进制的 `version` 自检 → 原子替换 `~/.local/bin/harmonia` → 重启用户级服务。旧版本保留为 `.old` 以便手动回退，全程不需要 sudo。
- **Android**：
  - App 在前台时检查，24 小时内最多检查一次。有更新时显示更新说明，用户确认后在 App 内下载 APK，验证哈希，然后交给系统安装器（需要 `REQUEST_INSTALL_PACKAGES` 权限）。
  - Android 与 iOS 共用下载进度界面：连接时显示等待状态，接收数据时按实际字节数与已签名清单中的总大小显示进度条、百分比和已下载大小；收完后显示校验状态。校验与缓存写入完成后才进入原有安装或分享步骤，下载失败仍留在 App 内提示重试。
  - 系统会校验 APK 签名必须与已安装版本一致。
  - `versionCode` 由版本号计算，顺序与版本顺序一致：基础版本 ×100 + 后缀分（alpha N → N，beta N → 20+N，rc N → 50+N，正式版 → 99），例如 `0.1.2-beta.1` → 10221、`0.1.2-rc.1` → 10251、`0.1.2` → 10299。不使用 CI 的 run_number。
- **服务端**：`/instance` 返回服务端版本和协议版本。客户端发现协议不兼容时，提示用户更新服务端（Sync fork 或 Actions 更新），或者更新客户端。
- **发布签名私钥**：只存放在 GitHub Actions secrets 中，测试使用临时生成的密钥。

### 5.12 限流与风控

规则和数值以 [protocol.md](protocol.md) 3.8 为准，这里说明取舍和界面表现。

- **目标**：攻击者的行为不能让合法用户无法登录。所以不做“同一账号失败 N 次就锁定”，也不让所有人共用同一份验证码尝试次数或发信额度，否则攻击者只要故意失败就能把用户挡在外面。
- **依据**：
  - 失败次数按网络计数。攻击者从别的网络失败多少次，都不会让用户所在网络的计数增加。
  - 密码会话只能发起配对，最终仍需管理设备批准，所以对密码登录可以管得严。
  - 登录验证码只在密码正确后发送，攻击者不知道密码就耗不掉这份额度；其他邮件单独计额度。
  - 设备会话、恢复会话靠签名，不受任何匿名请求的限流影响。管理设备随时可以修改密码，让攻击者手里的密码会话和配对请求全部作废；丢失全部设备时还有恢复码。
- **不做可信网络**：曾考虑把已接入设备用过的网络视为可信、单独放行，但移动网络常有大量用户共用一个出口 IP，误判后反而给攻击者放行；每次同步都要记录也有成本。去掉后，受攻击期间用户在任何网络登录都要多一步（2026-10-07 用户确认）。
- **开源部署的两种情况**：
  - 配置了发信：账号进入受攻击状态后，登录需要密码加邮件验证码，攻击者即使知道密码也登录不了；密码不对时不发邮件，不会被用来轰炸邮箱。
  - 未配置发信：没有邮件加验，改为把每个网络的免限制次数降为 1，并靠逐个网络递增的等待时间拖慢猜测。合法用户输对密码不受影响，输错时最多等几分钟。
- **残余影响**：受攻击期间，合法用户登录要多输一次邮件验证码，或在输错后等待；找回密码、重置账号的发信额度被攻击者用完时，最长约 1 小时内收不到新邮件，但已经收到的验证码仍然有效，也可以改用管理设备修改密码。
- **隐私**：网络标识只存 HMAC，原始 IP 只用于配对批准页的显示和“阻止这个网络”，随记录过期删除。
- **界面与 CLI**：
  - 被限流时显示需要等待的时间，例如“尝试次数过多，请 2 分钟后再试。如果不是你本人在尝试，请在管理设备上修改密码。”
  - 需要邮件加验时显示“这次登录需要邮箱验证码，已发送到 a***@example.com”，输入后继续登录。
  - 发信额度用完时显示“验证码发送次数过多，请稍后再试；已经收到的验证码 15 分钟内仍然有效。”
- **暂不做**：异常登录提醒（管理设备推送和失败记录）；隐藏邮箱是否已注册（目前登录、预登录会区分，已按网络限流）。

## 6. 关键流程

- **登录后**：先设置 App PIN（可选开启指纹），生成本机数据密钥。之后首次设置、配对、恢复中生成的设备密钥，一律用它加密后再保存。
- **首次设置**：手机生成设备密钥、恢复码（用户完整重输确认）、恢复公钥、authKey，然后调用 `POST /setup` 原子完成。之后引导用户创建第一个环境。
- **写入变量**：本地加密，`PUT` 时带幂等键；服务端接受后推送 `changed`；包括写入方在内的所有设备都通过 `/sync` 更新本地，不做乐观更新。写入必须在线。
- **批准设备**：见 5.10。授权行和封装在同一个事务中写入。
- **降权或升权**：只修改授权行。**新增环境授权**：管理设备验证目标设备的证书后，为它封装环境钥。
- **撤销**：服务端删除该设备的授权、封装和会话，推送 `revoked` 并断开连接；设备联网后自我清除。
- **删除环境或变量**：服务端删除密文并留下墓碑；所有设备同步后从缓存和 `env.sh` 中移除。
- **恢复**：获得恢复会话 → 解开全部环境钥 → 生成本机密钥，用恢复签名钥签发证书，然后 `enroll`（此时 `rotation_required = true`）→ 强制轮换：先显示说明页（新恢复码提交前不生效、只显示一次、完成前无法管理），用户确认后生成新恢复码，用户完整重输，重新封装全部环境钥，旧恢复钥签名轮换记录，`rotate`（带幂等键，结果不明时可以查询）。提交成功后，旧恢复码才失效。
- **恢复后检查其他设备**：恢复不会撤销任何已有设备，旧手机仍是有效的管理设备。因此强制轮换的完成页保存 PDF 后，进入“检查其他设备”页：
  - 列出账号中除本机以外的全部设备，管理设备在前、电脑在后，显示名称、平台和最后在线时间。
  - 说明旧手机仍然可以访问全部环境、批准和移除设备；已丢失或不再使用的设备应当移除。
  - 每台设备前有勾选框，默认都不勾选。勾选后点“移除所选（N 台）”：确认框列出所选设备的名称，确认后只验证一次身份，再逐台调用现有的撤销接口（不新增接口）。全部成功后进入主页；有设备没移除成功时留在本页，只保留未移除的设备并说明原因，可以重试或点“完成”。
  - 不勾选任何设备时点“完成”，保留全部设备，进入主页。
  - 没有其他设备时跳过这一页。只在这次恢复完成后出现一次：中途退出 App 后不再显示，之后仍可在“设备”页移除。主动轮换恢复码不显示这一页。
- **主动轮换恢复码**：流程与上面相同（同样先显示说明页，提交前再验证一次身份），轮换记录由管理设备签名。
- **修改密码**：已授权的管理设备验证 PIN 或指纹后，调用 `PUT /account/password`。
- **退出（logout）**：先通知服务端撤销本机（离线时先清本地，联网后补发），然后删除本地密钥和缓存（App 还要删除 PIN 槽、指纹槽和对应的 Keystore 密钥），并清空 `env.sh`。
- **卸载 CLI**：logout + 卸载服务 + 移除 rc 行 + 删除 `~/.harmonia` 和二进制文件。

## 8. 验收标准（v0.1.0）

### A. 交付物

- 服务端：发布仓库 + Fork 部署说明 + 升级方法。

### B. 核心流程（真实设备）

### C. 生命周期闭环

部署 / 升级服务端；安装 / 升级 / 重装 App（重装视为新设备）；安装 / 升级 / 卸载 CLI；配对 / 撤销 / logout；创建 / 删除环境和变量；授权 / 降权 / 到期；安装 / 移除 shell 集成和后台服务，重启后自动恢复；生成 / 轮换恢复码；修改密码。

### D. 异常场景

每种情况都要有明确的提示和下一步指引：

- 地址错误、不是 Harmonia 服务、服务端无法连接、协议版本不兼容
- 密码错误、登录被限流
- 配对码过期、扫错二维码、配对被拒
- 操作中途断网（写入、批准、轮换恢复码）
- CLI 离线时使用缓存；授权到期后停用；联网后自动追上
- 两台设备同时修改同一变量（最终一致）
- 删除一个正在使用中的环境
- 已撤销的设备再次联网
- 服务端升级后客户端继续可用
- App 被系统杀掉后重新打开
- 恢复码输错
- rc 文件是符号链接
- 更新包签名或哈希验证失败

### E. 自动化回归

`mise run test` 和 `mise run e2e` 全部通过。这是开发门禁，**不等于验收通过**。

### F. 最终验收：新用户测试

在全新的 Cloudflare 账号、没装过 App 的手机、干净的 Linux VPS 和 Mac 上，**只看 README** 完成“部署 → 使用 → 撤销 → 恢复 → 升级 → 卸载”的全过程。任何卡住的地方都算缺陷。

### G. 质量底线

- 界面和 CLI 输出中没有内部术语，每条错误都告诉用户下一步怎么做。
- 升级不丢数据：服务端有表结构迁移，App 覆盖安装后数据保留。
- 实时同步：在线设备 3 秒内收到变化；断线重连后自动补齐。

## 10. 防失控规则（写进 AGENTS.md）

1. 改动 API、数据格式、安全口径或用户流程之前，先更新 `docs/`，由用户确认。
2. 完成的标准是相关流程能闭环，不以测试数量为准。
3. 1.0 之前不做向后兼容，不保留并行版本；类型名和路由中不得出现 `v2`、`v5` 之类的后缀（`/api/v1` 前缀除外）。
4. 不新增密码学结构：除 5.2 所列之外，新增任何签名或加密格式都需要用户批准。
5. 不写没有入口的功能：每个公开方法都要有界面或命令在调用。
6. 体量预警：单个文件超过 500 行，或单个里程碑新增代码超过约 5,000 行，就停下来和用户确认。
7. 不提交过程产物（证据、验证记录、状态流水）；`docs/` 只放设计。
8. 界面和 CLI 文案面向用户，不出现内部术语。
9. 一次只推进一个里程碑，不预先实现后续功能。

## 11. 附录：旧项目的经验

- systemd 系统单元开启 `ProtectHome=true` 后无法访问 home 目录；用户级服务没有这个问题。
- 已经在运行的进程，环境变量无法从外部修改，文档必须写明。
- Android 的 `versionCode` 不能依赖 CI 的 run_number，迁移仓库后编号会回退。
- 更新检查失败时，不能显示“已是最新版本”；要区分网络错误、签名错误和元数据错误。
- 不要根据 Release 列表的第一项、发布时间或文件后缀来猜测最新版本，只认签名清单。
- Workers 上运行 Argon2id 的资源占用有风险，所以改为客户端计算 Argon2id。

## 13. 实现中的设计调整（2026-10-07）

| 项 | 方案原文 | 实际实现 | 原因 |
| --- | --- | --- | --- |
| 信任锚 | 管理设备维护“受信签发者集合”，证书逐级追溯 | 一把**账号根签名钥**：生成于首次初始化，封装给每台管理设备和恢复码；设备证书与每个环境钥封装都由它签名。设备首次接触账号时钉住 `rootPub`，配对指纹包含 `rootPub` | 更简单，没有证书链；还堵住了“服务器偷换封装”的漏洞（匿名 sealed box 本身不认证发送方） |

## 14. iOS App（v0.2.0，M10）

iOS App 与 Android App 是同一个 Flutter 工程（`app/`），`lib/` 下的界面和核心逻辑共用。除本节列出的差异外，页面、状态机、App 锁规则、配对和恢复流程都与 5.9、5.10 相同，协议和服务端不需要改动。

### 14.1 范围

**做：**

- `app/ios` 工程，最低支持 iOS 16；只面向 iPhone，iPad 上以 iPhone 兼容模式运行，不单独适配。
- Swift 原生实现，与 Android 的 Kotlin 部分一一对应：本机密钥保护、面容 ID / 触控 ID、恢复码 HTML 转 PDF、通过系统“存储到文件”保存、敏感内容复制、设备名。
- 界面沿用现有的 Material 风格，不另做一套 iOS 风格的界面。
- 发布未签名 IPA，App 内检查更新，下载新的 IPA 并交给签名工具。

**不做：** 上架 App Store 与 TestFlight、AltStore / SideStore 软件源、App 后台推送、iPad 布局、小组件、Apple Watch。

### 14.2 与 Android 的差异

| 项 | Android | iOS |
| --- | --- | --- |
| 协议中的 `platform` | `android` | `ios` |
| 默认设备名 | 用户在系统设置里给手机起的名字；取不到时用厂商 + 型号（2026-10-12 调整） | `iPhone`：iOS 16 起，系统只对苹果单独批准了权限的 App 提供用户起的设备名，自行签名的安装包拿不到。接入后可以在“设备详情”里重命名 |
| 生物识别 | 指纹（Class 3） | 面容 ID 或触控 ID，以本机支持的为准；文案随之显示“面容 ID 解锁”或“触控 ID 解锁” |
| 生物识别变化 | 新增或删除指纹、关闭锁屏后作废 | 新增或删除面容、指纹，或关闭锁屏密码后作废；之后的处理相同（改用 PIN，提示已关闭，可以在设置中重新开启） |
| 恢复码 PDF | 系统打印框架排版，“保存到”选择位置 | 系统网页引擎排成 A4，“存储到文件”选择位置；模板同为 `app/assets/recovery_sheet.html` |
| 敏感内容复制 | 标记为敏感，App 在 1 分钟后清空 | 由系统在 1 分钟后让剪贴板内容过期，并且不同步到其他 Apple 设备 |
| 扫码 | `mobile_scanner` | 相同；首次使用时系统询问相机权限，被拒绝时提示改为输入核对码，或到系统设置中允许 |
| 账号表单自动填充 | 需要替换 FlutterView 才能正常工作 | 系统自带，不需要额外处理 |
| 更新 | App 内下载并安装 APK | App 内下载并校验 IPA，交给签名工具安装，见 14.4 |

### 14.3 本机存储与密钥保护

格式见 [protocol.md](protocol.md) 2.5 的 iOS 部分。

- **PIN 槽**：`kek` 由 Secure Enclave 中不可导出的 P-256 私钥参与计算，每试一次 PIN 都要调用一次 Secure Enclave，PIN 无法拿到手机以外暴力破解。
- **面容 ID / 触控 ID 槽**：本机数据密钥保存为一条钥匙串条目，每次读取都由系统验证面容或指纹，不接受锁屏密码。
- **仅限本机**：钥匙串条目全部设为仅限本机，不进 iCloud 钥匙串，不会随备份或换机迁移到另一台手机；App 的数据目录标记为不备份。因此从备份恢复、换机迁移之后，App 都是一台新设备，需要重新登录并由管理设备批准或用恢复码恢复。
- **卸载重装**：iOS 的钥匙串在卸载后不会清除。App 启动时如果数据目录中没有安装标记，就先清除钥匙串中的残留（两个槽、Secure Enclave 密钥、输错记录），再写入标记。这样卸载重装同样视为新设备。
- **模拟器**：模拟器没有 Secure Enclave，仅在模拟器构建中改用保存在钥匙串里的普通 P-256 私钥，供布局检查使用；真机构建不包含这条路径。

### 14.4 分发与更新

- **发布物**：每个 Release 增加 `harmonia-<版本>.ipa`（未签名），由 CI 在 macOS 上构建。签名清单的 `assets` 增加 `ios` 一项（下载地址、SHA-256、大小），格式与 `android` 相同。构建号沿用 Android 的 `versionCode` 算法。
- **安装**：使用者用 AltStore、SideStore 或自己的开发者证书签名后安装。README 说明安装步骤，并提醒：
  - 用免费 Apple ID 签名的 App 7 天后过期，需要在过期前重新签名（上述工具会自动续签）；过期后 App 打不开，重新签名后数据仍在。
  - 换一个 Apple ID 或证书签名，相当于安装了另一个 App，原来的数据读不到，需要按新设备重新接入。
- **检查更新**：时机和渠道规则与 Android 相同（前台、24 小时内最多一次、正式版与测试版渠道），同样验证清单签名。发现新版本时显示版本号和更新说明，提供“下载并导入签名工具”和“打开下载页”。
- **下载并导入签名工具**（2026-10-12 增加）：App 下载新的 IPA，按清单核对大小和 SHA-256，然后弹出系统的分享面板，由用户选择安装 Harmonia 时使用的签名工具（轻松签、全能签、万能签等能接收 IPA 文件的工具都会出现在面板里）；之后的签名和安装在签名工具里完成，数据会保留。这样做不依赖各个工具自己的跳转接口（它们没有公开、稳定的“传入下载地址即导入”的接口），并且交出去的文件经过了校验。App 自己仍然不安装 IPA；下载的文件放在缓存目录，取消时立即删除，交出去的那一份在下次下载前清掉。
- **不做软件源**：AltStore / SideStore 的软件源没有签名校验，本次不提供。

## 15. Windows CLI（v0.3.0，M11）

Windows 上的 CLI 与 macOS、Linux 是同一份代码（`cli/`）：命令、配对、同步、权限、本地覆盖、更新渠道都相同。协议和服务端只增加一个设备字段（15.3 的系统变量开关），App 只增加对应的开关和 Windows 设备的图标。本节只列差异。

### 15.1 范围

**做：**

- 支持 Windows 10（1809 及以上）、Windows 11、Windows Server 2019 及以上，amd64 与 arm64。
- 把变量写入 Windows 的用户环境变量、登录后运行的后台服务、`exec`、自更新、卸载、PowerShell 安装脚本。
- 全程不需要管理员权限。

**不做：** PowerShell 配置文件注入与提示符刷新、cmd 的自动运行脚本、Git Bash / MSYS2 / Cygwin 的 shell 集成（WSL 里请安装 Linux 版）、开机未登录即运行的 Windows 服务、winget / Scoop / MSI 安装包、程序的代码签名、图形界面。

### 15.2 与 macOS、Linux 的差异

| 项 | macOS、Linux | Windows |
| --- | --- | --- |
| 协议中的 `platform` | `darwin`、`linux` | `windows` |
| 程序位置 | `~/.local/bin/harmonia` | `%LOCALAPPDATA%\Programs\Harmonia\harmonia.exe`，安装脚本把这个目录加入用户的 `Path` |
| 数据目录 | `~/.harmonia`，目录 0700、文件 0600 | `%USERPROFILE%\.harmonia`，访问控制列表只允许本人、系统和管理员访问，不继承上级目录的权限 |
| 变量怎么生效 | `env.sh` + rc 文件注入 + 提示符刷新（5.8） | 写入用户环境变量（15.3）；不生成 `env.sh` |
| `harmonia shell install｜uninstall` | 修改 rc 文件 | 开启、关闭“写入用户环境变量” |
| `harmonia shell system-vars on｜off` | 不需要：rc 注入对所有名字一视同仁 | 是否写入 `Path`、`TEMP` 这类系统变量（15.3） |
| 后台服务 | `systemd --user`、LaunchAgent | 当前用户的计划任务（15.4） |
| `harmonia exec` | 用要运行的命令替换自身 | 启动命令并等它结束，退出码与它相同；Ctrl+C 交给它处理。cmd 和 PowerShell 自带的命令要写成 `cmd /c …` 或 `powershell -Command …` |
| `harmonia import` | 列出当前终端里的变量，排除系统和 shell 自带的 | 相同，排除的是 Windows 自带的变量 |
| 默认设备名 | 主机名 | 计算机名 |
| 自更新 | 原子替换程序文件 | 运行中的程序不能被覆盖：先把当前程序改名为 `harmonia.exe.old`，再放入新程序 |
| 卸载 | 直接删除自身 | 运行中的程序不能删除自身：命令结束后几秒内由系统命令删除 |
| 安装脚本 | `install.sh` | `install.ps1`（15.5） |

### 15.3 写入用户环境变量

Windows 没有每个终端都会读取的 rc 文件；系统自己的办法是“用户环境变量”，新启动的程序都会带上。Harmonia 在 Windows 上用它代替 5.8 的 rc 注入。

- **位置**：注册表 `HKCU\Environment`，也就是“系统属性 → 环境变量”上半部分的“用户变量”，在那里可以直接看到 Harmonia 写入的内容。写入后通知系统“环境变量已变化”。
- **开关**：`harmonia shell install` 开启，`harmonia shell uninstall` 关闭并恢复原状。开启前先说明将要做什么，确认后才执行（默认 Y）；安装脚本同样会询问。没有开启时，Harmonia 不碰用户环境变量，变量只能通过 `harmonia exec`、`harmonia export` 使用。命令沿用 `shell` 这个名字，是为了三个平台的命令和文档一致；Windows 上的帮助、提示和 `harmonia status` 写的是“用户环境变量”。
- **写入时机**：与另外两个平台重写 `env.sh` 的时机相同：后台服务或 CLI 命令每次同步之后，以及激活、顺序、授权、本地覆盖变化之后。只写有变化的变量，没有变化时不通知系统。
- **生效边界**：
  - 新启动的程序读到新值：从开始菜单、任务栏、资源管理器启动的程序，Windows Terminal 新开的标签页。
  - 已经打开的终端和程序不会变，需要重开；从旧终端里启动的程序沿用旧终端的值；VS Code 之类自带终端的程序要重启程序本身。
  - 想在当前终端马上用到最新值，用 `harmonia exec`。
- **接管与恢复**：只处理 Harmonia 托管的变量。接管一个名字之前，先把它原来的状态（有没有、值、类型）记在数据目录的 `sysenv.json` 里；不再托管时恢复成原来的样子，原来没有就删除。不再托管的情况包括：变量被删除、环境被停用、授权到期或被撤销、退出登录、关闭开关、卸载。托管期间手动修改同名的用户变量，会在下一次同步时被覆盖；恢复时回到接管之前的值。
- **系统变量开关**（2026-10-12 用户确认）：
  - 系统自身使用的名字默认不写入，例如 `Path`、`PATHEXT`、`TEMP`、`TMP`、`USERPROFILE`、`APPDATA`、`SystemRoot`、`ComSpec`、`PSModulePath`，完整名单在代码里。写坏它们会让系统或其他程序无法工作。
  - 每台设备有一个“写入系统变量”开关，保存在服务端，默认关闭，做法与激活状态相同：在 App 的设备详情页（只对 Windows 设备显示）和这台电脑上的 `harmonia shell system-vars on|off` 都能修改，随同步生效（协议 3.2、3.4）。
  - 开启后，这些名字和其他变量一样写入，不再托管时一样恢复原值；关闭后，已经写入的系统变量在下一次同步时恢复原值。
  - 服务端版本较旧、没有这个开关时，按关闭处理；修改时提示先更新服务端。
- **不写入的变量**（`harmonia status` 会列出，`harmonia exec` 不受影响）：
  - 系统变量开关关闭时，上面那些系统自身使用的名字。
  - 空值：Windows 的用户环境变量不能为空。
  - 超过 32,767 个字符的值：超出 Windows 对单个环境变量的限制。
  - 只有大小写不同的名字：Windows 把它们当成同一个变量，只写入按名称排序的第一个。
- **值的保存方式**：保存为普通字符串，值里的 `%NAME%` 不会被展开，换行原样保留。
- **安全口径**（4.2 第 3 条的 Windows 部分）：
  - 值以明文保存在当前用户的注册表里（用户配置文件中的 `NTUSER.DAT`，只有本人、系统和管理员能读），保护程度与 `env.sh` 相同。
  - 与 rc 注入不同的是，本用户之后启动的**所有**程序都会带上这些变量，包括图形界面程序。
  - 使用漫游用户配置文件的域环境里，注册表会同步到域服务器，不建议开启。
  - “写入系统变量”开关没有加密，服务端可以改动它，但改不了变量的值：它只决定账号里已有的同名变量是否写入这台电脑。
  - 直接删除程序或数据目录不会清理已经写入的变量，要用 `harmonia shell uninstall` 或 `harmonia uninstall`。

### 15.4 后台服务

- **形式**：名为“Harmonia”的计划任务，触发条件是当前用户登录；以当前用户的普通权限运行。注册、启动、停止、删除都不需要管理员权限。和 macOS 一样，登录之后才运行；电脑开机但没有人登录时不运行。
- **不显示窗口**：后台服务在没有窗口的控制台里运行，登录时不会弹出或闪过终端窗口。
- **只运行一个**：同一个数据目录只允许一个后台服务，重复启动的会直接退出。
- **停止与重启**：由 CLI 通知后台服务自己退出，不强行结束进程；`harmonia service status` 据此判断是否在运行。
- **意外退出**：计划任务每 10 分钟检查一次，后台服务不在运行就重新启动。
- 职责与另外两个平台相同：维持推送连接、同步、写入用户环境变量（已开启时），每 24 小时检查一次更新。日志在数据目录的 `daemon.log`。

### 15.5 安装、更新与卸载

- **安装**：在 PowerShell 里运行一行命令。系统自带的 Windows PowerShell 5.1 和 PowerShell 7 都可以，不需要管理员权限，也不需要修改脚本执行策略：

  ```powershell
  irm https://github.com/harmonia-vault/harmonia/releases/download/update-feed/install.ps1 | iex
  ```

  脚本按更新渠道的清单下载当前处理器架构对应的 `harmonia.exe`，校验 SHA-256，放到安装目录并加入用户的 `Path`；然后依次询问是否开启“写入用户环境变量”、是否安装后台服务，直接回车即同意（默认 Y）。安装测试版时先运行 `$env:HARMONIA_CHANNEL = 'beta'`。
- **发布物**：每个 Release 增加 `harmonia-windows-amd64.exe` 和 `harmonia-windows-arm64.exe`，签名清单的 `assets` 增加 `cli-windows-amd64`、`cli-windows-arm64`；`install.ps1` 与 `install.sh` 一样放在 `update-feed` 中。
- **不做代码签名**：用安装脚本下载的程序不会被 SmartScreen 拦截；从浏览器手动下载再运行时系统会提示“Windows 已保护你的电脑”，README 说明这种情况以及怎样用清单里的 SHA-256 自行核对。
- **更新**：`harmonia update` 的步骤与 5.11 相同（下载 → 验证签名和哈希 → 自检 → 替换 → 重启后台服务），旧版本保留为 `harmonia.exe.old`。
- **卸载**：`harmonia uninstall` 依次退出账号、恢复用户环境变量、移除计划任务、删除数据目录、把安装目录从用户的 `Path` 中去掉、删除程序。
