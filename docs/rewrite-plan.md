# Harmonia 重写方案

> 状态：方案已定稿，**尚未开始实现**（等待用户明确说“开始”）。最后更新：2026-10-06。
> 依据：用户确认的项目定位（10 条 + 2 条边界）、现有五个仓库的代码与提交历史、2026-10-05 被删除的设计文档，以及之后几轮对齐的结论（第 12 节）。

---

## 1. 摘要

旧项目的问题是**方向失控**，不在于代码写得差：4 天写了 8 万行以上代码，大部分花在对抗“服务端完全恶意”的自研授权链和恢复连续链、多个协议版本并存，以及三平台系统级服务的边角问题上；而核心流程至今走不通。

重写原则：

1. **用户路径优先**：完成的标准是验收清单（第 8 节）中的流程能闭环，不以测试数量或“证据文件”为准。
2. **安全刚好够**：机密性靠端到端加密；授权与完整性由自己部署的服务端执行。设备端只防常见风险，密钥下发到设备后的风险由使用者承担。
3. **只用标准构件**：libsodium 原语 + HTTPS + minisign。不做 PAKE，不做 DAG，不允许多个协议版本并存。
4. **范围收窄**：Android、Cloudflare Workers 服务端、Linux 与 macOS CLI。
5. **单仓库，设计文档常驻**：`docs/` 是唯一事实来源，代码变更先改文档。

本次交付目标：**v0.1.0，一个可以闭环的完整产品，而不是 demo。**

## 2. 旧项目复盘

### 2.1 规模与现状

| 模块 | 代码量 | 测试 | 提交（10-03 ~ 10-06） | 现状 |
| --- | --- | --- | --- | --- |
| core-go | ~50,000 行 | ~30,800 行 | 75 | 恢复与 DAG 相关约 2.3 万行（含测试）；同一能力有多套并行实现 |
| mobile | ~17,900 行 Dart + ~9,200 行原生 | ~7,800 行 | 45 | 冷启动无法恢复会话；登录后必然停在走不通的“等待授权”页 |

### 2.2 与定位逐条对照

| # | 定位 | 旧实现 | 新方案 |
| --- | --- | --- | --- |
| 1 | 解决 AI Agent 环境的密钥配置 | 未提及 AI；明确“不做容器和 cron” | `exec` 与 rc 注入覆盖终端和常驻进程；提供 Agent 接入文档 |
| 2 | 个人多设备 | 多账号公开实例 + 邮件体系 | 单实例单账号，不发邮件 |
| 3 | 手机负责信任与管理 | 方向一致，但实现失控、流程断裂 | 扫码配对；手机是账号级管理设备 |
| 4 | 成熟组件，不追求复杂自研协议 | 自研 DAG、证书 v3/v4/v5、BoringSSL SPAKE2 | 只用 libsodium、minisign 和标准哈希 |
| 5 | 环境三档权限，降权立即生效 | 客户端验证授权历史 | 服务端每次请求执法 |
| 6 | 只能经 App/CLI 修改，导入只同步选中项 | 写入签名 + 续办状态机 | 在线写入 + 幂等键 |
| 7 | 显式本地例外 | 有 | 保留 |
| 8 | 后台服务，清理不破坏原环境 | 系统级服务、逐 key 记录原值 | 用户级服务；通过 rc 文件末尾 source 的方式自然回退原值 |
| 9 | 系统验证优先，PIN 兜底；恢复后先轮换 | 每次操作都做系统验证；PIN 原生工作流；恢复依赖连续链 | App 锁（系统验证 / PIN）只控制界面；恢复流程简化 |
| 10 | 开源自托管，控制复杂度 | 5 个仓库 + submodule，证据文化 | 单仓库 + 防失控规则 |

### 2.3 根因

1. 没有用户路径层面的定义，开发由安全门槛和证据驱动。
2. 威胁模型定得过高，衍生出授权链、过渡链、DAG 和多个证书版本。
3. 旧路径从不删除，并行实现层层叠加。
4. 核心闭环还没跑通，就先攻坚平台边角。
5. 设计文档被删除后，没有可以对照的依据。

### 2.4 保留的资产

- `design/icons`、`design/mascot`，以及 `design_system.dart`（按需取用）。
- Cloudflare 的 Fork 部署和 Actions 更新流程。
- shell 值转义规则、`__HARMONIA_` 保留前缀、旧更新设计中的经验（详见 5.10 和附录）。
- 不保留：旧代码、旧协议、旧测试向量、旧证据文件。旧仓库归档为只读。

## 3. 产品定义

### 3.1 使用者与场景

**一个人**，拥有 1～2 台 Android 手机，以及若干台 Mac、Linux 电脑或服务器（包括运行 AI Agent 的机器）。

| 场景 | 做法 |
| --- | --- |
| 在终端运行 Agent 或 CLI 工具 | 激活环境后，新开的终端里直接可用 |
| Linux 服务器上常驻的 Agent | 用户级服务开机后自动同步；进程用 `harmonia exec` 启动，或在服务配置中引用 `env.sh` |
| 不想把 Key 贴进 AI 对话 | Agent 从环境变量读取 Key |
| 更换或轮换某个 Key | 手机上改一次，所有获授权设备在 3 秒内同步（在线时） |
| 设备退役或丢失 | 手机上撤销该设备，服务端立即回收，设备联网后自动清除本地数据 |

### 3.2 本次范围（v0.1.0）

**做：**

- 服务端：Cloudflare Workers + Durable Object（SQLite），实时推送。
- Android App（Flutter）：首次设置、App 锁（系统验证 / PIN）、环境与变量管理、扫码批准设备、权限管理、撤销、多管理手机、恢复与轮换恢复码、修改密码、应用内更新。
- CLI（Go，macOS arm64/amd64、Linux amd64/arm64）：登录、配对、实时同步、多环境激活与优先级、rc 注入、`exec`、本地覆盖、选择性导入、写入、用户级后台服务、自更新、卸载。
- 发布：GitHub Releases（签名 APK、CLI 二进制、签名清单）、安装脚本、服务端发布仓库与一键部署。

**不做（已冻结）：** iOS、Windows、Docker 自托管、fish shell、macOS 图形界面 App 的环境注入、环境钥轮换、App 后台推送、实例重置功能（确有需要时删库重建）、团队与共享、Passkey、浏览器扩展。

> Docker 虽然不在本次范围内，但服务端核心逻辑要与存储接口分离，方便以后补一个 Node 适配层。

### 3.3 核心概念

| 概念 | 定义 |
| --- | --- |
| 实例 | 一个 Workers 部署，可以有多个相互隔离的账号 |
| 账号 | 邮箱 + 密码。密码**只用于登录**，不参与加密 |
| 管理设备 | Android 手机，持有全部环境的密钥，可以批准、调整权限、撤销设备，可以轮换恢复码。可以有多台 |
| 客户端设备 | CLI，按环境获得 RO / RW / Admin 权限。Admin = 读写 + 环境改名或删除；不能批准设备 |
| 环境 | 一组变量，拥有独立的 32 字节环境钥（保留 `keyVersion` 字段，本次不实现轮换） |
| 激活与优先级 | 每台 CLI 在本地决定启用哪些环境以及优先级，不上传 |
| 本地覆盖 | 对某个已存在变量设置仅本机生效的值，不上传；云端删除该变量或失去授权后，覆盖失效 |
| 恢复码 | 128 位随机数，离线保存；在失去全部管理设备时用于恢复 |

## 4. 安全口径

### 4.1 保证的

1. **服务器只保存密文。** 数据库泄露、云厂商、备份外流都拿不到变量值。
2. **即使服务器被完全控制，也拿不到明文**，前提是你没有批准一台假设备：
   - 配对时会核对公钥指纹，服务器无法偷换公钥。
   - 管理设备只给持有有效设备证书的设备封装环境钥，服务器无法往设备列表里塞假设备来骗取密钥。
   - 只拿到密码，只能发起配对请求，仍然需要你在手机上扫码核对。
3. **降权、撤销、删除立即生效**（在服务端诚实的前提下）：服务端同步删除对应的密文、封装、授权和会话，并断开该设备的实时连接。
4. **尽力回收**：设备联网后，一旦发现自己被撤销或失去授权，就主动清除本地密钥、缓存和 `env.sh` 中对应的变量。离线设备最晚在授权到期时停用。

### 4.2 明确不保证的

1. **密钥下发到设备后，风险由使用者承担。** 已复制或已泄露的值无法追回，也不另外设计机制去追。
2. **手机被他人拿到并解开锁屏不在防护范围内。** 这种情况下，用另一台手机或恢复码撤销它即可。
3. **在电脑上，同一用户的任何进程以及 root 都能读到变量**，包括 `env.sh` 文件和进程环境。Agent 运行 `env` 也可能把值带进日志或对话。
4. **服务器被攻破后，撤销可能被它假装执行。** 由于本次不实现环境钥轮换，这种情况不做补救。
5. **服务器可以回滚或隐藏数据**：它可以把变量换回旧密文，或不下发新变量。这不会泄露明文。
6. **元数据可见**：变量名、环境名、设备名、访问时间。
7. **恢复码等于整个账号**：恢复码泄露，对方就能登记管理设备；恢复码和所有手机都丢失，数据永远无法找回。
8. **不在范围内**：已 root 的手机、用户主动运行的恶意代码、依赖库的供应链风险（发布签名能缓解发布环节，但无法消除）。

### 4.3 设备端必须做到的底线

- Android：关闭系统备份（`allowBackup=false` 加数据提取规则）；密钥和缓存使用 Keystore 包装加密存储，不用明文 SharedPreferences。
- CLI：`~/.harmonia/` 目录权限 0700、文件 0600，写入采用原子替换。
- 两端：收到“设备已撤销”的响应后立即自我清除，然后回到未授权状态。

## 5. 技术方案

### 5.1 仓库结构

```
harmonia/                     # 唯一开发仓库
├── mise.toml                 # [tools] + [tasks]
├── docs/                     # design.md / protocol.md / threat-model.md / acceptance.md
├── vectors/                  # 三端共用测试向量
├── server/                   # TypeScript，完全自包含（发布时推送到 harmonia-worker 发布仓库）
│   ├── src/core/             # Hono 路由、权限、同步、推送；依赖 Storage 接口
│   └── src/workers/          # Durable Object 适配 + 入口
├── cli/                      # Go：cmd/harmonia + internal/{crypto,api,store,sync,merge,shell,service,update}
├── app/                      # Flutter：lib/core（纯 Dart，可无界面运行）+ lib/ui
├── e2e/                      # 端到端脚本
├── design/                   # 图标、吉祥物
└── 每个子目录有自己的 AGENTS.md
```

版本：全产品统一版本号。打 `vX.Y.Z` tag 时同时发布 CLI 和 APK；服务端随 main 分支推送到发布仓库。

### 5.2 密码学

| 用途 | 构件 | Go | Dart | TS |
| --- | --- | --- | --- | --- |
| 变量值加密 | XChaCha20-Poly1305；AAD 为 `["harmonia/value", envId, keyVersion, name]` | `x/crypto/chacha20poly1305` | `sodium` | — |
| 环境钥封装 | libsodium sealed box | `x/crypto/nacl/box` | `sodium` | — |
| 设备身份与证书 | Ed25519 | `crypto/ed25519` | `sodium` | WebCrypto 验签 |
| 密码 | 客户端 Argon2id（salt 由服务器下发）→ authKey → 服务端再做 PBKDF2-SHA256 存储 | `x/crypto/argon2` | `sodium` | WebCrypto |
| 恢复码 | 128 位随机数，Base32 分组显示；用 HKDF-SHA256 分用途派生 Ed25519 和 X25519 密钥 | 标准库 | `sodium` / `cryptography` | — |
| 更新清单 | minisign（Ed25519） | `aead.dev/minisign` | Dart 侧用 Ed25519 验证 minisign 格式 | — |

签名原文统一采用 JSON 字符串数组，首项为用途域。全项目只有三种签名：设备证书、登录挑战、恢复钥轮换记录。

### 5.3 密钥体系

```
密码 ──Argon2id──▶ authKey：只用于登录
恢复码 ──HKDF──▶ 恢复签名钥：签发恢复登记的设备证书和恢复钥轮换记录
      └─HKDF──▶ 恢复加密钥：服务端为每个环境保存一份封装给它的环境钥
每台设备：签名钥 + 加密钥（Android 存在 Keystore 包装的安全存储中；CLI 存为 0600 文件）
每个环境：环境钥，封装给全部管理设备、获授权的客户端设备和恢复钥
```

**设备证书**：由批准者（某台管理设备或恢复签名钥）签名，内容为 `[用途域, deviceId, kind, signPub, boxPub, issuerKeyId]`。管理设备在本地维护“受信签发者集合”，只为证书可以追溯到该集合的设备封装环境钥。不保存历史，不做 DAG。

### 5.4 认证与会话

| 会话 | 获取方式 | 权限 | 有效期 |
| --- | --- | --- | --- |
| 密码会话 | 密码登录 | 只能创建配对请求 | 15 分钟 |
| 设备会话 | 设备签名钥签名服务端下发的 nonce | 按该设备当前的授权 | 1 小时，自动续期 |
| 恢复会话 | 恢复签名钥签名 nonce（只需要恢复码，不需要密码） | 只能读取恢复封装、登记本机、轮换恢复码、设置新密码 | 15 分钟 |

登录、配对、恢复接口都按 IP 限流失败次数。

### 5.5 服务端

- **运行时**：Hono + 一个名为 `instance` 的 Durable Object（SQLite 存储），所有状态都在里面，天然串行、原子。
- **数据表**：`account`（单行）、`devices`、`pairings`、`environments`、`envelopes`、`grants`、`variables`、`sessions`、`idempotency`、`meta(head_seq)`。每次变更时 `head_seq + 1`，并写入受影响行的 `updated_seq`。
- **API**（`/api/v1`）：
  - 实例：`GET /instance`（产品标识、服务端版本、协议版本、是否已初始化）
  - 初始化：`POST /setup`
  - 认证：`GET /auth/prelogin`、`POST /auth/login`、`POST /auth/challenge`、`POST /auth/device-session`
  - 账号：`PUT /account/password`（管理设备）
  - 配对：`POST /pairings`、`GET /pairings/{id}`、`GET /pairings?status=pending`、`POST /pairings/{id}/approve`、`POST /pairings/{id}/reject`
  - 同步：`GET /sync?since=N`；推送：`GET /events`（WebSocket）
  - 环境：`POST|PATCH|DELETE /environments[/{id}]`
  - 变量：`PUT|DELETE /environments/{id}/variables/{name}`，需要带幂等键
  - 设备：`GET /devices`、`PUT /devices/{id}/grants`、`PATCH /devices/{id}`、`POST /devices/{id}/revoke`
  - 恢复：`POST /recovery/challenge`、`POST /recovery/session`、`GET /recovery/envelopes`、`POST /recovery/enroll`、`POST /recovery/rotate`、`GET /recovery/rotate/{key}`
- **执法规则**：每个请求都检查会话、设备状态、授权有效期和角色。`rotation_required` 为 true 的设备，除轮换恢复码外，其他管理操作一律拒绝。
- **同步**：返回 `updated_seq > since` 且该设备可见的环境、授权、自己的封装和变量（含墓碑），以及 `headSeq`。失去访问权的环境以“已移除”项下发。
- **冲突**：同一变量按服务端接受顺序后写覆盖先写；同一幂等键重放时返回原结果。
- **表结构迁移**：用 schema 版本号加顺序执行的迁移脚本，保证升级不丢数据。
- **删库重建**：不提供功能入口，文档说明在 Cloudflare 后台删除 Worker（连同 Durable Object 数据）后重新部署。具体步骤在实现时核实。

### 5.6 实时推送

- 客户端用设备会话建立 `GET /api/v1/events` WebSocket 连接，服务端使用 Durable Object 的 Hibernation API。
- 推送消息**只是提示**，不携带任何密钥或变量值：
  - `{"type":"changed","headSeq":N}`
  - `{"type":"pairing"}`（只推给管理设备）
  - `{"type":"revoked"}`（推送后关闭连接）
- 客户端收到 `changed` 后调用 `/sync` 拉取。拉取是唯一的数据来源。重连后立即同步一次。
- CLI 后台服务：长连接 + 心跳，断线后指数退避重连，另外每 5 分钟兜底同步一次。
- App：只在前台时连接，不做后台推送。
- 目标：在线设备 3 秒内收到变化。

### 5.7 CLI

```
harmonia login <url>
harmonia pair [--name 名称]
harmonia status
harmonia sync
harmonia env list | activate <env> [--priority N] | deactivate <env>
harmonia var list [--env] | set <env> <KEY> | rm <env> <KEY>
harmonia import --env <env>
harmonia override set|rm|list
harmonia exec [--env a,b] -- <cmd...>
harmonia export [--format sh|dotenv|json]
harmonia shell install|uninstall
harmonia service install|uninstall|status
harmonia update [--check]
harmonia logout
harmonia uninstall
```

- 本地状态放在 `~/.harmonia/`。CLI 和后台服务通过文件锁协调，不做本地 IPC。
- 合并规则：激活的环境按优先级叠加，同名变量高优先级覆盖；本地覆盖先替换所在环境中的值，再参与合并；授权已过期的环境在本地停用。
- 后台服务：
  - Linux 使用 `systemd --user` + `loginctl enable-linger`，开机后无需登录即运行。
  - macOS 使用 LaunchAgent，登录后运行。
  - 后台服务负责维持推送连接、同步、重写 `env.sh`，并每 24 小时检查一次更新。

### 5.8 rc 文件注入（与普通用户的使用习惯一致）

- 后台服务把合并结果原子写入 `~/.harmonia/env.sh`（0600），内容是普通的 `export KEY='value'`，值一律使用单引号字面量安全转义。
- `harmonia shell install` 先告诉用户要在哪个文件末尾加哪一行，确认后才写入：
  - zsh 写入 `~/.zshenv`，这样非交互的 zsh 也能读到。
  - bash 写入 `~/.bashrc`，并确保 `~/.bash_profile` 或 `~/.profile` 会加载它。
  - 写入的内容是带标记注释的一行 `source ~/.harmonia/env.sh`。
  - 如果 rc 文件是符号链接，不自动修改，只提示用户自己添加。
- **原值回退是自然发生的**：source 行在 rc 文件末尾，所以 Harmonia 的值会覆盖用户自己定义的同名变量；变量不再托管后，新开的 shell 就会用回用户原来的定义。
- 手动修改 `env.sh` 会在下一次同步时被覆盖。在某个 shell 里手动 export 的值只影响那个 shell。已经打开的 shell 需要重开或手动 source 才会看到变化。
- systemd、launchd、cron 不读 rc 文件，需要用 `harmonia exec` 启动，或在配置里引用 `env.sh`。文档会给出示例。

### 5.9 Android App

- **技术选型**：Flutter，`lib/core` 是纯 Dart，加密使用 `sodium_libs`；存储使用 `flutter_secure_storage`（Keystore 包装）；App 锁使用 `local_auth`；扫码使用 `mobile_scanner`；路由使用 `go_router`。**不写原生桥代码**。
- **单一状态机驱动路由**：

```
启动 → 有已保存的服务器？ ─否→ [连接服务器]
        └是→ 本机是已授权设备？ ─是→ [App 锁] → 需要轮换恢复码？ ─是→ [强制轮换]
               │                                             └否→ [主页]
               └否→ 服务器已初始化？ ─否→ [首次设置] → [恢复码确认] → [主页]
                      └是→ [登录] → [本机未授权]
                                     ├ 让另一台手机批准（显示二维码和核对码）
                                     └ 用恢复码恢复 → [强制轮换] → [主页]
```

  `go_router` 的 redirect 只读取这个状态机，页面自己不决定跳转。跨阶段的跳转一律是替换，不入栈。

- **App 锁**：
  - 打开 App，或从后台返回超过 5 分钟时，需要验证一次。
  - 批准设备、修改权限、撤销设备、查看或轮换恢复码、修改密码时，再验证一次。
  - 优先使用系统验证；设备没有设置锁屏时，使用 App PIN（至少 6 位，加盐哈希存储，失败次数限流）。
  - App 锁**只控制界面能否进入，不和密钥绑定**。
- **页面**：连接服务器、首次设置、恢复码展示与重输、登录、本机未授权、等待批准、恢复码输入、App 锁、环境列表、环境详情、变量编辑、设备列表（含待批准请求）、添加设备（扫码 → 核对 → 选择权限 → 验证 → 批准）、设备详情、设置（服务器、App 锁、修改密码、轮换恢复码、检查更新、退出）。
- **文案**：不出现任何内部术语；每条错误都给出下一步该做什么。

### 5.10 配对

1. 新设备在本地生成密钥，调用 `POST /pairings`，得到 `pairingId` 和 `secret`。
2. 计算指纹 = `SHA-256(["harmonia/pairing", pairingId, signPub, boxPub])`。二维码包含 `pairingId` 和完整指纹；人工核对码是指纹的前 80 位，显示为 16 个 Base32 字符（4 组，每组 4 个）。
3. 手机扫码或手输核对码，拉取该配对请求并重新计算指纹比对。比对一致后，显示设备名和平台，让用户选择环境、角色和有效期，或者选择“作为管理设备”。
4. 手机签发设备证书、封装环境钥，调用 `approve`；新设备通过推送或轮询得知已批准，换取设备会话后完成同步。

### 5.11 更新机制

- **发布源**：主仓库的 GitHub Releases。每个 Release 附带 `manifest.json`，内容包括版本号、各平台包的下载地址、SHA-256、大小，以及支持的协议版本，并附带 minisign 签名。公钥内置在客户端中。先只做 stable 渠道。
- **CLI**：
  - 后台服务每 24 小时（带随机抖动）检查一次，有更新时在 `status` 中和 stderr 上提示。
  - `harmonia update` 的步骤：下载 → 验证签名和哈希 → 运行新二进制的 `version` 自检 → 原子替换 `~/.local/bin/harmonia` → 重启用户级服务。旧版本保留为 `.old` 以便手动回退，全程不需要 sudo。
- **Android**：
  - App 在前台时检查，24 小时内最多检查一次。有更新时显示更新说明，用户确认后在 App 内下载 APK，验证哈希，然后交给系统安装器（需要 `REQUEST_INSTALL_PACKAGES` 权限）。
  - 系统会校验 APK 签名必须与已安装版本一致。
  - `versionCode` 由版本号计算（例如 `0.3.2` → 302），不使用 CI 的 run_number。
- **服务端**：`/instance` 返回服务端版本和协议版本。客户端发现协议不兼容时，提示用户更新服务端（Sync fork 或 Actions 更新），或者更新客户端。
- **发布签名私钥**：只存放在 GitHub Actions secrets 中，测试使用临时生成的密钥。

## 6. 关键流程

- **首次设置**：手机生成设备密钥、恢复码（用户完整重输确认）、恢复公钥、authKey，然后调用 `POST /setup` 原子完成。之后引导用户创建第一个环境。
- **写入变量**：本地加密，`PUT` 时带幂等键；服务端接受后推送 `changed`；包括写入方在内的所有设备都通过 `/sync` 更新本地，不做乐观更新。写入必须在线。
- **批准设备**：见 5.10。授权行和封装在同一个事务中写入。
- **降权或升权**：只修改授权行。**新增环境授权**：管理设备验证目标设备的证书后，为它封装环境钥。
- **撤销**：服务端删除该设备的授权、封装和会话，推送 `revoked` 并断开连接；设备联网后自我清除。
- **删除环境或变量**：服务端删除密文并留下墓碑；所有设备同步后从缓存和 `env.sh` 中移除。
- **恢复**：获得恢复会话 → 解开全部环境钥 → 生成本机密钥，用恢复签名钥签发证书，然后 `enroll`（此时 `rotation_required = true`）→ 强制轮换：生成新恢复码，用户完整重输，重新封装全部环境钥，旧恢复钥签名轮换记录，`rotate`（带幂等键，结果不明时可以查询）。提交成功后，旧恢复码才失效。
- **主动轮换恢复码**：流程与上面相同，轮换记录由管理设备签名。
- **修改密码**：已授权的管理设备通过系统验证后，调用 `PUT /account/password`。
- **退出（logout）**：先通知服务端撤销本机（离线时先清本地，联网后补发），然后删除本地密钥和缓存，并清空 `env.sh`。
- **卸载 CLI**：logout + 卸载服务 + 移除 rc 行 + 删除 `~/.harmonia` 和二进制文件。

## 13. 实现中的设计调整（2026-10-07）

以下调整在实现时做出，已同步到 [protocol.md](protocol.md)，待用户确认：

| 项 | 方案原文 | 实际实现 | 原因 |
| --- | --- | --- | --- |
| 信任锚 | 管理设备维护“受信签发者集合”，证书逐级追溯 | 一把**账号根签名钥**：生成于首次初始化，封装给每台管理手机和恢复码；设备证书与每个环境钥封装都由它签名。设备首次接触账号时钉住 `rootPub`，配对指纹包含 `rootPub` | 更简单，没有证书链；还堵住了“服务器偷换封装”的漏洞（匿名 sealed box 本身不认证发送方） |
| 服务端密码存储 | 客户端 Argon2id 后，服务端再做 PBKDF2 | 服务端存 `SHA-256(随机盐 ‖ authKey)` | authKey 已经过 Argon2id，暴力破解成本在客户端；避免 Workers 免费套餐 10ms CPU 限制 |
| CLI 配对命令 | `login` 与 `pair` 两步 | `harmonia login` 一步完成登录和配对 | 密码会话只有 15 分钟，拆成两步容易过期 |
| 封装构件 | sealed box | libsodium `crypto_box_seal`；加密密钥对按 `crypto_box_seed_keypair` 由 32 字节种子派生 | 三端一致（Go 与 Dart 已用测试向量验证） |
| App 原生代码 | 不写原生代码 | `MainActivity` 中约 40 行 Kotlin：设备名、安装更新 APK | `local_auth` 要求 `FlutterFragmentActivity`；现成的安装插件会申请媒体读取权限，不适合存放密钥的 App |
| 服务端发布仓库 | Release 时由 CI 推送 | 本地运行 `mise run publish-server` | 组织禁用了部署密钥，CI 无法写入另一个仓库 |
| 本地开发 | — | 服务端对 `localhost`、`127.0.0.1`、`10.0.2.2`（Android 模拟器）放行 HTTP | 便于本地与模拟器调试；线上只走 HTTPS |
