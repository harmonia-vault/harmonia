## 1. 摘要

旧项目的问题是**方向失控**，不在于代码写得差：4 天写了 8 万行以上代码，大部分花在对抗“服务端完全恶意”的自研授权链和恢复连续链、多个协议版本并存，以及三平台系统级服务的边角问题上；而核心流程至今走不通。

重写原则：

1. **用户路径优先**：完成的标准是验收清单（第 8 节）中的流程能闭环，不以测试数量或“证据文件”为准。
2. **安全刚好够**：机密性靠端到端加密；授权与完整性由自己部署的服务端执行。设备端只防常见风险，密钥下发到设备后的风险由使用者承担。
3. **只用标准构件**：libsodium 原语 + HTTPS + minisign。不做 PAKE，不做 DAG，不允许多个协议版本并存。
4. **范围收窄**：Android、Cloudflare Workers 服务端、Linux 与 macOS CLI。
5. **单仓库，设计文档常驻**：`docs/` 是唯一事实来源，代码变更先改文档。

本次交付目标：**v0.1.0，一个可以闭环的完整产品，而不是 demo。**

### 2.3 根因

1. 没有用户路径层面的定义，开发由安全门槛和证据驱动。
2. 威胁模型定得过高，衍生出授权链、过渡链、DAG 和多个证书版本。
3. 旧路径从不删除，并行实现层层叠加。
4. 核心闭环还没跑通，就先攻坚平台边角。
5. 设计文档被删除后，没有可以对照的依据。

### 2.4 保留的资产

- `design/icons`、`design/mascot`，以及 `design_system.dart`（按需取用）。
- Cloudflare 的 Fork 部署和 Actions 更新流程。
- shell 值转义规则、`__HARMONIA_` 保留前缀、旧更新设计中的经验（详见 5.10 和附录）。
- 不保留：旧代码、旧协议、旧测试向量、旧证据文件。旧仓库归档为只读。

## 3. 产品定义

### 3.1 使用者与场景

**一个人**，拥有 1～2 台 Android 手机，以及若干台 Mac、Linux 电脑或服务器（包括运行 AI Agent 的机器）。

| 场景 | 做法 |
| --- | --- |
| 在终端运行 Agent 或 CLI 工具 | 激活环境后，新开的终端里直接可用 |
| Linux 服务器上常驻的 Agent | 用户级服务开机后自动同步；进程用 `harmonia exec` 启动 |
| 不想把 Key 贴进 AI 对话 | Agent 从环境变量读取 Key |
| 更换或轮换某个 Key | 手机上改一次，所有获授权设备在 3 秒内同步（在线时） |
| 设备退役或丢失 | 手机上撤销该设备，服务端立即回收，设备联网后自动清除本地数据 |

### 3.2 本次范围（v0.1.0）

**做：**

- 服务端：Cloudflare Workers + Durable Object（SQLite），实时推送。
- Android App（Flutter）：首次设置、App 锁（系统验证 / PIN）、环境与变量管理、扫码批准设备、权限管理、撤销、多管理设备、恢复与轮换恢复码、生成配对码、应用内更新。
- CLI（Go，macOS arm64/amd64、Linux amd64/arm64）：登录、配对、实时同步、多环境激活与优先级、rc 注入、`exec`、本地覆盖、选择性导入、写入、用户级后台服务、自更新、卸载。
- 发布：GitHub Releases（签名 APK、CLI 二进制、签名清单）、安装脚本、服务端发布仓库（用户 Fork 后在 Cloudflare 导入部署）。

**不做（已冻结）：** Windows、Docker 自托管、fish shell、macOS 图形界面 App 的环境注入、环境钥轮换、App 后台推送（2026-11-09 解除冻结，见第 18 节）、实例重置功能（确有需要时删库重建）、团队与共享、Passkey、浏览器扩展。

> iOS App 不在 v0.1.0 范围内，放在 v0.2.0，见第 14 节。
>
> Windows 在 v0.1.0 中冻结不做，v0.3.0 增加 Windows 上的 CLI，见第 15 节。
>
> Docker 虽然不在本次范围内，但服务端核心逻辑要与存储接口分离，方便以后补一个 Node 适配层。

### 3.3 核心概念

| 概念 | 定义 |
| --- | --- |
| 实例 | 一个 Workers 部署，可以有多个相互隔离的账号 |
| 账号 | 只有邮箱，没有密码（2026-10-13 调整）。知道邮箱只能查到账号是否存在、账号公钥，以及发起一个管理设备看不到的匿名配对请求；能不能接入始终由管理设备核对后批准 |
| 配对码 | 管理设备临时生成的 8 位一次性码，有效期由用户选择（5 到 60 分钟，默认 10 分钟），用一次即作废。它只代替原来的密码，证明“发起配对的人拿到过管理设备”，让请求出现在管理设备上；不代替指纹核对 |
| 管理设备 | 具备管理功能的客户端（App；电脑另外接入管理身份后也是，见第 16 节），持有全部环境的密钥，可以批准、调整权限、撤销设备，可以轮换恢复码。可以有多台。发起配对时客户端声明是否具备管理功能，只有具备的才能被批准为管理设备 |
| 客户端设备 | CLI，按环境获得只读（RO）或读写（RW）权限；不能新建、改名、删除环境，不能批准设备。2026-10-14 去掉 Admin 一档：它只多出改名、删除环境，而 CLI 没有这两项命令；删除整个环境留在管理设备上做 |
| 变量库 | 变量真正存放的地方，拥有独立的 32 字节库钥（保留 `keyVersion` 字段，本次不实现轮换）。只在管理设备上管理，电脑上只能看到名字和被引用的变量。2026-11-09 由原来的“环境”改名而来，见第 17 节 |
| 环境 | 由若干条对变量库的引用组成，不能自己新增变量；每条引用可以选范围、改名。设备只能被授权环境。2026-11-09 起是新的一层，见第 17 节；2026-11-10 去掉引用上的“可以修改”，见第 19 节 |
| 手机批准解密 | 默认情况下电脑上不保存能解开变量的钥匙，每次要用变量时向管理设备发请求，在手机上批准并选择有效时长；可以为某台设备的某个环境开启“允许本机解密”，恢复原来的做法。见第 17 节 |
| 激活与顺序 | 每条授权带“是否激活”和顺序，存在服务端，可以在管理设备上（拖动排序、开关）或设备本身（CLI 命令）修改；新授权默认激活并排在最后。激活只是使用上的便利，不是安全边界：设备能读取什么只由授权决定 |
| 本地覆盖 | 对某个已存在变量设置仅本机生效的值，不上传；云端删除该变量或失去授权后，覆盖失效 |
| 恢复码 | 128 位随机数，离线保存；在失去全部管理设备时用于恢复 |

## 4. 安全口径

### 4.1 保证的

1. **服务器只保存密文。** 数据库泄露、云厂商、备份外流都拿不到变量值。
2. **即使服务器被完全控制，也拿不到明文**，前提是你没有批准一台假设备：
   - 配对时会核对公钥指纹，服务器无法偷换公钥。
   - 管理设备只给持有有效设备证书的设备封装环境钥，服务器无法往设备列表里塞假设备来骗取密钥。
   - 知道邮箱的人只能创建匿名配对请求：管理设备不扫码、不输核对码就看不到它，更不会自动弹出。用配对码发起的请求才会出现在管理设备上，批准前仍然要核对核对码或扫码。
3. **降权、撤销、删除立即生效**（在服务端诚实的前提下）：服务端同步删除对应的密文、封装、授权和会话，并断开该设备的实时连接。
4. **尽力回收**：设备联网后，一旦发现自己被撤销或失去授权，就主动清除本地密钥、缓存和 `env.sh` 中对应的变量。离线设备最晚在授权到期时停用。
5. **陌生人挡不住你接入**：知道邮箱的人可以把账号的匿名请求额度占满，但用配对码发起的请求不占这份额度，仍然可以接入（5.12）。

### 4.2 明确不保证的

1. **密钥下发到设备后，风险由使用者承担。** 已复制或已泄露的值无法追回，也不另外设计机制去追。
2. **手机被他人拿到，且对方知道 App PIN 或能通过指纹验证，不在防护范围内。** 这种情况下，用另一台管理设备或恢复码撤销它即可。
3. **在电脑上，同一用户的任何进程以及 root 都能读到变量**，包括 `env.sh` 文件（开启 Shell 集成时）、本机密钥文件和进程环境。Agent 运行 `env` 也可能把值带进日志或对话。Windows 上开启“写入用户环境变量”后，值保存在当前用户的注册表中，本用户之后启动的所有程序（不只是终端里的）都会带上这些变量，见 15.3。2026-11-09 起默认改为手机批准解密（第 17 节）：电脑上不再保存能解开变量的钥匙，明文只在批准的有效时长内出现在保管进程和运行的程序里；为某个环境开启“允许本机解密”后，这一条照旧适用于那个环境。
4. **服务器被攻破后，撤销可能被它假装执行。** 由于本次不实现环境钥轮换，这种情况不做补救。
5. **服务器可以回滚或隐藏数据**：它可以把变量换回旧密文，或不下发新变量。这不会泄露明文。
6. **元数据可见**：变量名、环境名、设备名、访问时间。
7. **恢复码等于整个账号**：恢复码泄露，对方就能登记管理设备；恢复码和所有手机都丢失，数据永远无法找回。
8. **诱导批准**：有人可能把他自己设备的二维码或核对码发给你，诱导你扫码批准。防护靠批准页显示的设备名、平台和来源 IP，以及你只在自己发起接入时才批准；服务器无法替他做到这一步，因为二维码和核对码里的指纹包含账号公钥 `rootPub`，服务器谎报也会在批准前被比对出来。
9. **不在范围内**：已 root 的手机在 App 解锁期间（内存中的密钥可以被读取）、用户主动运行的恶意代码、依赖库的供应链风险（发布签名能缓解发布环节，但无法消除）。App 锁定时，root 也只能在这台手机上逐个尝试 PIN（见 4.3）；6 位数字 PIN 的强度有限，按手机算力估计，最快一两天可以试完，更长的 PIN 相应更难。

### 4.3 设备端必须做到的底线

- Android：关闭系统备份（`allowBackup=false` 加数据提取规则）；设备密钥用本机数据密钥加密，只有输入 App PIN 或通过指纹验证才能解开，Keystore 参与每一次 PIN 尝试，PIN 无法拿到手机以外暴力破解（[protocol.md](protocol.md) 2.5）；App 锁定时清除内存中的密钥；不用明文 SharedPreferences。
- iOS（v0.2.0）：与 Android 同样的底线，实现方式见 14.3：钥匙串条目全部仅限本机，App 数据不进备份；设备密钥只有 App PIN 或面容 ID / 触控 ID 能解开，Secure Enclave 参与每一次 PIN 尝试。
- CLI：`~/.harmonia/` 目录权限 0700、文件 0600（Windows 上是只允许本人、系统和管理员访问的访问控制列表，不继承上级目录的权限），写入采用原子替换。日常身份的密钥就是这样保存的，不具备管理功能；电脑要作为管理设备时另外接入一个管理身份，它的密钥用管理口令加密保存，只在执行管理操作时解开，见第 16 节。
- 两端：收到“设备已撤销”的响应后立即自我清除，然后回到未授权状态。

## 5. 技术方案

### 5.1 仓库结构

```
harmonia/                     # 唯一开发仓库
├── mise.toml                 # [tools] + [tasks]
├── docs/                     # design.md / protocol.md / threat-model.md / acceptance.md
├── vectors/                  # 三端共用测试向量
├── server/                   # TypeScript，完全自包含（发布时推送到 harmonia-worker 发布仓库）
│   ├── src/core/             # Hono 路由、权限、同步、推送；依赖 Storage 接口
│   └── src/workers/          # Durable Object 适配 + 入口
├── cli/                      # Go：cmd/harmonia + internal/{crypto,api,store,sync,merge,shell,service,update}
├── app/                      # Flutter：lib/core（纯 Dart，可无界面运行）+ lib/ui
├── relay/                    # 推送中继（2026-11-09，第 18 节）：只由发布者部署，不进 harmonia-worker
├── e2e/                      # 端到端脚本
├── design/                   # 图标、吉祥物
└── 每个子目录有自己的 AGENTS.md
```

版本：全产品统一版本号。打 `vX.Y.Z` tag 时同时发布 CLI 和 APK；服务端随 main 分支推送到发布仓库。CLI 和 App 的版本号在构建时取自标签；服务端的版本号写在 `server/package.json`（`/instance` 返回的就是它），打标签前要改成将要发布的版本号（预发布标签对应去掉后缀的版本号），发布流水线会核对，不一致时不发布。

### 5.2 密码学

| 用途 | 构件 | Go | Dart | TS |
| --- | --- | --- | --- | --- |
| 变量加密 | XChaCha20-Poly1305，值和备注一起加密（2026-10-14 加入备注）；AAD 为 `["harmonia.var", envId, keyVersion, name]` | `x/crypto/chacha20poly1305` | `sodium` | — |
| 环境钥封装 | libsodium sealed box | `x/crypto/nacl/box` | `sodium` | — |
| 设备身份与证书 | Ed25519 | `crypto/ed25519` | `sodium` | WebCrypto 验签 |
| 恢复码 | 128 位随机数，Crockford Base32 分组显示（不含易混淆的 I、L、O、U）；用 HKDF-SHA256 分用途派生 Ed25519 和 X25519 密钥 | 标准库 | `sodium` / `cryptography` | — |
| 更新清单 | minisign（Ed25519） | `aead.dev/minisign` | Dart 侧用 Ed25519 验证 minisign 格式 | — |
| App 本机密钥保护 | Argon2id(PIN) → Keystore HMAC-SHA256 → XChaCha20-Poly1305 封装本机数据密钥；可选 Keystore AES-256-GCM（指纹）。见 protocol 2.5 | — | `sodium` + Keystore（Kotlin） | — |

签名原文统一采用 JSON 字符串数组，首项为用途域。全项目只有三种签名：设备证书、登录挑战、恢复钥轮换记录。2026-11-09 为手机批准解密增加批准请求（设备签名）和批准结果（root 签名）两种，另有一种加密给管理设备的写入内容，见 17.4 和协议 3.9。

账号没有密码（2026-10-13），Argon2id 只用于 App PIN（上表最后一行）；配对码是服务端随机生成的一次性码，服务端只存它的 SHA-256，不涉及新的签名或加密格式。

### 5.3 密钥体系

```
恢复码 ──HKDF──▶ 恢复签名钥：签发恢复登记的设备证书和恢复钥轮换记录
      └─HKDF──▶ 恢复加密钥：服务端为每个环境保存一份封装给它的环境钥
每台设备：签名钥 + 加密钥（Android 用本机数据密钥加密，数据密钥由 App PIN 或指纹解开；CLI 存为 0600 文件）
每个环境：环境钥，封装给全部管理设备、获授权的客户端设备和恢复钥
```

**设备证书**：由批准者（某台管理设备或恢复签名钥）签名，内容为 `[用途域, deviceId, kind, signPub, boxPub, issuerKeyId]`。管理设备在本地维护“受信签发者集合”，只为证书可以追溯到该集合的设备封装环境钥。不保存历史，不做 DAG。

### 5.4 认证与会话

| 会话 | 获取方式 | 权限 | 有效期 |
| --- | --- | --- | --- |
| 注册会话 | 注册（需要验证邮箱时，验证通过后） | 只能查看账号信息和首次初始化 | 15 分钟 |
| 设备会话 | 设备签名钥签名服务端下发的 nonce | 按该设备当前的授权 | 1 小时，自动续期 |
| 恢复会话 | 恢复签名钥签名 nonce（只需要恢复码） | 只能读取恢复封装、登记本机 | 15 分钟 |

发起配对不需要会话：请求头给出账号 ID，任何人都能创建匿名请求，带上有效配对码的请求才会出现在管理设备上（5.10）。限流与风控见 5.12。

### 5.5 服务端

- **运行时**：Hono + 一个名为 `instance` 的 Durable Object（SQLite 存储），所有状态都在里面，天然串行、原子。
- **数据表**：`account`（单行）、`devices`、`pairings`、`pairing_codes`、`pairing_blocks`、`environments`、`envelopes`、`grants`、`variables`、`sessions`、`idempotency`、`meta(head_seq)`。每次变更时 `head_seq + 1`，并写入受影响行的 `updated_seq`。
- **API**（`/api/v1`）：
  - 实例：`GET /instance`（产品标识、服务端版本、协议版本、是否已初始化）
  - 账号：`POST /register`、`POST /register/verify`、`GET /accounts/lookup`（匿名，以邮箱查询）、`GET /account`、`POST /account/setup`、`POST /account-reset/*`
  - 认证：`POST /auth/challenge`、`POST /auth/device-session`
  - 配对：`POST /pairing-codes`（管理设备生成配对码）、`POST /pairings`（匿名）、`GET /pairings/{id}/events`（发起方等待连接）、`GET /pairings/{id}/status`、`GET /pairings`、`GET /pairings/{id}`、`POST /pairings/{id}/approve`、`POST /pairings/{id}/reject`
  - 同步：`GET /sync?since=N`；推送：`GET /events`（WebSocket）
  - 环境：`POST|PATCH|DELETE /environments[/{id}]`
  - 变量：`PUT|DELETE /environments/{id}/variables/{name}`，需要带幂等键
  - 设备：`GET /devices`、`PUT /devices/{id}/grants`、`PATCH /devices/{id}`、`POST /devices/{id}/revoke`、`PUT|DELETE /devices/self/push`（后台通知的句柄，第 18 节）
  - 恢复：`POST /recovery/challenge`、`POST /recovery/session`、`GET /recovery/envelopes`、`POST /recovery/enroll`、`POST /recovery/rotate`、`GET /recovery/rotate/{key}`
- **实例首页**（`GET /`）：在浏览器里直接打开服务器地址时显示的一张静态页面，让部署的人确认服务器已经跑起来，也让拿到地址的人知道接下来怎么做。
  - 内容：Harmonia 图标与一句话介绍、“运行中”和服务端版本号（2026-10-14 增加）、这台服务器的地址（取自访问时用的地址，供填进 App 和命令行）和地址的二维码（内容就是地址本身，由服务端生成后内嵌在页面里，供 App 的“连接服务器”页扫码填写；用手机相机直接扫则打开这张首页）、三步开始使用（下载 App、用邮箱注册或接入、在电脑上安装命令行并 `harmonia login`；这一步在安装命令之前先给出“让 AI 助手安装”，卡片里只有提示词，不加其他说明，见 5.13）、三句话说明工作方式（手机负责授权、服务器只存密文、电脑自动同步）、项目主页和服务端仓库的链接。
  - 服务器地址、AI 助手提示词和每条命令旁边都有“复制”按钮（2026-10-13 用户要求），点后显示“已复制”；HTTPS 下用剪贴板接口，其他情况选中文字后复制，复制不了时提示手动复制。没有脚本时仍可点一下整段选中。
  - 口径：只带复制按钮这一段内嵌脚本，内容安全策略按它的 SHA-256 放行（`script-src 'sha256-…'`），不允许其他脚本；不加载任何外部资源，链接只指向 GitHub 上的项目仓库；不显示这台服务器的配置和状态（是否开放注册、有没有账号、版本）；注明服务器由部署者自行运营、与项目方无关；要求搜索引擎不收录。
  - 配色与图标沿用 App，跟随系统的深浅色。
- **执法规则**：每个请求都检查会话、设备状态、授权有效期和角色。`rotation_required` 为 true 的设备，除轮换恢复码外，其他管理操作一律拒绝。
- **同步**：返回 `updated_seq > since` 且该设备可见的环境、授权、自己的封装和变量（含墓碑），以及 `headSeq`。失去访问权的环境以“已移除”项下发。
- **冲突**：同一变量按服务端接受顺序后写覆盖先写；同一幂等键重放时返回原结果。
- **表结构迁移**：用 schema 版本号加顺序执行的迁移脚本，保证升级不丢数据。
- **删库重建**：不提供功能入口，文档说明在 Cloudflare 后台删除 Worker（连同 Durable Object 数据）后重新部署。具体步骤在实现时核实。

### 5.6 实时推送

- 客户端用设备会话建立 `GET /api/v1/events` WebSocket 连接，服务端使用 Durable Object 的 Hibernation API。
- 推送消息**只是提示**，不携带任何密钥或变量值：
  - `{"type":"changed","headSeq":N}`
  - `{"type":"pairing"}`（只推给管理设备）
  - `{"type":"revoked"}`（推送后关闭连接）
- 配对发起方另有一条等待连接 `GET /api/v1/pairings/{id}/events`，用来接收批准结果，同时让服务端知道它还在等待（协议 3.5.1）。
- 客户端收到 `changed` 后调用 `/sync` 拉取。拉取是唯一的数据来源。重连后立即同步一次。
- CLI 后台服务：长连接 + 心跳，断线后指数退避重连，另外每 5 分钟兜底同步一次。
- App：只在前台时连接 WebSocket。App 不在前台时，新的批准请求和配对请求经推送中继发系统通知（2026-11-09，第 18 节）。
- 目标：在线设备 3 秒内收到变化。


- 帮助与选项（2026-10-14 补充）：`harmonia help <命令>` 或在命令后加 `-h`/`--help`（`--` 之前）只输出这条命令的用法，不执行命令，例如 `update --help` 不会开始升级。每条命令只接受自己的选项，不认识的选项、该带值没带值都报错并提示查看 `--help`，不再悄悄忽略；`exec` 要传给命令的选项写在 `--` 之后。
- `exec --env`、`export --env` 只用指定的环境（2026-10-13 补充）：可以用逗号分隔，也可以重复给出，按列出的顺序合并，靠前的优先；已停用的环境也能指定；指定的环境授权已到期或密钥解不开时报错，不运行命令（2026-10-15 调整，原来是跳过并提示）。`exec --env` 时，终端里由其他环境写入的变量（开启了 Shell 集成，或 Windows 上写入了用户环境变量）不传给命令：值与这台设备某个环境（或本机覆盖）给的值相同的变量会去掉，用户自己设的不同值和系统必需的变量（`PATH`、`HOME` 等）保留。不论是否指定 `--env`，与要注入的变量同名的已有条目都先去掉，子进程只收到一份最新值（同名出现两次时，多数程序读到的是第一个，也就是终端里的旧值）。
- `--env` 指定单个变量（2026-10-14 增加）：每一项可以是整个环境，也可以写成 `环境:变量名`，只取这个环境里的这一个变量；同一环境要多个变量时写多项，例如 `--env a,b,c:API_KEY,c:DB_URL`。各项仍按列出的顺序合并，同名变量由靠前的一项提供。指定的变量在那个环境里不存在时报错，不运行命令，并提示用 `var list --env` 查看；环境授权已到期、这个变量解不开时同样报错。整串正好是某个环境的名称或 ID 时当作整个环境，否则按最后一个 `:` 拆开。
- 环境可以用完整 ID 或名称指定（见第 19 节）：先精确匹配 ID，再按名称匹配，名称不区分大小写且不能重复。`env list` 和 App 环境详情显示环境 ID；环境改名不影响按 ID 指定的脚本。变量库仍可以用名称或 ID 指定，变量库页显示变量库 ID。
- 变量备注（2026-10-14 增加）：`var list` 在值后面显示备注的第一行；`var set <环境> <变量名> [值] [--note 备注]` 写入备注，只给 `--note` 不给值时保留原值只改备注，`--note ""` 清除备注。导入（终端里的变量、管理页面的 `.env`）不带备注，已有变量的备注保留；在管理页面复制到其他环境时备注一起复制。
- 读取前先同步（2026-10-14 补充）：`status`、`env list`、`var list` 和 `exec`、`export` 一样，先同步一次（最多等 3 秒），连不上服务器时使用本机缓存并在 stderr 提示。没有安装后台服务时，授权的变化（例如被撤销）也能在这些命令里马上看到，`env.sh` 或用户环境变量随之更新。
- 没有任何环境的访问权限时（还没有授权，或授权全部被撤销）：`exec`（不带 `--env`）、`export --all` 照常运行，只在 stderr 说明没有可以提供的变量；`status`、`env list`、`var list` 和 `login` 的结果提示去管理设备上授权。
- `export` 必须指明范围（2026-10-15）：不带 `--all` 或 `--env` 时不输出任何变量，报错并提示两种写法。`--all` 输出全部启用环境合并后的变量，`--env` 的写法同 `exec`。
- 批量导入（2026-10-15；2026-11-09 起目标改为变量库，见 17.2）：`import --vault <变量库> --file <文件>`（`-` 表示标准输入）读取 `.env`（写法同 16.5）或 JSON（对象，名称 → 字符串值，与 `export --format json` 的输出相同）；不给 `--format` 时按内容判断，以 `{` 开头的是 JSON。有解析不了的行时列出行号，整份都不写入。写入前先同步，和环境里现有的值比较，值相同的跳过，已有变量的备注保留；其余按每批最多 100 项调用批量写入接口（协议 `PATCH /environments/{id}/variables`），一批整体成功或整体失败。逐条输出结果：已写入、未变化、失败及原因，有失败时退出码为 1；`--json` 以 JSON 输出逐条结果，给脚本和 AI 助手读。中断或部分失败后原样再运行一次即可：已写入的显示未变化，相当于从断点继续。不给 `--file` 时保持原来的交互勾选（从当前终端的环境变量中选），同样走批量写入。
- `var set` 回读校验（2026-10-15）：写入后同步一次，从本机缓存解密这个变量，比较值和备注的 SHA-256，一致才输出“已写入并校验”；哈希只在内存里比较，不输出（短的值配上哈希前缀可以被离线猜出）。写入成功但同步失败时说明“已写入云端，回读校验没有完成”和原因，不报写入失败。再按当前的启用状态、顺序和本机覆盖检查 `exec`（不带 `--env`）实际会拿到的值：环境没有启用、被排在前面的环境的同名变量遮住、被本机覆盖值盖住时，各提示一句怎么处理。
- 拿不到变量时说清原因（2026-10-15）：`exec`、`export` 发现问题时，每个问题一行“原因 + 怎么修”：
  - 变量不存在：说明在哪个环境里没找到；这台设备能访问的其他环境里有同名变量时一并指出。
  - 环境找不到：列出这台设备能访问的环境，并说明名字没写错的话需要在管理设备上为这台设备授权。授权已到期：提示在管理设备上重新授权。
  - 连不上服务器：说明具体原因（无法解析地址、连接超时、证书不对、服务器返回的状态码）和上次同步是多久前，然后继续使用本机缓存。
  - 解密失败：只影响解不开的那个变量，环境里其他变量照常使用；点名这个变量，提示用 `var rm` 删除或在管理设备上重新写入。环境密钥解不开时提示在管理设备上重新授权这台设备。
  - 不带 `--env` 时，跳过的环境和变量逐条提示后继续；带 `--env` 时指定的环境或变量拿不到就报错，不运行命令。`exec` 自身出错时退出码为 125，和要运行的命令自己的退出码区分开。
- `status` 显示变量级健康度（2026-10-15）：环境表的“变量”列显示变量数，另加“健康”列：正常、授权已到期、密钥解不开、N 个变量解不开。表后的“需要处理”逐条列出问题和修复命令：解不开的变量、本机覆盖值所在的环境已无法访问或变量已删除、被前面的环境遮住的同名变量（沿用原来的“同名变量”）、超过 24 小时没有同步。全部用本机缓存计算，不增加请求。
- 写入的短时重试（2026-10-15）：写入变量、删除变量、批量写入和提交激活状态遇到网络错误、5xx 或限流时，在约 10 秒内退避重试，重试时用同一个幂等键（协议第 3 节）；仍然失败就报错，不在本机排队稍后重放。
- 授权被撤销或环境被删除后，同步时自动删除它留下的本机覆盖（2026-11-10 调整，原来要用环境 ID 手动移除）。
- `skill` 输出给 AI 助手的使用说明，`skill install` 把它保存成技能文件，见 5.13。
- `login` 依次询问服务器、邮箱和配对码（2026-10-13）：不询问密码；配对码留空即扫码方式，之后显示二维码和核对码，等待管理设备批准（5.10）。
- 本地状态放在 `~/.harmonia/`。CLI 和后台服务通过文件锁协调，不做本地 IPC；唯一的例外是保管手机批准结果的保管进程（17.5）。
- 合并规则：激活的环境按顺序叠加，同名变量由排在前面的环境提供；本地覆盖先替换所在环境中的值，再参与合并；授权已过期的环境在本地停用。
- 激活与顺序存在服务端（随授权同步），`activate`、`deactivate`、`order` 直接提交，需要联网；`order` 把列出的环境按给定顺序移到最前面，其余环境保持原有顺序。`harmonia env list` 显示顺序、是否激活，以及同名变量由哪个环境提供。
- 后台服务：
  - Linux 使用 `systemd --user` + `loginctl enable-linger`，开机后无需登录即运行。普通用户（例如通过 SSH 登录）通常没有权限自己开启 linger：开启失败时，在终端里询问是否用 sudo 开启（默认 Y），不同意或没有终端时给出要执行的命令。
  - macOS 使用 LaunchAgent，登录后运行。
  - Windows（v0.3.0）使用当前用户的计划任务，登录后运行，见 15.4。
  - 后台服务负责维持推送连接、同步、重写 `env.sh`（开启 Shell 集成时），每 24 小时检查一次更新；开启自动更新后发现新版本直接升级，手机上点“更新”时也由它执行（5.11）。

### 5.8 rc 文件注入与提示符刷新

- **命令路径**：macOS、Linux 的安装脚本自动把安装目录加入 PATH，独立于可选的变量加载和后台服务，`HARMONIA_YES=0` 也会配置。Zsh 写入 `${ZDOTDIR:-$HOME}/.zshrc`；Bash 写入 `~/.bashrc` 和按 `.bash_profile`、`.bash_login`、`.profile` 顺序实际生效的登录配置，无现有文件时创建 `.profile`；POSIX sh 写入 `.profile`。保留原文件内容，重复安装不重复追加，加载配置不重复添加 PATH 条目。安装结束时明确提示当前终端需执行的 PATH 命令，之后再提示登录；新终端自动生效。
- 开启 Shell 集成后，后台服务和 CLI 把合并结果原子写入 `~/.harmonia/env.sh`（0600），内容是普通的 `export KEY='value'`，值一律使用单引号字面量安全转义。
- **没有开启时不生成 `env.sh`**（2026-10-15）：以 `~/.harmonia/shell.sh` 是否存在作为是否开启的标记（`shell install` 写入，`shell uninstall` 删除）；不检查 rc 文件，因为 rc 可能是手动添加的符号链接，后台服务看到的 `ZDOTDIR` 也可能和终端里不同。没有开启时，同步不写 `env.sh`，已有的在下一次同步时删除，只用 `harmonia exec` 的机器上不留变量的明文副本。本机缓存 `cache.json` 里是服务端下发的密文。
- **默认不开启，也不推荐**（2026-11-09 用户调整）：多数场景用 `harmonia exec` 就够了；Shell 集成让变量出现在每个终端的环境里，同一用户的任何程序都能读到，还要在磁盘上留一份明文 `env.sh`。所以：
  - 安装脚本不再询问、也不安装 Shell 集成，`HARMONIA_YES=1` 只安装后台服务；安装结束的提示介绍 `harmonia exec`。
  - `harmonia login` 完成后的“接下来”推荐 `harmonia exec -- <命令>`，不再提 Shell 集成；`harmonia env activate` 也不再提示开启。
  - `harmonia status` 里 Shell 集成未开启时只写“未开启”，不附开启命令；已开启时附一句说明：变量对这个用户的所有程序可见，本机留有明文变量文件，可以用 `harmonia shell uninstall` 关闭。
  - 已经开启的电脑升级后保持原样，不自动关闭。
- **安装时询问**：安装脚本装好 `harmonia` 后，如果有终端可以交互，询问是否安装后台服务，直接回车即安装（默认 Y）；没有终端（例如在脚本或 CI 中运行）时跳过询问，只提示对应命令。设置 `HARMONIA_YES=1` 时不询问，直接安装后台服务（2026-10-13）。设置 `HARMONIA_YES=0` 时不询问，不装后台服务，只提示对应命令（2026-10-13，供 AI 助手使用，见 5.13）。后台服务在接入账号之前安装也没问题，它在接入前等待（2026-10-07 用户确认）。
- `harmonia login` 完成后，只提示还没有安装的后台服务。
- `harmonia shell install` 先说明代价（变量对这个用户的所有程序可见、本机留有明文变量文件，多数场景用 `harmonia exec` 即可），再列出要修改的文件和内容，确认后才写入（默认 N，2026-11-09）；`--yes` 跳过确认。已存在的 Harmonia 标记块直接更新，不重复添加：
  - zsh 写入 `~/.zshenv`，这样非交互的 zsh 也能读到。
  - bash 写入 `~/.bashrc`，并确保 `~/.bash_profile` 或 `~/.profile` 会加载它。
  - 写入带标记的加载代码，交互式 Shell 同时注册提示符刷新函数；首次安装后，已有终端需按安装提示手动加载一次，或新开终端。
  - 如果 rc 文件是符号链接，不自动修改，只提示用户自己添加。
- `harmonia shell uninstall` 移除加载设置；zsh 和 bash 的加载设置都已移除时，删除 `shell.sh` 和 `env.sh`（2026-10-15）。已开启集成的终端在下一次提示符出现时发现文件不存在，把托管的变量恢复原状。
- **提示符刷新**：支持 Bash 5.1 及以上、Zsh 5.0 及以上的交互式 Shell。Bash 使用 `PROMPT_COMMAND`，Zsh 使用 `precmd` 钩子；每次主提示符显示前检查本地变量，有变化才应用，不联网、不启动 Harmonia CLI。保留已有提示符功能和命令退出状态，重复加载不重复注册。
- **变量清理**：仅处理 Harmonia 托管的变量；新增和修改使用最新合并值，不再托管时恢复本终端接管前的状态，原来不存在则移除。
- **生效边界**：停留在提示符时收到更新，按一次空回车即可刷新；直接执行的第一条命令可能使用旧值。正在运行的程序不受影响。
- 手动修改 `env.sh` 会在下一次同步时被覆盖。在某个 shell 里手动 export 的值只影响那个 shell，本地变量文件下次变化时重新应用 Harmonia 的值。
- systemd、launchd、cron 不读 rc 文件，需要用 `harmonia exec` 启动。不再支持在服务配置里引用 `env.sh`（2026-10-15）：没有开启 Shell 集成时它不存在。

### 5.9 Android App

- **技术选型**：Flutter，`lib/core` 是纯 Dart，加密使用 `sodium_libs`；存储使用 `flutter_secure_storage`（Keystore 包装）；App 锁使用 App PIN 和系统指纹（`androidx.biometric`，原生实现）；扫码使用 `mobile_scanner`；路由使用 `go_router`。**不写原生桥代码**。
- **单一状态机驱动路由**：

```
启动 → 有已保存的服务器？ ─否→ [连接服务器]
        └是→ 本机是已授权设备？ ─是→ [App 锁] → 需要轮换恢复码？ ─是→ [强制轮换]
               │                                             └否→ [主页]
               └否→ [输入邮箱] → 查询账号 ─未注册或未初始化→ [注册 / 验证邮箱] → [设置 App PIN] → [首次设置] → [恢复码确认] → [主页]
                                       └已初始化→ [设置 App PIN] → [本机未授权]
                                                                   ├ 接入这台手机（显示二维码和核对码，可选输入配对码）
                                                                   └ 用恢复码恢复 → [强制轮换] → [检查其他设备] → [主页]
```

  `go_router` 的 redirect 只读取这个状态机，页面自己不决定跳转。跨阶段的跳转一律是替换，不入栈。

  “连接服务器”页的地址输入框默认填入 `https://harmonia.zzz.sd`，用户可直接点击“连接”，也可手动修改地址或扫码填写。连接成功后保存用户选择的地址，后续启动沿用该地址。

  “输入邮箱”页只有一个邮箱输入框（2026-10-13）：服务器上还没有这个邮箱时，确认后按新账号注册（服务器没有开放注册时提示）；已注册但还没完成初始化的账号没有任何数据，确认后重新注册并初始化；已初始化的账号进入“本机未授权”。页面底部保留“用恢复码恢复”和“重置账号”。

- **App 锁**（格式见 [protocol.md](protocol.md) 2.5）：
  - **设置 App PIN**：确定账号后，在保存任何设备密钥之前，必须先设置 App PIN（从输入邮箱页直接用恢复码恢复时，在恢复之后、保存之前设置）（6–16 位数字，输入两次）。这样设备密钥从第一次写入就受保护，中途退出也不会留下没有保护的密钥。App 锁不能关闭。
  - **开启指纹**：设置完 PIN 后，如果手机支持强生物识别（Class 3，例如指纹；多数手机的普通人脸解锁达不到这个等级，不提供），不再询问，直接弹出系统验证来开启指纹解锁（2026-10-12 调整，Android 与 iOS 相同）：验证通过即开启并继续；用户取消或验证失败时留在这一页，可以重试，也可以点“跳过”。以后可以在设置中开关。不提供“锁屏密码”解锁：它和 App PIN 作用重复，而且知道锁屏密码的人就能打开 App。
  - **解锁时机**：打开 App，或在后台满 5 分钟后回到前台。手机锁屏不再单独触发立即锁定，按同一后台时长规则处理。开启了指纹时先弹指纹，取消或失败可以改输 PIN；没开启时输入 PIN。
  - **再次验证**：批准设备、修改权限、撤销设备、更换恢复码、退出登录、修改 PIN、开关指纹时，再验证一次（指纹或 PIN 均可）。
  - **解锁就是解开密钥**：验证通过指的是用指纹或 PIN 解开本机数据密钥，不是界面上的判断。锁定时（后台满 5 分钟，或进程结束）清除内存中的全部密钥，解锁后再解开。切后台不添加遮罩或清空页面，回到前台沿用正常页面；已经锁定的会话仍须验证后进入。
  - **输错限制**：PIN 连续输错 5 次后等待 30 秒，此后每错一次等待时间翻倍，最长约 30 分钟。错误次数保存在本机，重启 App 不清零。不会因为输错而自动清除数据。
  - **指纹失效**：用户新增或删除指纹、关闭锁屏后，系统会作废指纹密钥。App 发现后改用 PIN 解锁，解锁后提示“手机指纹有变化，指纹解锁已关闭”，用户可以在设置中重新开启。数据不受影响。
  - **忘记 PIN**：开启了指纹时，用指纹解锁后在设置中修改 PIN。没开启指纹时，在锁屏页选择“忘记 PIN”，清除本机数据后重新接入，再让另一台管理设备批准或用恢复码恢复。这台手机此时已经无法通知服务端，它的旧设备记录需要在其他设备上移除，界面要说明这一点。
- **页面**：连接服务器（填写地址，或扫描服务器首页上的二维码；扫到后直接连接，2026-10-12 增加）、首次设置、恢复码展示与重输、更换恢复码说明、输入邮箱、本机未授权（含输入配对码）、等待批准、恢复码输入、恢复后检查其他设备、设置 App PIN（含开启指纹）、App 锁、变量库列表、环境列表（与变量库列表分属底栏两个标签，2026-11-09 调整）、环境详情（变量下方显示备注；点一个变量从底部弹出变量面板，可以改名、从环境中移除、进入编辑值和备注，见第 19 节；底部显示可复制的环境 ID）、变量编辑（含可选的多行备注，2026-10-14 增加）、设备列表（分“管理设备”“CLI”两组，含待批准请求；2026-10-14 调整）、添加设备（点“添加设备”从按钮展开浮动菜单，两项：“生成配对码”直接显示配对码；“扫码确认”进入扫码页 → 核对 → 选择权限 → 验证 → 批准，扫码页里可以改为手输核对码。从标题栏的加号展开）、设备详情（2026-11-09 调整：只列已授权给这台电脑的环境，一行一个，行上显示权限、是否无人值守使用（开启时带期限和醒目标记），带激活开关和拖动手柄，卡片下方显示同名变量由哪个环境提供；点一行从底部弹出这个环境的授权面板，上方改权限（只读、读写），底部可展开的“高级”里是“无人值守使用（本机解密）”和它的期限（2026-11-10 调整，见第 19 节），改完点“保存”，面板底部可以取消对这个环境的授权；卡片末尾“添加环境”只列还没授权的环境，选中后打开同一个面板，默认只读、不开启无人值守使用。扫码批准设备时的“允许访问的环境”用同样的“添加环境 + 面板”；电脑上的 CLI 另有“版本与更新”：当前版本、可更新到的版本、“更新”按钮和“自动更新”开关，2026-10-14 增加，见 5.11）、设置（服务器、修改 App PIN、指纹解锁、轮换恢复码、检查更新、关于、退出）。“关于”页显示版本，以及 App 里用到的全部开源项目的版权说明和许可证全文（2026-10-12 增加）：Dart 包、Flutter 引擎和 libsodium 的部分由 Flutter 构建时自动收集，BudouX 模型和 Android 原生依赖（AndroidX、Kotlin）在 `app/lib/app/licenses.dart` 中补登记。
- **文案**：不出现任何内部术语；每条错误都给出下一步该做什么。成段的文字只在句子之间分行，段与段之间不留额外间距；句子内部按词折行，不把一个词拆到两行——词的边界由 Google BudouX 的简体中文模型判断（`app/assets/budoux/zh-hans.json`，Apache-2.0，实现见 `app/lib/core/phrases.dart`），Android 与 iOS 相同（2026-10-12 增加）。

#### 液态玻璃外观（Android 与 iOS）

- Android 与 iOS 仅保留液态玻璃界面。设置的“外观”分组提供“颜色模式”（亮色、暗色、跟随系统，默认跟随系统）和透明度，不再提供材质开关；导航、按钮、菜单与弹层共用同一套组件，变量正文与输入保持可读底色。选择立即生效并保存在本机，退出账号后保留，不随账号同步。系统高对比度只调整同一套组件的材质，减少动态效果只调整动效，不切换到另一套布局。
- 外观分组显示无级透明度滑条，左侧最通透，右侧遮盖最强，默认中点直接复用组件库 `LiquidGlassSettings.ios27Light / ios27Dark` 预设。在 0%、25%、50%、75%、100% 五个位置设置吸附区，其余位置连续调节，松手后保存到本机；失败恢复上次选择并提示重试。复用 `liquid_glass_easy 5.0.0` 的 LiquidGlassSlider 及默认白色滑块、接触阴影、尺寸与动效，深浅色均保持白色滑块；仅滑块使用液态玻璃交互，滑轨保留普通细线，不包裹玻璃外框或背景。2026-10-13 试过换成 `liquid_glass_widgets` 的 GlassSlider 以便只留一个玻璃库，但它的进度与滑块中心不重合、滑块按住时偏向一侧，效果不如前者，因此滑条仍保留 `liquid_glass_easy`，其余玻璃表面全部来自 `liquid_glass_widgets`。高对比度或减少动态效果时使用 Flutter 标准滑条。刻度与说明共用滑块中心的行程，左侧“最通透”、中间“默认”、右侧“遮盖最强”，实时显示遮盖百分比，方向与填充进度一致。调试会话独立保存选择。弹窗、底部弹层和通知使用单独的面板材质（见下），滑条在其可读范围内调节；输入内容、验证码和 PIN 落在半透明雾面上，计数、说明与错误提示使用正文对比度，不因高透明度而失去可读性。

### 5.10 配对

配对有两种发起方式，之后的核对、选择权限、再次验证、批准、等待连接完全相同（2026-10-13 调整，此前要先用密码登录）：

| 方式 | 发起方需要 | 管理设备怎样拿到请求 |
| --- | --- | --- |
| 扫码（匿名请求） | 服务器地址和邮箱 | 只能扫发起方的二维码，或手输 16 位核对码；不推送、不自动弹出、不出现在待批准列表中 |
| 配对码 | 服务器地址、邮箱和管理设备上生成的配对码 | 推送给管理设备，前台时自动弹出批准页，出现在待批准列表中；批准前仍然要核对核对码或扫码 |

1. 新设备在本地生成密钥，查询账号（`GET /accounts/lookup`，得到账号 ID 和 `rootPub`，首次接触时钉住），调用 `POST /pairings`（请求头给出账号 ID，可选带配对码），得到 `pairingId` 和 `secret`。请求 5 分钟内有效。
2. 计算指纹 = `SHA-256(["harmonia/pairing", pairingId, signPub, boxPub])`。二维码包含 `pairingId` 和完整指纹；人工核对码是指纹的前 80 位，显示为 16 个 Crockford Base32 字符（4 组，每组 4 个）。
3. 手机扫码或手输核对码（手输时在全部等待中的请求里匹配，包括匿名请求），拉取该配对请求并重新计算指纹比对。比对一致后，显示设备名和平台，让用户选择环境、角色和有效期，或者选择“作为管理设备”。
   - 用配对码发起的请求：管理设备在前台且已解锁时，收到推送或同步时发现就直接打开批准页，电脑和手机发起的都一样。App 在后台时发系统通知（2026-11-09，第 18 节）；回到前台或解锁后先同步，发起方仍在等待的请求随即弹出。每个请求只弹出一次，已经有弹出的批准页时不再叠加，其余请求留在设备页的待批准列表中。匿名请求不做这些。
   - 弹出的批准页和列表中打开的一样，没有经过扫码：用户必须勾选“核对码一致”才能批准，页面同时提示“只批准你自己刚刚发起的请求；此刻没有在其他设备上发起接入时请拒绝，并勾选阻止这个网络”。
4. 手机签发设备证书、封装环境钥，调用 `approve`；新设备通过等待连接得知已批准，换取设备会话后完成同步。
5. **发起方离开**：新设备在等待期间一直保持等待连接（协议 3.5.1）。CLI 按 Ctrl+C 或进程退出、新手机离开等待页或 App 被关闭，连接断开（或 25 秒没有心跳）后请求立即作废：管理设备不再弹出，已经打开的批准页改为显示“这次请求已失效”，只留“关闭”。等待连接因网络中断断开时同样作废，新设备提示重新发起。
6. **拒绝并阻止**：批准页显示请求来自的 IP。拒绝时可以勾选“30 分钟内阻止这个网络再次发起请求”；被阻止的一方看到“这个网络暂时不能发起配对，请稍后再试”。
7. **配对码**：管理设备点“添加设备”，在展开的浮动菜单中选择“生成配对码”（与“扫码确认”并列，不在扫码页里：配对码要在对方发起之前生成，扫码则在对方发起之后；菜单第三项是“复制 AI 安装提示词”，见 5.13），弹窗先选有效期（5、10、15、30、60 分钟，默认 10 分钟）再点“生成”，然后显示 8 位码（Crockford Base32，与邮件验证码相同，按 4 位一组显示）和剩余时间；过期后回到选择有效期，按钮为“重新生成”。
   - 在过期前、或成功创建一个配对请求之前一直有效（2026-10-14 调整，此前 5 分钟有效、每个账号同时只有一个）。生成新的不影响已有的，每个账号同时最多 10 个，超出时作废最早生成的那个。服务端只存哈希。
   - CLI（`harmonia login` 依次询问服务器、邮箱、配对码，或用 `--code` 给出）和新手机（“接入这台手机”时可选输入）走同一条路径。配对码留空就是扫码方式。
   - **配对码只代替原来的密码，不代替指纹核对**：它只决定请求能不能出现在管理设备上，用配对码发起后，管理设备仍然必须比对核对码或扫码，再选权限、验证、批准。
   - 输错的处理见 5.12：按“账号 + 网络”递增等待，不因输错作废配对码，也不锁定账号。

### 5.11 更新机制

- **发布源**：主仓库的 GitHub Releases。每个 Release 附带 `manifest.json`，内容包括版本号、各平台包的下载地址、SHA-256、大小，以及支持的协议版本，并附带 minisign 签名。公钥内置在客户端中。
- **更新渠道**（2026-10-07 增加）：
  - 正式版：只接收不带后缀的版本；测试版：接收全部版本中最新的一个。标签带 `-rc.x`、`-beta.x` 等后缀的发布为预发布，只进入测试版渠道。
  - 版本顺序：同一基础版本内，正式版 > rc > beta > alpha，同类后缀按数字比较。例如 `0.1.2 > 0.1.2-rc.2 > 0.1.2-rc.1 > 0.1.2-beta.3 > 0.1.1`。
  - 渠道清单放在固定的预发布 `update-feed` 中：`stable.json`、`beta.json` 及其签名。发版时由 `releasetool feed` 判断，只有版本更新时才覆盖，补丁旧版本不会让渠道回退。正式版渠道收到带后缀的版本会拒绝。
  - 渠道在 App“设置 → 更新渠道”和 `harmonia update channel stable|beta` 中切换，默认正式版；测试版程序默认测试版渠道。安装脚本用 `HARMONIA_CHANNEL=beta` 安装测试版。
- **CLI**：
  - 后台服务每 24 小时（带随机抖动）检查一次，结果写入本机缓存。
  - `harmonia update` 的步骤：下载 → 验证签名和哈希 → 运行新二进制的 `version` 自检 → 原子替换 `~/.local/bin/harmonia` → 重启用户级服务 → 用新程序的 `harmonia skill` 输出覆盖已保存的技能文件（5.13）。旧版本保留为 `.old` 以便手动回退，全程不需要 sudo。
  - **自动更新**（2026-10-14 增加）：每台电脑一个开关，默认关闭，存在服务端的设备记录上（协议 `PATCH /devices/{id}` 的 `autoUpdate`），手机和电脑改的是同一个值。电脑上用 `harmonia update auto on|off` 切换（需要联网），不带参数时显示当前状态；手机在设备详情的“版本与更新”里切换。开启后，后台服务每天检查时发现新版本就直接升级；从关闭切到开启时立即检查一次。自动更新由后台服务执行：没有安装后台服务时 `update auto on` 照常保存，同时提示运行 `harmonia service install`，否则不会生效。
  - **在手机上让电脑更新**（2026-10-14 增加）：设备详情的“版本与更新”显示 CLI 当前版本（同步时上报的 `version`），以及更新渠道里的最新版本。App 按 CLI 的版本推断它的渠道：版本带后缀用测试版渠道，否则用正式版渠道，读取方式和签名验证与 App 自己检查更新相同；CLI 用 `update channel` 改过渠道时可能推断不准，只影响显示，实际升级以 CLI 自己的渠道为准。点“更新”后，服务器向这台电脑的后台服务推送一条更新请求（协议 `POST /devices/{id}/update`），电脑上不弹确认，后台服务按自己的渠道检查并升级，不论自动更新是否开启。后台服务没有连上服务器（没有安装、电脑关机或断网）时，App 提示“这台电脑的后台服务现在没有连上服务器，请确认电脑开机并联网，或在电脑上运行 harmonia update”。升级完成后电脑下次同步上报新版本，服务端发现版本变化会通知管理设备，几秒内设备详情显示新版本。
  - 安全口径：更新请求不带签名、也不带版本号，只是让电脑“现在检查一次”。电脑只安装发布签名验证通过、并且比当前版本新的安装包，所以即使服务器被攻破、伪造更新请求，最多只能让电脑升级到一个真实的官方新版本，不能安装其他程序，也不能降级。后台服务 1 分钟内只处理一次更新请求。
  - **后台服务自己升级**：下载、验证、自检、替换、覆盖技能文件与 `harmonia update` 相同，不同的是最后不调用“重启服务”（那会先把自己停掉），而是退出，由系统按服务配置立即用新程序重新启动（Linux `Restart=always`、macOS `KeepAlive`；Windows 计划任务需要另外保证退出后马上重新启动，不能只等 10 分钟一次的检查，实现时在虚拟机里验证）。升级失败时记录到日志和本机缓存，不重试，第二天检查时再试；`harmonia status` 显示上次失败的原因和下一步怎么做。
  - **更新提示**（2026-10-14 补充）：`harmonia status` 每次都显示“有新版本 X 可用”以及自动更新是否开启。其他命令在 stderr 是终端时，每天最多提示一次“有新版本 X 可用，运行 harmonia update 升级（或 harmonia update auto on 开启自动更新）”，写在命令输出之后（`exec` 运行的命令接管了进程，提示写在运行命令之前），提示时间记在本机缓存里；stderr 不是终端（脚本、AI 助手、管道）时不提示，避免混进输出。自动更新已开启且后台服务已安装时不提示，交给后台服务处理。`update`、`version`、`help`、`skill` 和后台服务本身不提示。`status`、`env list`、`var list`、`exec`、`export` 发现本机的检查结果超过 24 小时（通常是没有安装后台服务）时，和读取前的同步并行检查一次更新（同样最多等 3 秒，失败不提示），所以不装后台服务也能收到提示。
- **Android**：
  - App 在前台时检查，24 小时内最多检查一次。有更新时显示更新说明，提供“下载并安装”和“打开下载页”（2026-10-13 增加）。前者在 App 内下载 APK，验证哈希，然后交给系统安装器（需要 `REQUEST_INSTALL_PACKAGES` 权限）；后者通过系统浏览器打开该版本的 GitHub Release 页面，不检查或申请安装权限，也不触发 App 内下载。无法打开时提示安装或启用浏览器后重试。
  - Android 与 iOS 共用下载进度界面：连接时显示等待状态，接收数据时按实际字节数与已签名清单中的总大小显示进度条、百分比和已下载大小；收完后显示校验状态。校验与缓存写入完成后才进入原有安装或分享步骤，下载失败仍留在 App 内提示重试。
  - Android 按现有支持架构分包：`harmonia-<版本>-android-arm64.apk`（ARM64）与 `harmonia-<版本>-android-arm.apk`（ARM32）；使用 Flutter `--split-per-abi --target-platform android-arm,android-arm64`，每个 APK 只包含对应架构的原生库，不发布通用包或 x86_64 包。
  - 签名清单的 Android 资源键改为 `android-arm64`、`android-arm`，每项独立记录 URL、SHA-256 与大小；App 使用 Dart 标准 `Abi.current()` 选择当前运行架构，不以设备型号猜测，不新增原生桥。缺少匹配资源时明确提示去发布页选择，不误报已是最新版本。iOS 和 CLI 的资源键不变。
  - 分包保持统一版本号、原有签名密钥和构建号算法；设置 Flutter 官方 `force-version-code-ignoring-abi=true`，禁止为架构额外抬高 versionCode，避免后续版本被系统判成降级。
  - 0.3.1-rc.10 是首次分包版本；此前版本只认识通用包资源键，需要从发布页选择对应架构覆盖安装一次（不卸载），之后继续 App 内更新。按照 1.0 前不保留兼容分支的规则，不保留通用包资源键。
  - 系统会校验 APK 签名必须与已安装版本一致。
  - `versionCode` 由版本号计算，顺序与版本顺序一致：基础版本 ×100 + 后缀分（alpha N → N，beta N → 20+N，rc N → 50+N，正式版 → 99），例如 `0.1.2-beta.1` → 10221、`0.1.2-rc.1` → 10251、`0.1.2` → 10299。不使用 CI 的 run_number。
- **服务端**：`/instance` 返回服务端版本和协议版本。客户端发现协议不兼容时，提示用户更新服务端（Sync fork 或 Actions 更新），或者更新客户端。
- **兼容承诺**（2026-10-15）：1.0 之前（0.x）版本之间不保证兼容，协议、本机数据格式和命令用法都可能改变，升级 CLI 可能需要同时更新服务器。1.0 起冻结协议，破坏性修改只能通过提升协议版本进行。这句话写在 README 和 `harmonia help` 里（`harmonia version` 只输出一行版本号，安装脚本和升级自检读取它）。
- **升级前预检**（2026-10-15）：CLI 的协议版本只定义在一处，发布清单的 `protocol` 由它生成。`harmonia update` 和后台服务升级前，已接入账号时先请求服务器的 `/instance`，新版本清单的 `protocol` 和服务器的不一致就不升级，提示先更新服务器；后台服务把原因记到日志和本机缓存，`harmonia status` 显示。连不上服务器时，`harmonia update` 提示没能确认兼容后照常升级，后台服务跳过、下次检查时再试。1.0 起同一机制作为兼容闸。
- **发布签名私钥**：只存放在 GitHub Actions secrets 中，测试使用临时生成的密钥。

### 5.12 限流与风控

规则和数值以 [protocol.md](protocol.md) 3.8 为准，这里说明取舍和界面表现。

- **目标**：攻击者的行为不能让合法用户无法接入。所以不做“同一账号失败 N 次就锁定”，不做“输错 N 次作废配对码”，也不让所有人共用同一份验证码尝试次数或发信额度，否则攻击者只要故意失败就能把用户挡在外面。
- **依据**：
  - 账号没有密码，知道邮箱的人能做的只有查询账号和创建匿名配对请求；匿名请求不推送、不弹出，管理设备不扫码或输核对码就看不到，最终仍需管理设备批准。
  - 失败次数按网络计数。攻击者从别的网络猜错多少次配对码，都不会让用户所在网络的计数增加。
  - 匿名请求有账号合计上限；用配对码发起的请求另有一个较小的独立上限，不占匿名额度。攻击者把匿名额度占满时，用户在管理设备上生成配对码仍然可以接入。
  - 配对码 8 位（40 位熵），最长 60 分钟有效、同时最多 10 个；同一网络前 5 次输错不受限制，之后等待从 5 秒起翻倍，最长 5 分钟，60 分钟内最多只能试二三十次，即使 10 个配对码同时有效，猜中的概率也可以忽略。猜中也只是让请求出现在管理设备上，批准前仍要核对核对码。
  - 设备会话、恢复会话靠签名，不受任何匿名请求的限流影响；丢失全部设备时还有恢复码。
- **不做可信网络**：曾考虑把已接入设备用过的网络视为可信、单独放行，但移动网络常有大量用户共用一个出口 IP，误判后反而给攻击者放行；每次同步都要记录也有成本（2026-10-07 用户确认）。
- **邮件**：只剩注册验证和重置账号两种用途，共用一份按账号、按网络的额度。额度被攻击者用完时，最长约 1 小时内收不到新邮件，但已经收到的验证码仍然有效。
- **隐私**：网络标识只存 HMAC，原始 IP 只用于配对批准页的显示和“阻止这个网络”，随记录过期删除。
- **界面与 CLI**：
  - 配对码输错过多时显示需要等待的时间，例如“配对码输错次数过多，请 2 分钟后再试。也可以不填配对码，改用扫码。”
  - 配对码不对或已过期时提示“请在管理设备上重新生成配对码，或留空改用扫码”。
  - 匿名请求额度已满时提示“请在管理设备的“添加设备”中生成配对码，用配对码发起”。
  - 发信额度用完时显示“验证码发送次数过多，请稍后再试；已经收到的验证码 15 分钟内仍然有效。”
- **暂不做**：异常请求提醒（管理设备推送和失败记录）；隐藏邮箱是否已注册（匿名查询会区分，已按网络限流；查到的只有账号 ID、是否初始化和账号公钥）。

### 5.13 给 AI 助手使用（2026-10-13）

目标：用户给 AI 助手（Claude Code、Codex 等）一句提示词，它就能装好 CLI，向用户说明后台服务后按用户的选择开启，并知道怎样正确调用 CLI；CLI 升级后，它能拿到新版本的说明。

- **一行安装**：提示词里用 `HARMONIA_YES=0`，安装脚本不询问，只装命令行，不装后台服务（5.8；2026-10-13 用户调整，原先用 `HARMONIA_YES=1` 直接装上）。两个平台都用环境变量，因为 PowerShell 的 `irm | iex` 没法传参数。不能只靠“没有终端就跳过”：AI 助手运行命令的环境有时能打开 `/dev/tty`，脚本会停在询问上。

  ```bash
  curl -fsSL https://github.com/harmonia-vault/harmonia/releases/download/update-feed/install.sh | HARMONIA_YES=0 sh
  ```

  ```powershell
  $env:HARMONIA_YES = '0'; irm https://github.com/harmonia-vault/harmonia/releases/download/update-feed/install.ps1 | iex
  ```

  - `HARMONIA_YES=1` 保留，不询问、直接装上后台服务，供脚本使用。
  - 安装脚本不安装技能文件，由提示词让 AI 助手运行 `harmonia skill`（用户确认）。
- **询问用户**（2026-10-13 用户要求；2026-11-09 调整为只问后台服务）：装好后，AI 助手按使用说明向用户解释后台服务，问是否开启，用户同意才运行 `harmonia service install`。说明里写清：
  - 作用：后台服务保持与服务器的连接，变量、授权和撤销几秒内同步，授权到期及时停用，每天检查更新。
  - 不开启时怎么用：`harmonia exec -- <命令>` 每次启动先同步一次，只是在运行这类命令时才同步。
  - 区别：后台服务让变量始终最新、撤销最快生效，代价是一个常驻进程。
  - AI 助手不主动提出 Shell 集成。用户自己要求“终端里自动带上变量”时，先说明代价（变量对这个用户的所有程序可见、本机留有明文变量文件，Windows 上明文存在注册表）和替代办法 `harmonia exec`，用户坚持才运行 `harmonia shell install --yes`。
  - Linux 上开启后台服务后提示的 `sudo loginctl enable-linger`，由 AI 助手转告用户并说明原因，不自己运行 sudo。
- **使用说明（技能）**：内容是一份 `SKILL.md`（带 `name`、`description` 头部），放在 `cli/internal/skill/SKILL.md`，编译进 CLI，不单独发布。开头写明对应的 harmonia 版本。内容包括：读取最新说明（会话中途程序可能被后台升级，命令报用法错误时重新运行 `harmonia skill` 或 `--help`）、安装、接入账号要用户在手机上批准（用 `--email`、`--code` 参数，等待最长 5 分钟）、用 `harmonia exec` 使用变量、不把变量值打印到对话里、通过标准输入写入变量值、哪些命令需要用户明确同意才能运行。
- **`harmonia skill`**：把使用说明输出到标准输出，AI 助手直接读取。
- **`harmonia skill install [--dir 目录]`**：保存成技能文件 `<技能目录>/harmonia/SKILL.md`。保存的是入口文件（2026-10-15 调整）：头部与完整说明相同，正文只让 AI 助手每次使用前运行 `harmonia skill` 读取当时的说明，并附找不到命令时的位置和安装命令（`cli/internal/skill/STUB.md`）。完整说明始终由程序输出，程序升级（包括后台自动升级）后技能文件不会过期。
  - 不给 `--dir` 时，写入 `~/.claude/skills` 和 `~/.agents/skills` 中所在工具目录（`~/.claude`、`~/.agents`）已存在的那些，再加上之前保存过的位置；一个都没有时报错，提示用 `--dir` 指定或改用 `harmonia skill`。
  - 给 `--dir` 时只写这一处。
  - 写入过的文件记在 `~/.harmonia/settings.json`（与账号无关，退出登录时保留）。
- **升级后更新说明**（2026-10-15 调整）：
  - 入口文件不随版本变化，升级后一般不需要改写。记录的技能文件内容和当前入口文件不同时（例如早期版本保存的是完整说明），在这几处换成入口文件：`harmonia update` 替换程序后、后台服务启动时、运行 `harmonia skill` 时（不输出任何提示，免得混进说明）。用户已经删掉的不再写回。
  - `harmonia update` 完成后提示 AI 助手运行 `harmonia skill` 重新读取。已经读进会话的旧说明无法更新，说明里要求 AI 助手在命令报用法错误时重新读取；CLI 遇到不认识的选项会报错并提示 `--help`。
  - 不在程序升级后向 stderr 输出“请重新读取说明”：CLI 分不清调用方是 AI 会话还是脚本，提示会混进脚本日志。
- **卸载**：`harmonia uninstall` 删除记录的技能文件，`harmonia` 目录为空时一并删除。
- **README 和实例首页**：优先推荐 AI 助手部署（2026-10-13 用户确认）。给出一段 macOS、Linux、Windows 通用的提示词：开头一句介绍 Harmonia（用户部署的环境变量同步服务，开源、自托管，附这台服务器的地址，说明 AI 助手可以用命令行取用变量、不必让用户把 Key 贴进对话）。提示词对 AI 助手说话，用“用户”称呼使用者，不用“我”，然后同时写两个平台的安装命令，由 AI 助手按系统选用；让 AI 助手向用户要邮箱和配对码。实例首页把它放在“接入电脑”一步、手动安装命令之前（不放在服务器地址和 App 配对之前，2026-10-13 用户调整），已经填好这台服务器的地址，带“复制”按钮；提示词框只显示约 5 行，超出部分在框内滚动，带滚动条（2026-10-13）。README 在“在电脑上接入”开头给出同一句，手动安装放在后面。
- **App 里复制**（2026-10-14 用户要求）：设备页“添加设备”的浮动菜单里有第三项“复制 AI 安装提示词”，点后弹出“让 AI 助手安装”弹窗，不加说明文字。顶部两个选项：
  - “仅服务器”：与实例首页的提示词相同，服务器地址是这台手机接入的服务器，邮箱和配对码让 AI 助手向用户询问。默认选中。
  - “含邮箱和配对码”：选中后先选有效期（与“生成配对码”相同，默认 10 分钟），点“生成”后把账号邮箱和配对码写进提示词，AI 助手不必再询问；提示词下面一行显示配对码和剩余时间。配对码过期后回到选择有效期，按钮为“重新生成”。用这个配对码发起的请求和平常一样弹出批准页，仍要核对核对码。
  - 提示词框约显示 5 行，超出部分在框内滚动，文字可以选中；底部是“关闭”和“复制”，复制后提示“已复制”。

## 6. 关键流程

- **确定账号后**：先设置 App PIN（可选开启指纹），生成本机数据密钥。之后首次设置、配对、恢复中生成的设备密钥，一律用它加密后再保存。
- **首次设置**：用注册会话，手机生成账号根密钥、设备密钥、恢复码（用户完整重输确认）、恢复公钥，然后调用 `POST /account/setup` 原子完成。之后引导用户创建第一个环境。
- **写入变量**：本地加密，`PUT`（多个变量时用批量写入）时带幂等键；服务端接受后推送 `changed`；包括写入方在内的所有设备都通过 `/sync` 更新本地，不做乐观更新。写入必须在线。
- **批准设备**：见 5.10。授权行和封装在同一个事务中写入。
- **降权或升权**：只修改授权行。**新增环境授权**：管理设备验证目标设备的证书后，为它封装环境钥。
- **撤销**：服务端删除该设备的授权、封装和会话，推送 `revoked` 并断开连接；设备联网后自我清除。
- **删除环境或变量**：服务端删除密文并留下墓碑；所有设备同步后从缓存和 `env.sh` 中移除。
- **恢复**：获得恢复会话 → 解开全部环境钥 → 生成本机密钥，用恢复签名钥签发证书，然后 `enroll`（此时 `rotation_required = true`）→ 强制轮换：先显示说明页（新恢复码提交前不生效、只显示一次、完成前无法管理），用户确认后生成新恢复码，用户完整重输，重新封装全部环境钥，旧恢复钥签名轮换记录，`rotate`（带幂等键，结果不明时可以查询）。提交成功后，旧恢复码才失效。
- **恢复后检查其他设备**：恢复不会撤销任何已有设备，旧手机和管理登录过的电脑仍是有效的管理设备。因此强制轮换的完成页保存 PDF 后，进入“检查其他设备”页：
  - 列出账号中除本机以外的全部设备，管理设备在前、电脑在后，显示名称、平台和最后在线时间。
  - 说明其他管理设备仍然可以访问全部环境、批准和移除设备（管理设备可能是手机，也可能是电脑，见第 16 节）；已丢失或不再使用的设备应当移除。
  - 每台设备前有勾选框，默认都不勾选。勾选后点“移除所选（N 台）”：确认框列出所选设备的名称，确认后只验证一次身份，再逐台调用现有的撤销接口（不新增接口）。全部成功后进入主页；有设备没移除成功时留在本页，只保留未移除的设备并说明原因，可以重试或点“完成”。
  - 不勾选任何设备时点“完成”，保留全部设备，进入主页。
  - 没有其他设备时跳过这一页。只在这次恢复完成后出现一次：中途退出 App 后不再显示，之后仍可在“设备”页移除。主动轮换恢复码不显示这一页。
- **主动轮换恢复码**：流程与上面相同（同样先显示说明页，提交前再验证一次身份），轮换记录由管理设备签名。
- **生成配对码**：管理设备调用 `POST /pairing-codes`，把显示的配对码告诉要接入的设备（5.10）。不需要再次验证：配对码只让请求出现在管理设备上，批准时仍要验证。
- **退出（logout）**：先通知服务端撤销本机（离线时先清本地，联网后补发），然后删除本地密钥和缓存（App 还要删除 PIN 槽、指纹槽和对应的 Keystore 密钥），并删除 `env.sh`。
- **卸载 CLI**：logout + 卸载服务 + 移除 rc 行 + 删除 `~/.harmonia`（包括 `shell.sh`、`env.sh`）和二进制文件。

### C. 生命周期闭环

部署 / 升级服务端；安装 / 升级 / 重装 App（重装视为新设备）；安装 / 升级 / 卸载 CLI；配对 / 撤销 / logout；创建 / 删除环境和变量；授权 / 降权 / 到期；安装 / 移除 shell 集成和后台服务，重启后自动恢复；生成 / 轮换恢复码；生成配对码。

### D. 异常场景

每种情况都要有明确的提示和下一步指引：

- 地址错误、不是 Harmonia 服务、服务端无法连接、协议版本不兼容
- 邮箱未注册、配对码错误或过期、配对码输错被限流
- 配对请求过期、扫错二维码、配对被拒、匿名请求额度已满
- 操作中途断网（写入、批准、轮换恢复码）
- CLI 离线时使用缓存；授权到期后停用；联网后自动追上
- 两台设备同时修改同一变量（最终一致）
- 删除一个正在使用中的环境
- 已撤销的设备再次联网
- 服务端升级后客户端继续可用
- App 被系统杀掉后重新打开
- 恢复码输错
- rc 文件是符号链接
- 更新包签名或哈希验证失败

### E. 自动化回归

`mise run test` 和 `mise run e2e` 全部通过。这是开发门禁，**不等于验收通过**。

CI（`ci.yml`，2026-11-09 调整）：

- 按改动的路径决定跑哪些任务：`cli/**` 跑 Linux、Windows 的 CLI 测试；`server/**` 跑服务端测试；`app/**` 跑 App 分析与测试和 iOS 无签名构建；三者任一有改动、或 `e2e/**` 有改动时跑端到端。改了 `ci.yml` 或 `mise.toml` 时全部都跑；只改文档时都不跑。
- 端到端与各单元测试并行，不再等它们结束；无界面管理脚本先编译成可执行文件再调用。
- 同一分支有新的推送时取消还在跑的旧运行。
- 工具版本从 `mise.toml` 读取，不在工作流里另写一份；发布流程 `release.yml` 同样如此。Android SDK 用 runner 自带的：`mise.toml` 里的 `ANDROID_HOME` 已经设置时沿用。
- 端到端启动服务端时传入 `DEV_RELAXED_LIMITS=true`（[protocol.md](protocol.md) 3.8），不再为等过每分钟限流而停顿；心跳超时那一步仍然真实等待。

### F. 最终验收：新用户测试

在全新的 Cloudflare 账号、没装过 App 的手机、干净的 Linux VPS 和 Mac 上，**只看 README** 完成“部署 → 使用 → 撤销 → 恢复 → 升级 → 卸载”的全过程。任何卡住的地方都算缺陷。

### G. 质量底线

- 界面和 CLI 输出中没有内部术语，每条错误都告诉用户下一步怎么做。
- 升级不丢数据：服务端有表结构迁移，App 覆盖安装后数据保留。
- 实时同步：在线设备 3 秒内收到变化；断线重连后自动补齐。

1. 改动 API、数据格式、安全口径或用户流程之前，先更新 `docs/`，由用户确认。

7. 不提交过程产物（证据、验证记录、状态流水）；`docs/` 只放设计。
8. 界面和 CLI 文案面向用户，不出现内部术语。
9. 一次只推进一个里程碑，不预先实现后续功能。

## 11. 附录：旧项目的经验

- systemd 系统单元开启 `ProtectHome=true` 后无法访问 home 目录；用户级服务没有这个问题。
- 已经在运行的进程，环境变量无法从外部修改，文档必须写明。
- Android 的 `versionCode` 不能依赖 CI 的 run_number，迁移仓库后编号会回退。
- 更新检查失败时，不能显示“已是最新版本”；要区分网络错误、签名错误和元数据错误。
- 不要根据 Release 列表的第一项、发布时间或文件后缀来猜测最新版本，只认签名清单。
- Workers 上运行 Argon2id 的资源占用有风险，所以改为客户端计算 Argon2id。

| 信任锚 | 管理设备维护“受信签发者集合”，证书逐级追溯 | 一把**账号根签名钥**：生成于首次初始化，封装给每台管理设备和恢复码；设备证书与每个环境钥封装都由它签名。设备首次接触账号时钉住 `rootPub`，配对指纹包含 `rootPub` | 更简单，没有证书链；还堵住了“服务器偷换封装”的漏洞（匿名 sealed box 本身不认证发送方） |

### 12.5 去掉密码，配对改为扫码和一次性配对码（2026-10-13）

密码不参与加密，真正的认证一直是管理设备核对指纹后批准；它只起“防止陌生人发配对请求”的作用，代价是要把它输进服务器、虚拟机这类不可信的机器。因此去掉密码（M12）。

| 决策 | 结论 |
| --- | --- |
| 账号 | 只有邮箱。删除预登录、密码登录、找回密码、修改密码、登录邮件加验、受攻击状态、恢复时设置新密码，以及修改密码作废待处理请求 |
| 注册 | `POST /register` 只带邮箱。需要验证邮箱时（`REQUIRE_EMAIL_VERIFICATION`）照旧用邮件验证码，验证通过后发放注册会话；不需要时注册直接发放。注册会话 15 分钟，只能查看账号信息和首次初始化。已注册但未初始化的账号没有任何数据，可以重新注册；已初始化的返回 `conflict` |
| 查询账号 | 新增匿名接口 `GET /accounts/lookup?email=`，返回账号 ID、是否初始化和 `rootPub`，按“以邮箱为入口”的规则限流。服务器谎报 `rootPub` 不构成问题：指纹包含 `rootPub`，管理设备批准前会比对 |
| 配对请求 | `POST /pairings` 不需要会话，用请求头 `X-Harmonia-Account` 指定账号，有效期 5 分钟。不带配对码的是匿名请求：不推送、不自动弹出、不出现在待批准列表中，管理设备只能扫码或手输核对码取到。`GET /pairings` 每项带 `authorized`。指纹、核对、权限选择、再次验证、批准、等待连接都不变，不新增签名或加密格式 |
| 配对码 | 管理设备生成（`POST /pairing-codes`）：8 位 Crockford Base32，有效期 5 到 60 分钟、默认 10 分钟，创建一个请求后作废，每个账号同时最多 10 个（2026-10-14 调整，此前 5 分钟、同时只有一个），服务端只存哈希。带有效配对码的请求才推送和弹出，并且不占匿名额度。配对码只代替密码，不代替指纹核对。CLI 和新手机走同一条路径 |
| 猜错配对码 | 复用按“账号 + 网络”计数的递增等待（前 5 次不限，之后从 5 秒起翻倍，最长 5 分钟，成功后清零）；不作废配对码，不锁定账号 |
| 接受的风险 | 有人把自己设备的二维码或核对码发给用户，诱导扫码批准（4.2 第 8 条）。靠批准页的设备名、平台、来源 IP，以及只在自己发起时批准来防护 |
| 密码学 | Argon2id 只用于 App PIN；CLI 的密码派生代码和测试向量删除 |

### 12.7 电脑作为管理设备（2026-10-14）

| 决策 | 结论 |
| --- | --- |
| 电脑能否作为管理设备 | 可以。同一台电脑另外接入一个管理身份，在服务端是独立的一台设备；协议不新增接口和签名格式 |

| 决策 | 结论 |

| 引用上的“可以修改” | 去掉。电脑能不能改变量只看授权的“读写”；新增变量要求读写授权的环境里有这个变量库的“全部变量”引用（用户确定） |
| 环境 ID | App 环境详情和命令行环境列表显示完整 ID；命令行支持环境 ID 或名称，环境名不能重复。变量库 ID 保留 |
| 授权期限和批准后的时长 | 合并成用户只看到一个期限：需手机批准的授权一直有效，直到取消；期限只在开启无人值守使用时选。批准页的“有效时长”改名为“多久内不再询问”（用户确定） |
| 允许本机解密 | 收进授权面板底部可展开的“高级”，标题改为“无人值守使用（本机解密）”；开启时的风险确认和设备详情里的醒目标记保留（用户确定） |
| 环境页里的变量 | 点变量先弹出变量面板：改名（只影响这个环境）、从环境中移除、进入编辑值和备注；“编辑引用”只负责选变量库和变量（用户确定） |

## 14. iOS App（v0.2.0，M10）

iOS App 与 Android App 是同一个 Flutter 工程（`app/`），`lib/` 下的界面和核心逻辑共用。除本节列出的差异外，页面、状态机、App 锁规则、配对和恢复流程都与 5.9、5.10 相同，协议和服务端不需要改动。

### 14.1 范围

**做：**

- `app/ios` 工程，最低支持 iOS 16；只面向 iPhone，iPad 上以 iPhone 兼容模式运行，不单独适配。
- Swift 原生实现，与 Android 的 Kotlin 部分一一对应：本机密钥保护、面容 ID / 触控 ID、恢复码 HTML 转 PDF、通过系统“存储到文件”保存、敏感内容复制、设备名。
- 界面沿用现有的 Material 风格，不另做一套 iOS 风格的界面。
- 同时发布 GitHub 未签名 IPA 与 TestFlight 内部测试包，更新行为见 14.4。

**不做：** 上架 App Store、AltStore / SideStore 软件源、App 后台推送（2026-11-09 起在 M16 做，见第 18 节；只有发布者签名的版本能收到）、iPad 布局、小组件、Apple Watch。

### 14.2 与 Android 的差异

| 项 | Android | iOS |
| --- | --- | --- |
| 协议中的 `platform` | `android` | `ios` |
| 默认设备名 | 用户在系统设置里给手机起的名字；取不到时用厂商 + 型号（2026-10-12 调整） | `iPhone`：iOS 16 起，系统只对苹果单独批准了权限的 App 提供用户起的设备名，自行签名的安装包拿不到。接入后可以在“设备详情”里重命名 |
| 生物识别 | 指纹（Class 3） | 面容 ID 或触控 ID，以本机支持的为准；文案随之显示“面容 ID 解锁”或“触控 ID 解锁” |
| 生物识别变化 | 新增或删除指纹、关闭锁屏后作废 | 新增或删除面容、指纹，或关闭锁屏密码后作废；之后的处理相同（改用 PIN，提示已关闭，可以在设置中重新开启） |
| 恢复码 PDF | 系统打印框架排版，“保存到”选择位置 | 系统网页引擎排成 A4，“存储到文件”选择位置；模板同为 `app/assets/recovery_sheet.html` |
| 敏感内容复制 | 标记为敏感，App 在 1 分钟后清空 | 由系统在 1 分钟后让剪贴板内容过期，并且不同步到其他 Apple 设备 |
| 扫码 | `mobile_scanner` | 相同；首次使用时系统询问相机权限，被拒绝时提示改为输入核对码，或到系统设置中允许 |
| 账号表单自动填充 | 需要替换 FlutterView 才能正常工作 | 系统自带，不需要额外处理 |
| 更新 | App 内下载并安装 APK | Apple 分发包只提示新版本号；GitHub IPA 下载并校验 IPA，交给签名工具安装，见 14.4 |

### 14.3 本机存储与密钥保护

格式见 [protocol.md](protocol.md) 2.5 的 iOS 部分。

- **PIN 槽**：`kek` 由 Secure Enclave 中不可导出的 P-256 私钥参与计算，每试一次 PIN 都要调用一次 Secure Enclave，PIN 无法拿到手机以外暴力破解。
- **面容 ID / 触控 ID 槽**：本机数据密钥保存为一条钥匙串条目，每次读取都由系统验证面容或指纹，不接受锁屏密码。
- **仅限本机**：钥匙串条目全部设为仅限本机，不进 iCloud 钥匙串，不会随备份或换机迁移到另一台手机；App 的数据目录标记为不备份。因此从备份恢复、换机迁移之后，App 都是一台新设备，需要重新接入，由管理设备批准或用恢复码恢复。
- **卸载重装**：iOS 的钥匙串在卸载后不会清除。App 启动时如果数据目录中没有安装标记，就先清除钥匙串中的残留（两个槽、Secure Enclave 密钥、输错记录），再写入标记。这样卸载重装同样视为新设备。
- **模拟器**：模拟器没有 Secure Enclave，仅在模拟器构建中改用保存在钥匙串里的普通 P-256 私钥，供布局检查使用；真机构建不包含这条路径。

### 14.4 分发与更新

- **发布物**：每个 Release 增加 `harmonia-<版本>.ipa`（未签名），由 CI 在 macOS 上构建。签名清单的 `assets` 增加 `ios` 一项（下载地址、SHA-256、大小），格式与 Android 分包相同。构建号沿用 Android 的 `versionCode` 算法。
- **TestFlight 内部测试**（2026-11-11 增加）：Release 工作流完成公开发布后调用独立的 TestFlight 工作流，也支持指定已发布标签手动重跑。使用仓库的 `IOS_CERTIFICATE_BASE64`、`IOS_CERTIFICATE_PASSWORD`、`IOS_APP_PROFILE_BASE64` 导入临时钥匙串并手动签名，使用 `ASC_KEY_ID`、`ASC_ISSUER_ID`、`ASC_PRIVATE_KEY` 上传；构建同一个发布提交，不复用公开 IPA；构建号为 GitHub `run_id.run_attempt`，跨工作流及重跑不重复。导出限制为内部测试，上传后由 Apple 处理；出口合规按下方“加密声明”处理。
- **Apple 包检查更新**：仅该构建传入 `APPLE_DISTRIBUTION=true`。沿用渠道、检查频率、版本比较和清单签名验证，只读取版本号；发现更新仅提示新版本号，不读取 IPA 元数据，不显示更新说明、下载页、签名工具或分享入口。页面调试同步使用独立的模拟场景，不访问真实更新服务。
- **加密声明**（2026-11-11 增加）：iOS 包使用系统之外的 libsodium 加密（协议第 2 节）。在 App Store Connect 如实选择系统外的标准加密算法、当前不在法国分发后，问卷明确提示无需上传文稿。因此 `Info.plist` 声明 `ITSAppUsesNonExemptEncryption=false`，表示豁免提交加密材料，并非不使用加密；无需填写 `ITSEncryptionExportComplianceCode`。此声明适用于当前的加密实现与非法国分发范围；改变算法或扩大至法国分发前，重新评估并更新声明。
- **安装**：使用者用 AltStore、SideStore 或自己的开发者证书签名后安装。README 说明安装步骤，并提醒：
  - 用免费 Apple ID 签名的 App 7 天后过期，需要在过期前重新签名（上述工具会自动续签）；过期后 App 打不开，重新签名后数据仍在。
  - 换一个 Apple ID 或证书签名，相当于安装了另一个 App，原来的数据读不到，需要按新设备重新接入。
- **GitHub IPA 检查更新**：时机和渠道规则与 Android 相同（前台、24 小时内最多一次、正式版与测试版渠道），同样验证清单签名。发现新版本时显示版本号和更新说明，提供“下载并导入签名工具”和“打开下载页”。
- **GitHub IPA 下载并导入签名工具**（2026-10-12 增加）：App 下载新的 IPA，按清单核对大小和 SHA-256，然后弹出系统的分享面板，由用户选择安装 Harmonia 时使用的签名工具（轻松签、全能签、万能签等能接收 IPA 文件的工具都会出现在面板里）；之后的签名和安装在签名工具里完成，数据会保留。这样做不依赖各个工具自己的跳转接口（它们没有公开、稳定的“传入下载地址即导入”的接口），并且交出去的文件经过了校验。App 自己仍然不安装 IPA；下载的文件放在缓存目录，取消时立即删除，交出去的那一份在下次下载前清掉。
- **不做软件源**：AltStore / SideStore 的软件源没有签名校验，本次不提供。

## 15. Windows CLI（v0.3.0，M11）

Windows 上的 CLI 与 macOS、Linux 是同一份代码（`cli/`）：命令、配对、同步、权限、本地覆盖、更新渠道都相同。协议和服务端只增加一个设备字段（15.3 的系统变量开关），App 只增加对应的开关和 Windows 设备的图标。本节只列差异。

### 15.1 范围

**做：**

- 支持 Windows 10（1809 及以上）、Windows 11、Windows Server 2019 及以上，amd64 与 arm64。
- 把变量写入 Windows 的用户环境变量、登录后运行的后台服务、`exec`、自更新、卸载、PowerShell 安装脚本。
- 全程不需要管理员权限。

**不做：** PowerShell 配置文件注入与提示符刷新、cmd 的自动运行脚本、Git Bash / MSYS2 / Cygwin 的 shell 集成（WSL 里请安装 Linux 版）、开机未登录即运行的 Windows 服务、winget / Scoop / MSI 安装包、程序的代码签名、图形界面。

### 15.2 与 macOS、Linux 的差异

| 项 | macOS、Linux | Windows |
| --- | --- | --- |
| 协议中的 `platform` | `darwin`、`linux` | `windows` |
| 程序位置 | `~/.local/bin/harmonia` | `%LOCALAPPDATA%\Programs\Harmonia\harmonia.exe`，安装脚本把这个目录加入用户的 `Path` |
| 数据目录 | `~/.harmonia`，目录 0700、文件 0600 | `%USERPROFILE%\.harmonia`，访问控制列表只允许本人、系统和管理员访问，不继承上级目录的权限 |
| 变量怎么生效 | `env.sh` + rc 文件注入 + 提示符刷新（5.8） | 写入用户环境变量（15.3）；不生成 `env.sh` |
| `harmonia shell install｜uninstall` | 修改 rc 文件 | 开启、关闭“写入用户环境变量” |
| `harmonia shell system-vars on｜off` | 不需要：rc 注入对所有名字一视同仁 | 是否写入 `Path`、`TEMP` 这类系统变量（15.3） |
| 后台服务 | `systemd --user`、LaunchAgent | 当前用户的计划任务（15.4） |
| `harmonia exec` | 用要运行的命令替换自身 | 启动命令并等它结束，退出码与它相同；Ctrl+C 交给它处理。cmd 和 PowerShell 自带的命令要写成 `cmd /c …` 或 `powershell -Command …` |
| `harmonia import` | 列出当前终端里的变量，排除系统和 shell 自带的 | 相同，排除的是 Windows 自带的变量 |
| 默认设备名 | 主机名 | 计算机名 |
| 自更新 | 原子替换程序文件 | 运行中的程序不能被覆盖：先把当前程序改名为 `harmonia.exe.old`，再放入新程序 |
| 卸载 | 直接删除自身 | 运行中的程序不能删除自身：命令结束后几秒内由系统命令删除 |
| 安装脚本 | `install.sh` | `install.ps1`（15.5） |

### 15.3 写入用户环境变量

Windows 没有每个终端都会读取的 rc 文件；系统自己的办法是“用户环境变量”，新启动的程序都会带上。Harmonia 在 Windows 上用它代替 5.8 的 rc 注入。

- **位置**：注册表 `HKCU\Environment`，也就是“系统属性 → 环境变量”上半部分的“用户变量”，在那里可以直接看到 Harmonia 写入的内容。写入后通知系统“环境变量已变化”。
- **开关**：`harmonia shell install` 开启，`harmonia shell uninstall` 关闭并恢复原状。开启前先说明将要做什么和代价，确认后才执行（默认 N，2026-11-09）；安装脚本不询问、不开启（5.8）。没有开启时，Harmonia 不碰用户环境变量，变量只能通过 `harmonia exec`、`harmonia export` 使用。命令沿用 `shell` 这个名字，是为了三个平台的命令和文档一致；Windows 上的帮助、提示和 `harmonia status` 写的是“用户环境变量”。
- **写入时机**：与另外两个平台重写 `env.sh` 的时机相同：后台服务或 CLI 命令每次同步之后，以及激活、顺序、授权、本地覆盖变化之后。只写有变化的变量，没有变化时不通知系统。
- **生效边界**：
  - 新启动的程序读到新值：从开始菜单、任务栏、资源管理器启动的程序，Windows Terminal 新开的标签页。
  - 已经打开的终端和程序不会变，需要重开；从旧终端里启动的程序沿用旧终端的值；VS Code 之类自带终端的程序要重启程序本身。
  - 想在当前终端马上用到最新值，用 `harmonia exec`。
- **接管与恢复**：只处理 Harmonia 托管的变量。接管一个名字之前，先把它原来的状态（有没有、值、类型）记在数据目录的 `sysenv.json` 里；不再托管时恢复成原来的样子，原来没有就删除。不再托管的情况包括：变量被删除、环境被停用、授权到期或被撤销、退出登录、关闭开关、卸载。托管期间手动修改同名的用户变量，会在下一次同步时被覆盖；恢复时回到接管之前的值。
- **系统变量开关**（2026-10-12 用户确认）：
  - 系统自身使用的名字默认不写入，例如 `Path`、`PATHEXT`、`TEMP`、`TMP`、`USERPROFILE`、`APPDATA`、`SystemRoot`、`ComSpec`、`PSModulePath`，完整名单在代码里。写坏它们会让系统或其他程序无法工作。
  - 每台设备有一个“写入系统变量”开关，保存在服务端，默认关闭，做法与激活状态相同：在 App 的设备详情页（只对 Windows 设备显示）和这台电脑上的 `harmonia shell system-vars on|off` 都能修改，随同步生效（协议 3.2、3.4）。
  - 开启后，这些名字和其他变量一样写入，不再托管时一样恢复原值；关闭后，已经写入的系统变量在下一次同步时恢复原值。
  - 服务端版本较旧、没有这个开关时，按关闭处理；修改时提示先更新服务端。
- **不写入的变量**（`harmonia status` 会列出，`harmonia exec` 不受影响）：
  - 系统变量开关关闭时，上面那些系统自身使用的名字。
  - 空值：Windows 的用户环境变量不能为空。
  - 超过 32,767 个字符的值：超出 Windows 对单个环境变量的限制。
  - 只有大小写不同的名字：Windows 把它们当成同一个变量，只写入按名称排序的第一个。
- **值的保存方式**：保存为普通字符串，值里的 `%NAME%` 不会被展开，换行原样保留。
- **安全口径**（4.2 第 3 条的 Windows 部分）：
  - 值以明文保存在当前用户的注册表里（用户配置文件中的 `NTUSER.DAT`，只有本人、系统和管理员能读），保护程度与 `env.sh` 相同。
  - 与 rc 注入不同的是，本用户之后启动的**所有**程序都会带上这些变量，包括图形界面程序。
  - 使用漫游用户配置文件的域环境里，注册表会同步到域服务器，不建议开启。
  - “写入系统变量”开关没有加密，服务端可以改动它，但改不了变量的值：它只决定账号里已有的同名变量是否写入这台电脑。
  - 直接删除程序或数据目录不会清理已经写入的变量，要用 `harmonia shell uninstall` 或 `harmonia uninstall`。

### 15.4 后台服务

- **形式**：名为“Harmonia”的计划任务，触发条件是当前用户登录；以当前用户的普通权限运行。注册、启动、停止、删除都不需要管理员权限。和 macOS 一样，登录之后才运行；电脑开机但没有人登录时不运行。
- **不显示窗口**：后台服务在没有窗口的控制台里运行，登录时不会弹出或闪过终端窗口。
- **只运行一个**：同一个数据目录只允许一个后台服务，重复启动的会直接退出。
- **停止与重启**：由 CLI 通知后台服务自己退出，不强行结束进程；`harmonia service status` 据此判断是否在运行。
- **意外退出**：计划任务每 10 分钟检查一次，后台服务不在运行就重新启动。
- 职责与另外两个平台相同：维持推送连接、同步、写入用户环境变量（已开启时），每 24 小时检查一次更新。日志在数据目录的 `daemon.log`。

### 15.5 安装、更新与卸载

- **安装**：在 PowerShell 里运行一行命令。系统自带的 Windows PowerShell 5.1 和 PowerShell 7 都可以，不需要管理员权限，也不需要修改脚本执行策略：

  ```powershell
  irm https://github.com/harmonia-vault/harmonia/releases/download/update-feed/install.ps1 | iex
  ```

  脚本按更新渠道的清单下载当前处理器架构对应的 `harmonia.exe`，校验 SHA-256，放到安装目录并加入用户的 `Path`；然后询问是否安装后台服务，直接回车即同意（默认 Y）；不询问、也不开启“写入用户环境变量”（5.8，2026-11-09）。安装测试版时先运行 `$env:HARMONIA_CHANNEL = 'beta'`；先运行 `$env:HARMONIA_YES = '1'` 时不询问，直接安装后台服务；`'0'` 时不询问，不安装（5.13）。
- **发布物**：每个 Release 增加 `harmonia-windows-amd64.exe` 和 `harmonia-windows-arm64.exe`，签名清单的 `assets` 增加 `cli-windows-amd64`、`cli-windows-arm64`；`install.ps1` 与 `install.sh` 一样放在 `update-feed` 中。
- **不做代码签名**：用安装脚本下载的程序不会被 SmartScreen 拦截；从浏览器手动下载再运行时系统会提示“Windows 已保护你的电脑”，README 说明这种情况以及怎样用清单里的 SHA-256 自行核对。
- **更新**：`harmonia update` 的步骤与 5.11 相同（下载 → 验证签名和哈希 → 自检 → 替换 → 重启后台服务），旧版本保留为 `harmonia.exe.old`。
- **卸载**：`harmonia uninstall` 依次退出账号、恢复用户环境变量、移除计划任务、删除数据目录、把安装目录从用户的 `Path` 中去掉、删除程序。

### 15.6 开发与测试

- 工具链不变，Windows 版由 Go 交叉编译；`mise run check-cli-windows` 在任意系统上对 Windows 部分做静态检查。
- 写入用户环境变量的规则（接管、恢复、跳过）是核心逻辑，放在 `cli/internal` 并做单元测试；注册表读写、数据目录权限、文件锁在 Windows 上测试。

- 分工：我在 Windows 11 虚拟机里跑安装、写入、后台服务、升级和卸载；真机验收由你进行。

## 16. 电脑作为管理设备（M13）

让电脑上的 CLI 也能成为管理设备，并提供一个在本机浏览器里打开的管理页面，三个平台相同。协议不新增接口和签名格式，只在 [protocol.md](protocol.md) 2.5 增加管理密钥在电脑上的保存格式；服务端和 App 不需要改动。

### 16.1 范围

**做：**

- 同一台电脑上，日常身份之外另有一个管理身份，两者各自登录、各自退出。
- 管理身份的密钥用管理口令加密保存，只在管理页面解锁期间解开。
- `harmonia manager` 在本机打开管理页面：管理登录、环境和变量管理（含批量操作）。

**不做：**

- 由服务器提供管理页面：页面代码每次由服务器下发，服务器被控制后可以换掉脚本拿走密钥，与 4.1 第 2 条冲突。
- 把日常身份的密钥也加密；系统钥匙串、触控 ID、Windows Hello、硬件钥匙。
- 让脚本或 AI 助手使用管理身份；在电脑上用恢复码恢复账号。
- 本里程碑不做设备管理（批准、权限、移除、配对码）和更换恢复码，它们仍在手机上操作，见 16.8。

### 16.2 两个身份

| | 日常身份 | 管理身份 |
| --- | --- | --- |
| 命令 | `harmonia login`、`harmonia logout` 及现有命令 | 全部在 `harmonia manager` 之下 |
| 用途 | 后台同步、`exec`、读写被授权环境的变量 | 管理设备的操作 |
| 能访问的环境 | 手机授权给它的那些 | 全部 |
| 密钥保存 | 0600 文件，与现在相同 | 用管理口令加密（协议 2.5） |
| 何时解开 | 随时 | 只在管理页面解锁期间，锁定即清除内存中的密钥 |

- 两个身份在服务端是两台设备，各有自己的密钥和证书，互不影响：可以只有其中一个，退出一个不影响另一个。
- 两个身份必须属于同一台服务器上的同一个账号。已有一个身份时，登录另一个沿用它的服务器地址和账号；都没有时，管理登录自己询问服务器地址和邮箱。
- 管理身份的默认设备名是“<这台电脑的设备名>（管理）”，登录时可以修改。
- 管理身份不在本机保存任何缓存（环境钥封装、变量、账号根密钥都不保存）：解锁后现登录、现同步，账号根密钥从同步结果的封装中解开并与本机钉住的 `rootPub` 核对。后台服务不接触管理身份。

### 16.3 命令

```
harmonia manager [ui] [--port 端口] [--no-open]
                                      打开管理页面；还没有管理登录时，页面从登录开始。
                                      --no-open 只打印地址，不自动打开浏览器
harmonia manager login                同上，直接进入登录步骤；已经登录时提示并打开管理页面
harmonia manager logout               退出管理登录
harmonia manager status               是否已管理登录、设备名（不需要口令）
```

- 管理登录、设置和修改口令、全部管理操作都在管理页面里完成，终端里不另做一套。
- `harmonia status` 增加一行，说明这台电脑是否有管理登录。
- 使用说明（`harmonia skill`）写明：AI 助手不运行 `harmonia manager` 下的任何命令。

### 16.4 管理口令

- **规则**：8–128 个字符，只能用英文字母、数字和键盘上的符号（中间可以有空格）；大写字母、小写字母、数字、符号四类中至少包含两类。
- **常见口令表**：设置和修改口令时，口令（不区分大小写）与表中某一项相同就拒绝，提示“这个口令太常见，请换一个”。
  - 来源：SecLists（MIT 许可）的 `Passwords/Common-Credentials/100k-most-used-passwords-NCSC.txt`，取固定的一次提交，只保留 8 个字符及以上的条目。
  - 文件放进仓库并编译进程序，旁边记录来源、提交号和许可证。程序运行时不联网获取或更新这张表；口令和它的任何摘要都不发往任何在线服务。
  - 更新这张表只能改仓库里的文件，随新版本发布。
- **规则和常见口令表只在设置、修改口令时检查。** 解锁时只看口令能否解开密钥，不再检查规则和表。所以表或规则以后随版本变化，已经设置的口令照常可用，不会被挡在外面。
- **在管理页面里输入。** 输入框标记为不让浏览器保存或自动填充。终端里只有 `harmonia manager logout` 会询问口令：不回显，不接受命令行参数、环境变量或标准输入。
- 设置时输入两次。输错时提示口令不对，可以重输，不做等待限制：每次尝试本身约需 1 秒，而文件被拿走后的离线猜测不受本机限制约束。
- **修改口令**：在管理页面的设置中，先输入旧口令。
- **忘记口令**：`harmonia manager logout` 在询问口令时直接回车，只删除本机的管理密钥，并提示到手机上移除对应的设备（给出设备名）；之后可以重新管理登录。与手机“忘记 PIN”的处理相同。

### 16.5 管理页面

**启动：**

- `harmonia manager` 只在回环地址（`127.0.0.1`）上监听，默认随机端口，可以用 `--port` 指定。启动后用系统默认浏览器打开页面，同时在终端打印地址；终端保持运行，Ctrl+C 结束。
- 打不开浏览器时（例如通过 SSH 登录）只打印地址，并说明可以用 SSH 端口转发在自己的电脑上打开。
- 页面内嵌在程序里，随程序的签名发布，不加载任何外部资源；手写 HTML、CSS 和脚本，不引入前端构建工具。配色、墨线描边和手绘图形沿用 App 和实例首页，跟随系统深浅色。
- 布局：没有解锁时，左边说明它怎样工作（密钥留在这台电脑、由手机批准、服务器只有密文），右边是要填写的内容。解锁后整页是一张表单：顶栏显示还有多久自动锁定和“锁定”；左栏通过“环境 / 变量库”切换，每次只显示一类列表，以及这一类的新建入口，底部显示这次登录的账号、设备名、服务器；右边是所选环境或变量库。两类列表分别保留本次页面会话中上次选中的条目，从环境打开变量库时同步切换左栏；当前分类为空时显示对应的新建入口。
- 环境详情中，引用的变量库与下方变量表格左对齐，不保留列表的默认缩进。新建、编辑环境时，保存前的预览只显示最终变量数量，不重复列出全部变量名；重名和遮蔽提示仍列出需要处理的变量。
- 加解密全部在 CLI 进程内完成，浏览器只负责显示和提交操作。

**访问控制：**

- 打开的地址带一次性访问码，放在 `#` 之后（不会出现在请求和日志里）。页面用它换取这次会话的令牌，访问码随即作废。
- 令牌只放在这个标签页的会话存储里，通过请求头发送，不使用 Cookie：Cookie 不区分端口，会被本机其他端口上的网站带走。刷新页面不丢，关闭标签页即失效。
- 请求的 Host 必须是本机地址和所监听的端口；带 Origin 的请求必须同源；不开放跨域。
- 响应带严格的内容安全策略，禁止被其他页面嵌入。
- 同一时间只有一个页面会话；要换浏览器或标签页，重新运行 `harmonia manager`。

**解锁与锁定：**

- 页面先要求输入管理口令（还没有管理登录时进入登录）。解开的密钥只在 CLI 进程的内存里，不交给浏览器。
- 以下情况立即锁定并清除内存中的密钥：5 分钟没有操作、关闭页面（30 秒没有收到页面的心跳）、点“锁定”、CLI 进程结束。锁定后页面回到输入口令。
- 解锁期间保持与服务器的推送连接，其他设备上的修改几秒内出现在页面上。

**管理登录（在页面中）：**

1. 说明这会让这台电脑能管理整个账号，建议只在自己日常使用的电脑上开启，不要在多人共用的机器或运行 AI 助手的服务器上开启；确认后继续。
2. 这台电脑还没有日常身份时，填写服务器地址和邮箱。
3. 设置管理口令，确认设备名。
4. 生成管理身份的密钥。批准之前密钥只在 harmonia 进程的内存里；批准后用口令加密再写入本机，所以密钥从第一次写入就受保护，与 App 先设 PIN 的规则相同。
5. 发起配对并声明具备管理功能；可以填写配对码，也可以留空。页面显示二维码和核对码，等待手机批准。
6. 手机上批准，保持“作为管理设备”开启。
7. 批准后同步一次，核对账号根密钥与本机钉住的 `rootPub` 一致，进入管理页面。
8. 手机把它批准成了普通设备时：提示重新发起并在批准页保持“作为管理设备”开启，从账号中移除这次接入，删除刚写入的密钥。
9. 取消、关闭页面、进程结束、请求失效或被拒绝时，配对请求作废（与 5.10 发起方离开相同），内存中的密钥随之丢弃，本机不留下任何文件。

**本里程碑的管理内容：**

- 环境：列表、新建、改名、删除；所选环境显示变量数和能读取它的设备数（全部管理设备，加上授权没有到期的电脑）。
- 变量：以表格显示一个环境的全部变量，名称下方显示备注的第一行，可以按名称或备注筛选（备注 2026-10-14 增加）。值默认遮住，只显示长度；点“显示”“复制”或“编辑”时，页面才向 harmonia 进程取这一个值。新增、修改、删除、多选删除。
- 批量导入：粘贴 `.env` 内容、选择文件，或把文件拖进页面；先列出新增、修改和不变的项以及没有识别的行，勾选确认后写入。
- `.env` 的写法：每行“名称=值”，支持 `#` 注释、`export` 前缀、单引号（原样）、双引号（`\n`、`\t`、`\"`、`\\`、`\$` 转义）和跨行的引号值；同名变量以后出现的为准。
- 跨环境复制：把所选变量复制到另一个环境，同样先对比再确认；在 harmonia 进程内解密再加密，值不经过浏览器。
- 批量写入（导入、复制、多选删除）调用批量写入接口（协议 `PATCH /environments/{id}/variables`，2026-10-15），每批最多 100 项，带幂等键；某一批失败时这一批的每一项都列为失败，可以重试。
- 设置：修改管理口令、退出管理登录。

### 16.6 退出与移除

- **页面里“退出管理登录”**（已解锁）：再输入一次口令 → 通知服务端移除这个管理身份（它是最后一台管理设备时要再确认一次）→ 删除本机的管理密钥。
- **`harmonia manager logout`**：询问口令后做同样的事；直接回车时只删除本机的管理密钥，并提示到手机上移除。
- `harmonia logout` 只退出日常身份，不影响管理登录。`harmonia uninstall` 两个都退出，管理身份按 `harmonia manager logout` 处理。
- 被其他管理设备移除后，在下一次解锁时发现：清除本机的管理密钥并说明原因。

### 16.7 安全口径

- **防得住**：管理密钥文件被复制（备份外流、硬盘被拿走、其他程序在没有解锁时读取），不知道口令解不开。本机其他程序可以连到监听的端口，但没有会话令牌调用不了任何操作。
- **防不住**：与 4.2 第 3 条相同，同一用户下的恶意程序可以在输入口令时记录它、读取解锁期间 CLI 或浏览器的内存，或者替换 `harmonia` 程序本身，这时等同于整个账号泄露。
- **浏览器扩展**：有权读取页面内容的浏览器扩展能看到输入的口令和显示出来的变量值。页面提示在没有不可信扩展的浏览器里使用。
- **离线猜测**：口令没有硬件参与，文件外流后可以离线猜。Argon2id 让每次猜测都要占用 256 MiB 内存和约 1 秒，口令强度由使用者负责。
- **补救**：电脑丢失或文件可能外流时，尽快在手机上移除这台电脑的管理身份。管理身份不在本机保存任何密文和账号根密钥，移除之后即使口令被猜出，对方也无法从服务端取到数据（服务端诚实的前提下）。

### 16.8 后续

在同一个管理页面里分里程碑增加，做之前先补充本节并确认：

- 设备管理：待批准请求与批准、权限、激活与顺序、改名、移除、生成配对码。
- 更换恢复码。

### 16.9 开发与测试

- 口令规则与常见口令表、口令槽、访问控制、批量导入的解析与对比放在 `cli/internal` 并做单元测试；口令槽用独立算出的测试向量核对，其他端不需要实现这个格式。页面本身不写单元测试。
- 端到端脚本增加管理身份：用本地服务端和无界面 Dart 管理脚本批准，再通过本机接口完成解锁、新建环境和批量导入。
- 口令派生要占用 256 MiB 内存，内存不足的机器上程序会直接退出，不适合进行管理登录；README 说明这一点。
- 页面用的手绘图形由 `design/icons/build-manager-glyphs.mjs` 生成。
- 分工不变：我在浏览器里检查页面布局和深浅色；功能验收由你进行。

## 17. 变量库与环境、手机批准解密（M14、M15）

2026-11-09 与用户讨论确定，决策见 12.9。要解决两个问题：

- 同一个 Key 往往用在好几个环境里，现在只能在每个环境里各存一份，改一次要改好几处。
- 电脑上的设备私钥以明文保存在 `keys.json` 里，能读取这个用户文件的程序，或拿到数据目录的人，可以解开这台电脑能访问的全部变量（4.2 第 3 条）。

分两个里程碑做：M14 两层结构（17.1–17.3），M15 手机批准解密和保管进程（17.4–17.6）。协议见 [protocol.md](protocol.md) 的 3.2、3.4、3.9。

### 17.1 两层结构（M14）

| | 变量库 | 环境 |
| --- | --- | --- |
| 放什么 | 变量 | 对变量库的引用，不能新增变量 |
| 钥匙 | 每个变量库一把库钥（就是原来的环境钥） | 没有钥匙，它不保存任何值 |
| 引用别的 | 不能 | 只能引用变量库，不能引用环境，所以只有一层 |
| 谁能看到 | 管理设备；被授权的设备只看到自己的环境所引用的变量库的名字，看不到其中没被引用的变量 | 管理设备，以及被授权这个环境的设备 |

**引用**：每条引用指向一个变量库，有两个选项（2026-11-10 去掉第三项“可以修改”，见第 19 节）：

- **范围**：“全部变量”（这个变量库以后新增的变量也自动包含）或“勾选的变量”。
- **改名**：给某个变量在这个环境里换一个名字，例如把 `OPENAI_API_KEY` 改成 `LLM_KEY`。改名只影响这个环境，变量库里的原名不变。范围是“全部变量”时也可以给其中几个改名。

规则：

- 一个环境可以引用多个变量库；同一个变量库在同一个环境里只能有一条引用。一个变量库可以被任意多个环境引用。
- **环境里的名字不能重复**：名字全部来自引用，所以保存环境时就检查改名后的最终名字，有重复时拒绝保存，并指出是哪几个名字、来自哪些引用，让用户改名或取消勾选。改名后的名字要符合变量名的规则（协议第 1 节）。
- 唯一的例外：范围是“全部变量”的变量库以后新增了一个和环境里其他名字相同的变量。这时按引用的先后顺序取值，排在前面的引用优先；App 的环境详情、CLI 的 `status` 和 `env list` 指出这个同名变量和修复方法（给其中一个改名）。
- **新建变量库**只建变量库，不再同时创建环境；需要给电脑用时，到“环境”里新建环境并引用它。App 和命令行的管理页面一致。
- **删除变量库**：确认框列出引用它的环境。删除后这些环境里对应的引用显示为“已失效”，不再提供变量，由管理设备删掉或换成其他变量库。
- **删除环境**：同时删除设备对它的授权，变量库不受影响。
- 变量库和环境的改名只改名字，ID 不变，命令行里用 ID 指定的写法继续有效；用名称指定时需要同步修改脚本中的名称。环境名不能重复（5.7、第 19 节）。

### 17.2 授权

- **设备只能被授权环境**。授权仍然分只读和读写，可以设到期时间，另加一项“允许本机解密”（默认关闭）。管理设备能看到并管理全部变量库和环境。
- **能读什么**：环境里引用到的变量，用环境里的最终名字。
- **能改什么**：这台设备对环境有读写权限，就能修改这个环境里的变量（2026-11-10 调整，原来还要求变量所在的引用开启“可以修改”）。写入的是变量库里的原变量，所有引用它的环境都会看到新值，CLI 写入前提示这一点并要求确认（`--yes` 跳过）。
- **新增变量必须指定变量库**（2026-11-09 用户确定）：`var set --vault <变量库> <变量名>`、`import --vault <变量库>`（名称或完整 ID）。这台设备必须有一个读写授权的环境，其中有一条引用这个变量库的“全部变量”引用，否则提示到管理设备上调整。目标写成环境、而变量在环境里不存在时，报错并列出这台设备可以新增变量的变量库，提示改用变量库。
- **修改和删除已有变量**：目标可以写环境（用环境里的名字，改名过的也行），也可以写变量库（用原名），都写回变量库里的原变量。提示会影响所有引用它的环境。`var set <环境> <变量名>`、`var rm <环境> <变量名>` 的位置参数只按环境解析；操作变量库必须写成 `var set --vault <变量库> <变量名>`、`var rm --vault <变量库> <变量名>`。两种目标都支持名称或完整 ID；不按名称或 ID 自动切换目标类型，环境中没有变量时不转到同名变量库新增。
- **激活与顺序**：和现在相同，只在环境之间排。
- **允许本机解密**（开启时）：管理设备先验证设备证书，再把这个环境引用到的全部变量库的库钥封装给这台设备，电脑可以随时在本机解密，和以前一样。环境以后新增对另一个变量库的引用时，管理设备在保存环境的同一个请求里，为所有开启了本机解密的授权补上新变量库的封装；某个变量库不再被这台设备任何开启本机解密的授权用到时，服务端删除给它的封装。
- **允许本机解密**（关闭时，默认）：不给这台设备封装任何库钥。服务端只下发环境和变量名，不下发变量密文；变量值只能通过手机批准拿到（17.4）。
- **部分引用的边界**：开启本机解密时，设备拿到的是整个变量库的钥匙，“只勾选部分变量”由服务端执行，不是密码学边界，界面上要说明。手机批准时，手机只解开并交出请求的那几个变量，部分引用就是真正的加密边界。
- **开启本机解密要再验证一次**。开关在每个环境的授权面板底部可展开的“高级”里，标题是“无人值守使用（本机解密）”（2026-11-10 调整，见第 19 节），下方只说明区别：关闭时“每次使用需在手机上批准”，开启时“无需手机批准，仅建议在服务器或 CI 上开启”。在面板里点“保存”时如果是新开启，先弹确认框说明风险：“开启后，相关变量库的密钥将保存在此设备上，能访问此设备文件的人员或程序均可解密其中的变量。”（其中的变量包括这个环境没有选中的。）

### 17.3 数据转换

- 服务端用表结构迁移完成，不需要重新封装，设备也不需要重新接入：
  - 每个原来的环境转成一个**同 ID、同名**的变量库。变量密文、封装和 `keyVersion` 原样保留：变量的 AAD 里用的就是这个 ID（协议第 2 节），所以 ID 必须沿用。
  - 再为每个变量库建一个同 ID、同名的环境，引用它的全部变量，开启“可以修改”。脚本里写的 `--env <ID>` 继续有效。（2026-11-10 起去掉“可以修改”，见第 19 节。）
  - 设备原来的授权转到这个环境上，权限、到期时间、激活状态和顺序不变，**开启“允许本机解密”**，这样已有的电脑升级后照常工作。
- 升级后不自动关闭本机解密（那会让服务器和 CI 上的电脑突然无法使用），也不额外提示；需要时在设备详情里逐个关闭。
- 1.0 之前不保留旧接口和旧数据格式；服务端、App 和 CLI 一起升级，CLI 的升级前预检（5.11）会挡住与服务器不一致的版本。

### 17.4 手机批准解密（M15）

**读取变量：**

1. **触发**：`exec`、`export`、`var get` 等需要变量值的命令，用到某个没有开启本机解密的环境时，先问保管进程（17.5）有没有这次要用的变量；缺的变量合在一起发一个请求。只需要变量名的命令（`var list`、`env list`、`status`）不发请求。开启了本机解密的环境照旧在本机解密，同一条命令里两种可以混用。
2. **请求**：CLI 在内存里生成一对临时密钥，用设备签名钥签名后提交。请求里写明：这台设备、要运行的命令（程序名和参数，过长时截断）、所在目录、要用哪些环境的哪些变量名、临时公钥。
3. **电脑上的提示**（stderr，不论是不是终端都输出）：“已请求手机批准，请在手机上核对请求码 7KQ2 后批准。最多等待 2 分钟，Ctrl+C 取消。”请求码由请求内容的哈希得出（协议 3.9），手机上显示同一个码。
4. **手机上**：App 在前台且已解锁时，收到推送或同步时发现就直接弹出批准页，和配对码的请求一样；App 在后台时发系统通知（M16，第 18 节），回到前台或解锁后，仍在等待的请求随即弹出。批准页显示：设备名和平台、请求码、命令、目录，按环境列出变量（改过名的显示“来自 变量库 / 原名”）；选择有效时长和授权范围；“批准”要验证指纹或 PIN，“拒绝”不需要。页面提示“确认是你刚在电脑上发起的、请求码一致，再批准”。
5. **多久内不再询问**（2026-11-10 由“有效时长”改名）：仅这一次、30 分钟、2 小时、8 小时、自定义（1 分钟到 30 天）、长期（下方小字“到电脑重启或退出登录为止”）。默认选中这台设备上次的选择，第一次为“仅这一次”。
6. **授权范围**：“仅这个终端”（默认）或“这台电脑上的所有程序”（用于 IDE、AI 工具这类不在终端里运行的程序）。“仅这一次”时不显示这一项。
7. **手机核对后交出变量**：验证请求的设备签名（设备证书由 root 签名），按自己同步到的数据检查：环境已授权给这台设备、没有到期、没有开启本机解密、请求的变量都在环境里。核对通过后只解开这几个变量，用临时公钥加密，root 签名，提交批准。服务器转发但解不开，也无法替换临时公钥或伪造结果。
8. **电脑上**：验证 root 签名，解开变量，运行命令。有效时长不是“仅这一次”时，把变量交给保管进程。
9. **没拿到时**：`exec` 的退出码为 125，说明原因和下一步，例如“手机上拒绝了这次请求”，或者“2 分钟内没有在手机上批准，请重新运行。需要无人值守运行时，可以在手机上为这台电脑的这个环境开启‘允许本机解密’”。

**写入变量**（`var set`、`var rm`、`import`，只用于没有开启本机解密的环境）：

- CLI 把新的值（协议 2.6 的明文，连同变量名和所在变量库）分别加密给每一台管理设备（用同步得到的管理设备公钥，先验证设备证书），签名后提交请求。
- 手机批准页列出要写入或删除的变量名，值默认遮住，可以点“显示”；批准后由手机用库钥加密并调用批量写入接口写入，再标记请求已批准。电脑上输出“已在手机上批准并写入”。
- 写入请求没有有效时长，每次都要批准；不经过保管进程。电脑上拿不到库钥，所以没有本机回读校验，由手机写入后核对。

### 17.5 保管进程

- **单独的进程**：有效时长不是“仅这一次”时，CLI 启动一个只负责保管批准结果的进程（已经在运行时直接交给它）。变量只放在它的内存里，从不写磁盘。它与后台服务无关：后台服务升级或重启不影响它，没有安装后台服务也能用。没有任何生效的授权时它自己退出。
- **本机通道**：macOS 和 Linux 用数据目录下的 Unix 套接字（目录 0700），Windows 用只允许本人访问的命名管道。保管进程核对请求方是同一个用户。
- **不让同一用户的其他程序读它的内存**：Linux 设置不可转储（`PR_SET_DUMPABLE=0`），同一用户的程序读不到它的内存，也不能调试它；macOS 系统本身不允许普通程序读取其他进程的内存；Windows 收紧进程的访问权限，不允许本用户读取内存（只能挡住一部分）。另外锁定内存不进交换区，关闭崩溃转储。
- **仅这个终端**：保管进程查出请求来自哪个进程、属于哪个终端会话（macOS 和 Linux 是会话 ID，分别通过 `LOCAL_PEERPID`、`SO_PEERCRED` 得到对方进程）。其他会话来要变量时需要重新批准；那个终端关闭后，它的授权随之结束。Windows 按发起进程所属的控制台区分，实现时在虚拟机里验证；做不到时 Windows 只提供“这台电脑上的所有程序”，批准页说明原因。
- **结束**：时间到、电脑重启、退出登录、`harmonia lock`、在手机上点“结束”、设备被撤销、授权被删除或到期、环境的引用改变。某个变量在有效期内被修改时，保管进程丢掉它，下次使用时重新请求，不会继续用旧值。
- **手机上能看到、能结束**：设备详情显示“正在生效的授权”：环境和变量、授权范围、剩余时间（长期的显示“长期”）、“结束”。结束通过服务器推送通知保管进程；电脑不在线时，到它下次连上服务器才结束，App 说明这一点。
- `harmonia status` 列出正在生效的授权；`harmonia lock` 结束这台电脑上的全部授权。

### 17.6 其他功能的变化

- **Shell 集成、Windows 写入用户环境变量**：需要随时有明文，只包含开启了本机解密的环境；其他环境跳过，`status` 说明原因。
- **后台服务**：同步变量名、开启本机解密的环境的密文，以及上面两项的写入，不发起批准请求。
- **本机覆盖**：不变，仍是本机明文保存的值；`override set` 的帮助里写明这一点。
- **给 AI 助手的说明**（5.13）：说明需要用户在手机上批准，看到提示时告诉用户请求码并等待；被拒绝或超时不要反复重试；需要无人值守时由用户自己在手机上开启本机解密，AI 助手不代为决定。
- **App**：底栏分“变量库”“环境”“设备”“设置”四个标签，打开 App 默认在“变量库”；变量库和环境各自一个列表，右上角的加号直接新建对应的一种；新增变量库列表和详情、环境编辑（添加引用：选变量库 → 全部或勾选 → 改名；2026-11-10 去掉“可以修改”）、批准页、“正在生效的授权”；设备详情的授权改为按环境，每个环境多一个“允许本机解密”开关（2026-11-09 起每个环境单独在底部面板里修改并保存，见 5.9 的设备详情）。页面调试目录同步增加这些页面和分步状态的合成场景（名字冲突、引用已失效、请求等待中、已失效、批准、拒绝），全部走模拟实现。
- **电脑上的管理页面**（第 16 节）：环境和变量的管理改为变量库、环境两层，M14 一起调整。管理页面暂时不处理批准请求，只在 App 上批准（2026-11-09 用户确定）。

### 17.7 安全口径

- **防得住**（没有开启本机解密的环境）：数据目录被拷走、进了备份、电脑丢失，里面没有任何能解开变量的东西（本机覆盖除外）；服务器看不到值，不能伪造批准结果，也不能替换临时公钥（请求由设备签名，结果由 root 签名）。
- **防不住**：
  - 有效时长内，同一用户下的程序可以向保管进程要变量（授权范围是“仅这个终端”时只限那个终端里的程序），也可以读取运行中程序的环境变量。
  - 电脑上的恶意程序可以用设备私钥发起一个请求，诱导你批准。防护靠请求码、命令和目录，以及只批准自己刚发起的请求。
  - 服务器可以不转发请求或结果，让你用不了，但不会泄露明文；服务器能改动环境的组成，但手机批准页按变量名逐个列出要交出的内容，你看得到。
  - 手机被他人拿到且对方知道 PIN，同 4.2 第 2 条。
- **开启了本机解密的环境**：同 4.2 第 3 条。
- **可用性**：手机不在身边或没有网络时，没有开启本机解密的环境用不了；服务器、CI 等无人值守的场合需要开启本机解密。

### 17.8 开发与测试

- 核心逻辑放在 `server/src/core`、`cli/internal`、`app/lib/core` 并做单元测试：环境最终名字和冲突的计算（三端结果一致，放进测试向量）、服务端按授权计算可见的变量和封装、数据转换、批准请求和结果的签名与加密（`mise run vectors` 和三端测试）、保管进程的授权范围与结束条件。
- 端到端脚本增加：两层结构下的授权和读取、开启与关闭本机解密、手机批准（无界面 Dart 管理脚本批准和拒绝）、保管进程的有效时长和 `lock`。
- M14、M15 各自新增代码超过约 5,000 行时停下确认（AGENTS.md 第 7 条）。

## 18. App 后台通知（M16）

2026-11-09 与用户讨论确定，决策见 12.10。App 不在前台时可能无法处理 WebSocket 事件，因此有新的批准请求或配对码请求时经推送中继发系统通知，点开进入 App，解锁后批准页照常弹出。发送范围和前台展示规则见 18.2、18.4。

通知只是提醒，不携带任何数据；收不到时流程不受影响，CLI 的提示和 App 在前台时的自动弹出都不变。协议见 [protocol.md](protocol.md) 3.10 和第 5 节。

### 18.1 结构

```
App ──登记推送令牌──▶ 推送中继 ──返回句柄──▶ App ──交给──▶ 实例
实例 ──有新请求：句柄 + 事件类型──▶ 推送中继 ──▶ APNs / FCM ──▶ 手机
```

- **推送中继**：一个独立的 Workers 服务，代码在 `relay/`，只由发布者部署，地址写在 App 和服务端的代码里。APNs 密钥（.p8）和 FCM 服务账号只放在中继里，实例拿不到。
- **为什么要中继**：推送凭据和 App 的身份绑定（APNs 按 Team 和 bundle ID，FCM 按 Firebase 项目），属于发布者；实例由各个用户自己部署，不能把凭据发给每个实例。
- **句柄**：App 向中继登记推送令牌，中继返回一个随机句柄；App 把句柄交给实例，实例只保存句柄，看不到推送令牌。句柄本身就是凭证，持有它就能让中继给这台手机发通知，所以实例把它当密钥保存。中继只保存句柄的 SHA-256，中继的数据泄露也不能拿来发通知。
- **不影响自部署**：`relay/` 不在 `server/` 目录里，发布到 harmonia-worker 时不会带上（5.1）。`server/` 不能引用 `relay/` 的代码。

### 18.2 什么时候发

- **批准请求**：新的批准请求的等待连接建立时，这时请求才会出现在 `GET /approvals` 中（协议 3.9）。
- **配对请求**：由配对码发起的配对请求的等待连接建立时。匿名请求不发，和前台弹出的规则一致（5.10）。
- **发给谁**：登记了句柄、状态有效且不需要轮换恢复码的管理设备，无论 App 是否在前台、是否连着 `/events` 都发送（2026-11-10 用户确认）。通知横幅由 App 按前后台状态处理，前台仍直接弹出批准页。电脑上的管理身份不登记句柄。
- **不发**：请求被批准、拒绝、取消或过期，“批准成功”“配对成功”，变量变化，授权结束。
- 发送失败不重试，也不影响请求本身。中继答复句柄已失效时，实例删除这个句柄。

### 18.3 通知内容

- 文案由中继按事件类型生成，实例只传类型，不能传文字：
  - 批准请求：标题“Harmonia”，正文“有一个待批准的请求，打开 App 查看”。
  - 配对请求：标题“Harmonia”，正文“有设备请求接入，打开 App 查看”。
- 不带设备名、命令、目录、变量名和服务器地址：通知内容会经过苹果、谷歌的服务器。
- **有效期**：等于请求本身的有效期，批准请求 2 分钟，配对请求 5 分钟，由中继按类型固定。手机关机或断网超过这个时间，之后不会再收到。
- **合并**：同一类通知在手机上只保留最新的一条（APNs 的 `apns-collapse-id` 和 FCM 的 `tag` 都用事件类型）。
- **不撤回**：请求处理或过期后，已经显示的通知不撤回（用户确定）。点开时已经没有待处理的请求，App 提示“这个请求已处理或已过期”。
- iOS 不申请“时效性通知”能力，按普通通知显示。Android 建一个通知渠道“批准请求”，重要性为高。

### 18.4 App

- **平台实现**：
  - Android：原生 Kotlin 直接使用 `firebase-messaging`，不用 Flutter 插件，与 14.1 的其他 Kotlin 实现放在一起。不提交 `google-services.json`：发布构建由 CI 从 Secrets 以 `--dart-define` 传入 `FIREBASE_APP_ID`、`FIREBASE_API_KEY`、`FIREBASE_PROJECT_ID`，Gradle 把它们写成 Firebase 自动初始化读取的资源；没有传入的构建不初始化 Firebase，按“收不到”处理。通知由 FCM 在 App 不在前台时直接显示，图标用启动图标的单色层。
  - iOS：原生代码申请通知权限、取得 APNs 令牌，经平台通道交给 Dart，与 14.1 的其他 Swift 实现放在一起。令牌属于哪个 APNs 环境按安装包里描述文件的 `aps-environment` 判断：开发描述文件是测试环境，其余（Ad Hoc、TestFlight、App Store）是正式环境，登记时告诉中继。工程加上推送能力（`aps-environment`）。
  - 两端经平台通道 `harmonia/push` 提供：通知权限的查询与请求、推送令牌、打开系统的通知设置、“用户点开过通知”。
- **请求通知权限**：手机第一次成为管理设备、进入主页时请求一次（首次设置完成、作为管理设备被批准、用恢复码恢复之后）；已经是管理设备的手机升级后，第一次进入主页时请求一次。只请求一次，用户拒绝后不再弹出。
- **登记**：有权限并且开关打开时：取得推送令牌 → 向中继登记，得到句柄 → 交给实例（协议 3.10）。之后每次回到前台，最多每天一次向中继确认登记，令牌变了也在这时更新；中继答复句柄不存在时，重新登记并把新句柄交给实例。
- **设置 → 后台通知**：开关，默认打开，下方一行状态：
  - 正常：“有新的请求时通知你”。
  - 开关关闭：“已关闭。打开 App 时仍会看到待批准的请求”。
  - 还没有请求过系统权限（例如第一次进入主页时没有弹出）：“还没有允许 Harmonia 发送通知”，附“允许通知”。
  - 系统权限被关闭：“通知已在系统设置中关闭”，附“打开系统设置”。
  - 拿不到推送令牌（没有 Google 服务、网络不通、自行签名的 iOS 版本等）：“这台手机暂时收不到后台通知，打开 App 时会看到待批准的请求”。
  - 实例关闭了推送（18.6）：“这台服务器关闭了后台通知”。

  关闭开关时向实例和中继删除句柄；重新打开时重新登记。
- **点开通知**：打开 App，按 App 锁规则解锁后先同步，仍在等待的请求随即弹出（5.10、17.4）；没有时提示“这个请求已处理或已过期”。App 在前台时收到通知不显示横幅，仍直接弹出批准页。
- **退出登录、本机被撤销**：App 尽力向中继删除句柄；撤销时实例删除它保存的句柄，并尽力通知中继删除。
- **页面调试**：设置页的“后台通知”增加合成场景：正常、系统权限已关闭、收不到、服务器已关闭、开关切换、请求通知权限、点开已失效通知的提示。全部走模拟实现，不申请真实权限、不取推送令牌、不访问中继。

### 18.5 推送中继

- **运行时**：Hono + Durable Object（SQLite），和服务端一样运行在 Workers 上。每条登记保存：句柄的 SHA-256、平台、推送令牌、APNs 环境、登记时间、最近确认时间和限流计数；不保存 IP。
- **接口**（协议第 5 节）：登记、确认、删除（App 调用），发通知（实例调用）。
- **发送**：
  - APNs：HTTP/2，用 .p8 签 ES256 的 JWT，每 40 分钟左右更换；topic 为 App 的 bundle ID。
  - FCM：HTTP v1 接口，用服务账号签 RS256 的 JWT 换取 OAuth 令牌，缓存到过期前。
  - APNs 返回 `BadDeviceToken`、`Unregistered`、`DeviceTokenNotForTopic`，或 FCM 返回 `UNREGISTERED` 时，删除这条登记，并答复实例句柄已失效。
- **限流与防滥用**（数值见协议第 5 节）：
  - 同一个句柄、同一类通知 10 秒内最多发一条，多出来的合并掉，照常答复成功：手机上同一类通知本来只显示一条。每个句柄每天另有 1000 条的上限，只作兜底。
  - 登记按网络限制次数。
  - 全局每分钟上限，默认 1000 条，可以用部署变量调整，主要保护中继的 Workers 用量。所有实例共用这份额度，被打满时大家暂时收不到通知，流程不受影响。
  - 限流按句柄（每台手机）计算，与实例无关：一个实例上有多少用户都互不影响。发通知不按来源 IP 限流：实例都运行在 Cloudflare 上，出口 IP 是共用的。
  - 文案固定、句柄猜不到，拿到句柄的人最多每 10 秒发一条通用通知；在设置里关闭再打开“后台通知”，旧句柄即失效。
- **清理**：90 天没有确认过的登记删除。App 每天确认一次，正常使用的手机不会被清理。
- **部署**：
  - 单独一个 Worker（`harmonia-relay`），绑定专用域名 `harmonia-push.zzz.sd`（2026-11-09 用户确定），`https://harmonia-push.zzz.sd` 就是写进 App 和服务端代码的常量。旧版本会一直使用这个地址，不能更换；用一级子域名，由 Cloudflare 的通用证书覆盖。不和发布者自己的实例合在一起：实例代码从 `server/` 发布，中继凭据不应和实例放在一起，两边也要能分开部署和回滚。
  - 不另建发布仓库，也不 Fork：harmonia-worker 存在是因为每个用户都要 Fork 一份部署到自己的账号，中继只有发布者一个部署者，直接从主仓库部署。
  - 部署流水线 `deploy-relay.yml`：打正式版本标签（不含“-”）时，或在 Actions 页面手动运行；先跑中继的测试，再在 `relay/` 下执行 `wrangler deploy`。GitHub Secrets 只放 `CLOUDFLARE_API_TOKEN`（只授予这个账号的 Workers 部署权限）和 `CLOUDFLARE_ACCOUNT_ID`；APNs 和 FCM 的凭据只在 Cloudflare 控制台的 Worker Secrets 里填写一次，不进 GitHub。`wrangler.jsonc` 设 `keep_vars: true`，部署不覆盖控制台里的配置。
  - 正式标签同时发布服务端和中继，中继随版本更新；中继接口只做增量修改（12.10），先部署中继、再发布用到新接口的 App 和服务端不会出问题。
  - 同一个 Cloudflare 账号下所有 Worker 共用免费套餐的每日请求额度；用户多了以后中继可能挤占发布者自己实例的额度，到时升级付费套餐或把中继放到单独的账号。
- **配置**：凭据放在中继 Worker 的 Secrets：`APNS_KEY`、`APNS_KEY_ID`、`APNS_TEAM_ID`、`APNS_TOPIC`、`FCM_SERVICE_ACCOUNT`；全局上限用部署变量 `NOTIFY_GLOBAL_PER_MINUTE`（默认 1000）。

### 18.6 服务端

- 新增部署变量 `PUSH_NOTIFICATIONS`，默认开启。设为 `false` 时实例不接受句柄、不联系中继，`GET /instance` 返回 `push:false`，App 显示“这台服务器关闭了后台通知”。给不希望实例连接外部服务的部署者使用。
- `devices` 表增加 `push_handle`，设备被撤销或本机退出时删除。
- 通知在请求处理完后用 `waitUntil` 发出，不拖慢响应。
- 中继地址是代码里的常量，不做成配置：句柄只在登记它的中继上有效，地址必须和 App 里的一致。自己打包 App 的 Fork 需要同时修改 App 和服务端的常量，并部署自己的中继。
- 只用于本地开发的 `DEV_PUSH_RELAY_URL`：服务端的部署变量和 App 的 `--dart-define` 同名，把中继地址换成本地 `wrangler dev` 的地址。部署和发布构建都不设置。

### 18.7 安全口径

- **中继看得到**：推送令牌、句柄的哈希、每次通知的时间和类型。看不到账号、邮箱、设备名、变量或任何密文；实例发来的请求出口 IP 属于 Cloudflare，也看不出来自哪个实例。
- **苹果、谷歌看得到**：通用文案和通知时间。
- **中继被攻破或作恶**：只能发假的通用通知（用户打开 App 发现没有请求）或者不发；不能读取或修改任何数据，批准仍然要在 App 里核对请求码，配对仍然要扫码或核对核对码。
- **实例的数据泄露**：拿到句柄的人能在限额内给手机发通用通知；在设置里关闭再打开“后台通知”，旧句柄即失效。
- 不改变第 4 节和 17.7 的任何保证。隐私政策要写明使用了推送，以及中继保存哪些内容（上架时一并准备）。

### 18.8 覆盖范围

- **Android**：手机有 Google 服务、并且连得上 FCM 时能收到。侧载安装的 APK 同样可以，FCM 不检查安装来源。
- **iOS**：只有发布者签名的版本能收到。用户用自己的证书或签名工具重签的 IPA，推送令牌不属于发布者的 App，收不到。GitHub 的未签名 IPA 与 TestFlight 内部测试包同时保留（14.4），后者可使用发布者的 APNs 正式环境；开发时用 Xcode 签名安装到真机上验证（APNs 测试环境）。
- 收不到的手机按 18.4 显示说明，流程不受影响。

### 18.9 开发与测试

- 核心逻辑放在 `relay/src/core`、`server/src/core`、`app/lib/core` 并做单元测试：中继的句柄登记与哈希、限流、APNs 和 FCM 请求的构造与错误归类；服务端什么时候发、发给谁、句柄失效后的清理；App 的登记状态（权限、开关、令牌变化、句柄失效后重新登记）。
- 中继提供只用于本地的 `DEV_FAKE_SENDER=true`：不连接 APNs、FCM，把要发的通知写进日志。端到端脚本用它验证“新请求 → 实例 → 中继”这一段：无界面管理脚本用假的推送令牌登记，脚本检查中继日志里出现了配对请求和批准请求的通知，匿名配对请求没有。
- 真机上的通知由用户验收。本地 `wrangler dev` 在 macOS 上调用 APNs 有已知问题（cloudflare/workerd#4841），真实发送只在部署后的中继上验证；部署中继由发布者在 Cloudflare 上操作。
- mise 任务：`test-relay`、`dev-relay`、`deploy-relay`（发布者在本机手动部署时用，正常由 `deploy-relay.yml` 部署）；`ci.yml` 的路径过滤增加 `relay/**` 和中继的测试任务。
- AGENTS.md：仓库说明加上 `relay/`，核心逻辑目录加上 `relay/src/core`。
- 新增代码超过约 5,000 行时停下确认。

## 19. 环境与授权简化（2026-11-10）

用户真机试用 0.13 后提出：环境页里有一个和变量库相同的 ID，改名要进“编辑引用”，“可以修改”放在引用上难以理解，“允许本机解密”像在鼓励打开，两个“有效期”分不清。决策见 12.11。

### 19.1 去掉引用上的“可以修改”

- 引用只剩范围和改名两个选项。电脑能不能修改、删除环境里的变量，只看它对这个环境的授权是不是“读写”；写入的仍是变量库里的原变量，CLI 照旧提示会影响所有引用它的环境。
- 电脑新增变量：要有一个读写授权的环境，其中有这个变量库的“全部变量”引用。
- 服务端迁移去掉已存数据里的 `writable`；协议里引用、同步的 `items` 不再有这个字段（协议 3.2、3.4、3.9）。

### 19.2 环境 ID 的显示与使用

- App 环境详情显示可复制的完整环境 ID，`harmonia env list` 显示 ID 列。电脑上的管理页面环境详情同样显示可复制的环境 ID。
- CLI 所有指定环境的位置均支持完整 ID 或名称：先精确匹配 ID，再按名称匹配（不区分大小写）。包括 `--env`、`环境ID:变量名`、环境启用/停用/排序、本机覆盖，以及 `var set`、`var rm` 的目标。环境改名不改变 ID，按 ID 指定的脚本继续有效。
- `harmonia var set <环境ID> <变量名>` 可以修改该环境中已有变量的值或备注；`harmonia var rm <环境ID> <变量名>` 删除对应变量库中的原变量，所有引用它的环境都会受到影响。变量名使用环境中的名字；仍要求该设备具有未到期的读写授权，未开启无人值守使用时由手机批准。
- `var set` 和 `var rm` 不加 `--vault` 时只查找环境；加 `--vault` 时只查找变量库，变量名使用变量库中的原名。加 `--vault` 时位置参数只保留变量名及 `set` 可选的值，不再填写环境目标。移除旧的变量库位置参数用法和同名变量库自动新增路径，即使环境与变量库同名或同 ID 也按显式类型处理。
- 新增变量使用 `harmonia var set --vault <变量库名称或ID> <变量名>`，`import --vault` 继续只接受变量库名称或完整 ID；授权条件不变。
- CLI 配套 skill 同步更新目标类型和示例：临时操作使用名称；生成脚本、CI 或长期配置时优先使用完整 ID；用户已经指定名称或 ID 时沿用其选择。ID 区分大小写，名称不区分大小写。
- 环境名不能重复：新建或改名时与已有环境重名（去掉首尾空白、不区分大小写）就拒绝，提示换一个名字。服务端迁移时，已有的重名环境按创建先后在后面加“ 2”“ 3”。
- 授权被撤销或环境被删除后，电脑同步时自动删除它留下的本机覆盖；恢复按 ID 指定环境不改变这项清理行为。

### 19.3 授权面板与期限

- 面板上方只有“权限”（只读、读写）。底部“高级”默认收起，展开后是“无人值守使用（本机解密）”开关，下方说明照旧（关闭时“每次使用需在手机上批准”，开启时“无需手机批准，仅建议在服务器或 CI 上开启”）；开关打开后才出现“期限”（长期有效、1 天、7 天、30 天、90 天），说明“到期后这台电脑不能再使用这个环境”。已经开启的授权打开面板时，“高级”默认展开。
- 新开启时的风险确认、设备详情行上的“本机解密”标记保留。
- 需手机批准的授权一直有效，直到取消授权。保存时关闭了无人值守使用的授权，期限一律存为一直有效（协议里 `expiresAt` 为 0）；以前设过期限的这类授权，行上照常显示到期时间，下一次保存时改为一直有效。
- 批准页的“有效时长”改名为“多久内不再询问”，选项不变；保管进程照旧在授权到期或被取消时结束。
- 协议不变：`expiresAt` 字段保留，服务端照旧按它判断到期。

### 19.4 环境页的变量面板

- 环境详情里点一个变量，从底部弹出变量面板：显示环境里的名字、来自哪个变量库和原名、备注；操作有：
  - **改名**：只改这个环境里的名字，保存环境的引用（与“编辑引用”里的改名相同，检查重名）；改回原名即取消改名。
  - **从环境中移除**：只在变量来自“选中的变量”引用时显示，取消勾选后保存；来自“全部变量”引用时显示说明“这个变量来自‘全部变量’，要单独移除，请在编辑引用里改为选中的变量”。
  - **编辑值和备注**：进入变量库里这个变量的编辑页，说明修改会影响所有用到它的环境。
- “编辑引用”保留，负责添加、移除变量库，选全部或勾选，调整顺序；其中的改名入口保留。
- 页面调试目录增加变量面板的几种合成场景（改名过的变量、来自全部变量的变量、来自选中的变量），授权面板增加“高级”收起和展开、开启无人值守使用的场景。

### 19.5 开发与测试

- 三端去掉 `writable` 后更新测试向量（`vectors/refs.json`）并运行 `mise run vectors` 和三端测试；端到端脚本覆盖环境名称、完整环境 ID 和 `环境ID:变量名` 的选择，以及按环境 ID 修改和删除已有变量。页面调试的环境详情场景同步展示可复制的环境 ID。
- 电脑上的管理页面（第 16 节）同步去掉“可以修改”，新建、改名环境时显示重名的错误。
